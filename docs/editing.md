# 編集と公開

編集は admin が draft に対して行い、公開は admin の単独操作。データ提供者やレビュアは共有リンクから
preview とコメントだけができる。

モデルの側の不変条件は [data-model.md](data-model.md) にある。ここは操作とその制約。

## 誰が何をできるか

認証は Keycloak (DDBJ 所管)。**1 人 1 アカウントとし、共有アカウントは持ち込まない** — 共有
アカウントを許すと証跡の解像度がそこで失われる。

- **人と結び付ける key は Keycloak の `sub`。** `preferred_username` は表示にだけ使う。変わりうる値を
  key にすると、改名で権限と証跡の主体が切れる
- **admin かどうかは v2 側が持つ。** Keycloak の role には寄せない。realm が他組織の所管なので、role の
  付与が依頼になり担当者の交代に即応できない。Postgres に状態だけを持ち、管理画面から付け外しする
- **認可は要求ごとに server 側で導出し、cookie に焼かない。** admin を外せば次の要求から効く
- **役割は admin ひとつ。** 認可のコードは capability で書き、admin は全 capability を持つ唯一の役割

| capability | 何を許すか |
|---|---|
| `view-unpublished` | 管理画面で未公開を読む |
| `edit-content` | draft の作成・編集・破棄、共有リンクの管理、コメントの解決 |
| `publish` | 版の公開と fix |
| `withdraw` | 取り下げと再公開 |
| `manage-labels` | hum ラベルと dataset id の pin と解除 |
| `manage-files` | ファイルの upload と公開状態の切り替え |
| `manage-catalog` | catalog のキーと語彙 |
| `manage-admins` | admin の付け外し |
| `delete-research` | research の削除 |

**ログイン済みで admin でない主体は capability を 1 つも持たない。** 導出を「主体 → capability の集合」の
形にしてあるので、後から一般利用者向けの操作を足すときに認可の形を触らずに済む。

**要求する capability は操作の名前で書く。** admin が全部を持つので実際の答えは変わらないが、読み取り
だけの画面は `view-unpublished` を、書き込みと編集画面は `edit-content` を通る。後から役割を足すときに
call site を読み直さずに済む。

**認可が返す答えは 3 つだけ。** 未ログインはサインインへ送って元の場所に戻す。ログイン済みで capability が
無ければ 403 — サインインし直しても答えは変わらないので、redirect にしない。あれば主体を返す。

## セッション

**cookie に入れるのは推測不能な値 1 つで、セッションの中身は Postgres の行が持つ。** cookie の中身が
認可の根拠になる余地を構造的に消すためで、「認可を cookie に焼かない」を cookie の形の側からも守る。

- **行は cookie の値の hash を持つ。** 行を読めることと、その人になりすませられることを別にする
- **ログアウトは行を消すこと**なので server 側で即座に効く。cookie を消すだけにしない
- **期限は 2 本** — 最終アクセスから 7 日と、発行から 30 日。cookie の寿命を後者にして前者は読み取りの
  ときに判定する。最終アクセス時刻の更新は値が 1 時間より古いときだけで、**ページを読むことが書き込みに
  ならない**。期限切れの行の掃除はログインのときに行う
- **Keycloak の token は保存しない。** public API に認証が無く、token を付けて転送する先も無い。例外は
  id_token だけで、Keycloak 側のセッションを終わらせる `id_token_hint` に要る
- **client は public client + PKCE (S256)。** 長期の credential を 1 つも持たないので、client secret が
  守る対象が無い。`state` と PKCE の verifier と戻り先は 10 分の cookie に置く
- **戻り先はサイト内のパスに限る。検査は結果の側で行う** — `/..//example.com` は「このサイトのパス」として
  parse できてしまい、`Location` に入った瞬間に別のホストになる
- **session の行は失ってよい。** 失えば全員が再ログインするだけなので、backup も移行の対象にならない

**最初の admin は管理画面からは作れない。** 付け外しは `sub` を指定して行い、`sub` を表示するのは管理画面
だけだから。ここは 2 つで解く。

- **管理画面の入口はセッションだけを要求し、開いた人自身の `sub` を見せる。** 見せるのは本人の identity
  だけで、ポータルのデータは capability の要る画面の側にある
- **付け外しは CLI からもできる。** dev の初期 admin も、本番の初期 admin (移行の作業項目) もこれで入れる。
  CLI 由来の event の actor は人ではないので、予約された値を焼く

## 管理画面

`/admin/research` が一覧、`/admin/research/:researchId` が 1 研究、その下の
`/admin/research/:researchId/draft/:draftId` が編集フォーム。公開ページと同じく ja / en の両方に
アドレスを持つ。

**research は identity で指す。** hum ラベルはまだ pin されていないことがあり、pin は訂正もされるので、
管理画面のアドレスをラベルに寄せると開けない研究と動くアドレスが生まれる。

**一覧の窓は直引きで、公開検索ではない。** 全文索引は公開分しか持たないのに、この一覧の主役は未公開の
方にある。窓は hum ラベル・dataset id・研究題目・提供者名に部分一致し、空白で区切った語はすべて含む
ものを探す。並びは最後に触れた順。

**不備の絞り込みは content から導出できる 3 つだけ** — hum ラベルが未 pin、未確定の値がある、未翻訳の
field がある。判定は純関数で、**draft があればその content を、無ければ最新公開版を見る** (直すのは
draft の側なので)。「上流の対応と食い違う」はキャッシュを要するので公開ゲートの側に置く。

## draft

**1 つの research に draft を複数持てる。** draft は未公開の作業コピーで、履歴ではない。

- **content** — 編集中の research content。共有リンクはここに紐づく
- **メモ** — draft 全体に対する自由文。admin だけが読み、preview には出ない。提供者に伝えたいことは
  コメントで書くので経路が分かれる
- **parent** — 派生元の ContentSnapshot への参照。公開時に「派生元が最新でない」を検出する。版ではなく
  スナップショットを指すのは、fix が版番号を変えないため
- **変更エントリ** — 触った dataset / experiment だけが実体を持つ (copy-on-write)。**派生元の published
  content も併せて持つ**ので、衝突の差分は 3-way になる
- **新規 dataset の identity** — 公開時に台帳へ載る。破棄すれば消える

draft ごとに変更エントリを持つのは、draft を複数許す決定から導かれる。共有の 1 行にすると、並行する
2 つの draft が同じ dataset を別内容で持てない。

**draft の保存には完全性の制約を置かない。** 未確定を抱えたまま保存して共有するのが標準の作業状態で、
検査は公開操作のときだけ行う。

**draft が作られる経路は 2 つ。** 新しい研究を作る (identity と空の content を同時に作る) か、既存の
research から作る (最新公開版の ContentSnapshot を parent にして content をコピーする)。公開版が 1 つも
無い research では空から始まり parent を持たない。

## 編集フォーム

**1 研究の版は 1 つのものなので、1 画面ぶんをまとめて保存する。** 翻訳対は左右 2 カラムで、状態は
ja / en が独立に持つ。

- **打ちかけの値は状態を変えても消えない。** 「未確定にする」を押した field の入力は画面に残り、
  **保存の時点で状態が値以外なら捨てられる**。押し間違いが入力の消失にならない
- **未翻訳は操作しない。** 両方の言語が値を持ち片方だけが空なら、自動でバッジが出る
- `datasetIds` はこの research の既存 dataset から選んで並べる。**他の research の dataset を並べる
  保存は拒む** — dataset は 1 つの research に従属するので、画面が出さないものは入力でもない

## 文の保存

文は markdown で入力し、**保存の時点で木に落とす**。落とせない記法は弾き、黙って消さない
([data-model.md](data-model.md) の「値と文」)。

- 弾くのは見出し・箇条書き・引用・コード・強調・打ち消し・表・水平線・画像・参照リンク・脚注・生 HTML。
  残るのは段落と行とインラインのリンクだけ
- **弾いたら保存全体を止める。** どの field のどの言語の何行目かを返し、フォームの入力はそのまま残る。
  **1 つ目で止めず全部を返す** — 1 回の編集を 2 往復にしないため
- **保存は書かれていないリンクを作らない。** 表を見分けるために GFM を有効にする必要があるが、GFM は
  裸の URL もリンクに変える。これを採ると URL を含む field を開いて何も変えずに保存しただけで content が
  変わるので、裸の URL は文字のまま残す。おかげで**一度保存を通った文は、編集画面に出して保存し直しても
  同じ木になる** — 衝突の差分にも版間の差分にも、誰も書いていない変更が出ない
- 移行の変換は逆に**畳む**。dump は自分を直せないが、人は直せる

## 同時編集

**排他しない。** 編集画面を開いている人を presence として表示するだけで、他者を read-only にしない。
正しさは保存時の楽観照合で担保する。

- **draft 配下の可変な行 (draft の content と dataset の変更エントリ) は整数の revision を持ち、更新は
  `WHERE id = ? AND revision = ?` の形で行う。影響行数が 0 なら 409**。experiment は変更エントリの
  content の中にあるので、その編集は属する dataset のエントリの revision で照合される
- **変更エントリの初回作成は「無ければ挿入」で行い、挿入されなければ 409**
- **複数行にまたがる保存は 1 トランザクションで全部照合し、1 つでも 0 行なら全体を rollback する**
- **revision に `xmin` を使わない。** VACUUM FREEZE で値が変わるので照合の基準にならない
- **書き込みを 1 つのモジュールに閉じ込め、既存の行を変える全関数が照合対象の revision を必須引数に取る。**
  DB のトリガでは守れない — 述語を忘れた更新も revision を増やせば通るので、防げるのは呼び出し側の形だけ。
  行を作る操作だけは照合の相手がいないので revision を取らない
- **409 では相手が変えた箇所を出し、手元の入力は捨てない。自動 reload はしない**
- **presence は (draft, セッション) を主キーにし、保持者と期限の列を最初から持つ。** 値は当面 NULL で、
  排他に上げる判断をしたときに列を足さずに済む形にしておく。期限切れは読み取り時に除外する

**衝突の差分は画面の側で取る。** 相手が変えた field は「この画面が開いたときの content」と「いまの
content」の比較で決まり、前者を持っているのは画面だけになる。server は現在の content を返すところまでを
受け持つ。取り込みは field 単位で、押した field だけが相手の値になる。

**破棄も revision を取る。** 元に戻せない操作なので、開いてから誰かが編集した draft は捨てさせない。

**答えの分け方が 3 つある。** payload が画面の送る形になっていなければ 400 (画面側の不具合で、人には
直せない)。文の記法が弾かれたら 422。revision が合わなければ 409。どれもフォームの中身は動かさない。

## draft の巻き戻し

draft ごとに undo を持つ。**目的は 409 で弾かれた入力を捨てないことで、履歴を残すことではない。**

- 記録するのは明示保存の直前状態と、409 で弾かれたフォームの内容
- 粒度は draft 全体。**深さの上限は 10。保持期間の上限は持たない**
- **スナップショットを行として積み、11 件目を入れるときに最古を消す。** 1 つの JSONB 値にまとめると、
  1 回の保存がスタック全体の書き換えになる
- draft と運命を共にする。破棄・公開すれば undo も消えるので、永続する履歴にはならない
- autosave は持たない。差分表示は 409 の画面と共用する

## 公開

**版を切るのは編集者の明示的な操作**で、内容の変化から自動判定しない。**公開版番号は公開時に確定する**
ので、公開しなかった draft に由来する欠番が生じない。

公開操作の入口で「版を切る」「fix として出す」を選ぶ。

**fix は版番号を増やさない。** 効果範囲が 2 種類に分かれるので、モデルとイベントも分ける (UI では 1 つの
操作に見せてよい)。

| fix の対象 | スコープ | 効果 |
|---|---|---|
| research content | その版 | 公開版が指す ContentSnapshot を差し替える |
| experiment / dataset content | identity | 参照している全公開版に効く |

後者が全公開版に効くのは「dataset は versioning しない」の帰結なので、**公開前の差分に「この dataset を
参照する公開版が N 件変わる」を必ず出す。** 同じ記述を複数の dataset に適用する一括編集も同様に
「N 件の dataset の experiment が変わる」を出す。

**fix で差し替える前の公開内容は、外部から参照可能にしない。** 内部にスナップショットが両方残るのは
research content の fix に限り、experiment / dataset content の訂正は現在の content を上書きする。

## 公開ゲート

検査は 2 種類に分かれる。

**公開を止める検査。** ラベルと関連の構造が揃っていないものは公開できない。

- research に hum ラベルが pin されている
- その版が持つ全 dataset に dataset id が pin されている

**列挙して通す検査。** 内容の未完成と上流との食い違いは公開を止めない。未解決を並べて admin が明示的に
通す形にし、**通した記録は証跡に残す。**

- 未確定 (unknown) とマークされた値
- 翻訳対 field の未翻訳
- content が空の dataset
- dataset が選択したファイルのうち非公開のもの
- hum ラベルと dataset id の対応が、JGA 申請管理システム由来のキャッシュと合わないもの

**状態は言語ごとに立つ**ので ([data-model.md](data-model.md) の「値の状態」)、未確定の列挙は
(field, 言語) の単位になる。未翻訳は「両方の言語が値を持ち、片方だけが空」のときだけ立ち、状態が
食い違うときは未確定として数える。**同じ 1 つの欠けが 2 行になることはない。**

**ファイルの列挙は「まとめて公開する」の入口を兼ねる。** ファイルの公開は research の公開とは独立した
操作で、切り替えは実バイトコピーの job になる。列挙されたものをその場でまとめて公開に倒せる形にし、
公開操作そのものは待たせない。

**上流との検算の対象は JGAD / JGAS に限る。** 申請管理システムが hum と JGAD / JGAS の対応の master
なので、そこに無い対応を pin しているのは疑わしい状態であり、不在も食い違いと同じく列挙する。上流には
typo や版違いでの食い違いの実績があるので、**上流を公開を止める側に置かない。**

## 取り下げと再公開

状態遷移は公開・取り下げ・再公開の 3 つで、取り下げと再公開は版番号 pin の公開状態の切り替えとして
表現する。専用の状態を増やさない。

**取り下げは UI 上は単に見えなくなる。** データは残るので復旧できる。

## 破棄と削除

| 操作 | データ | 外から見た挙動 |
|---|---|---|
| draft の破棄 | 関連ごと消える。draft が新規に作った dataset identity も消える | 元から見えていない |
| 版の取り下げ | 残る。pin も台帳に残る | 見えなくなる。再公開できる |
| research の削除 | 配下の dataset / experiment ごと消える。hum ラベルと dataset id の pin も外れる。event は残る | 見えなくなる。どちらのラベルも再 pin できる |

draft の破棄で消えるのは、draft 本体・変更エントリ・undo・コメント・共有リンク・その draft が新規に
追加した dataset の identity。既存の dataset に対する編集は変更エントリが消えるだけで、identity も pin も
動かない。

**dataset の pin を外した側は、その時点で公開版から外す。** 可視性判定は published content の有無で行い
pin を見ないので、外しただけだと id を失った dataset が既公開版の一覧に残り続ける。pin を外す操作の中で、
検索用の行と ContentSnapshot の dataset の列から同時に外す。

## レビュー

Google Docs 的な共有にする。**draft ごとに 1 本のリンクを持ち、リンクを知っている人全員が preview +
コメントできる。人ごとにリンクを発行しない。** 共有リンクの相手にはデータ提供者を含む。

- **共有状態は private とコメント可の 2 値。期限は既定で無期限。** トークンは draft に保持されるので、
  private に戻してから再度有効化しても同じリンクが使える
- **トークンの再発行を持つ。** 外に漏れたときに旧リンクを止める手段がこれしかない。private は
  「いまは見せない」、再発行は「このリンクはもう使わせない」で役割が違う
- **preview の応答に `X-Robots-Tag: noindex` と `Referrer-Policy: no-referrer` を付ける。** 未公開の
  content を無認証 URL で配る以上、クローラに拾われる経路と、外部リンクを踏んだときに Referer で
  トークンが漏れる経路を塞ぐ
- **トークンの検証は server 側のデータ取得経路に置く。** 画面のルートに掛けた guard は、同じデータを
  返す別経路が到達できるので担保にならない
- **preview は未確定値のスロットを残す。** 第一の用途が提供者への確認なので、公開画面と同じ姿を見せると
  いちばん聞きたいスロットが消える
- **preview と編集画面で、最新公開版と差がある箇所を highlight する**

**コメントはフィールド単位と値スロット単位で付ける。テキスト範囲は持たない。** コメントは対象の
フィールドへの参照を持ち、未確定値のスロットにも同じ経路で付く。**配列要素は identity を持つ** —
コメントの宛先の主戦場がここなので、順序で指すと並び替えで参照が壊れる。参照の書き方は編集フォームと
衝突の差分が使う path と同じもので、配列要素は位置ではなく identity で指す
(`dataProviders.{id}.name`)。

コメントはリンクを持つ人全員に見え、スレッドで返信でき、**手動で解決済みにできる**。

- **編集されたことを自動でコメントに反映する仕組みは持たない。** 未確定値の解消は「コメントの付いた
  箇所を編集する」操作そのものなので、自動で解決にすると確認の機会が消える
- 解決済みにしてもコメントは消えない。**共有リンクの期限が切れても残る。** 消えるのは draft を破棄した
  ときだけ
- **通知は無い。** メール送信基盤が無いので、admin が管理画面でコメントを見る

投稿者は、画面を開いた時点でサインインか自己申告の名前の入力を促す。サインイン済みなら Keycloak の
`preferred_username` を出して DDBJ アカウントの icon を付け、未サインインなら自己申告の名前を
**sessionStorage に置く** (共有端末で前の人の名前が残るのを避ける)。閲覧者は LGTM を押せる。承認権限では
なくレビュー済みの意思表示で、サインインしている場合にだけ本人性が伴う。

## 証跡

**公開・取り下げ・fix・削除・pin 操作・ファイルの公開状態の切り替え・admin の付け外しを append-only の
event として記録する。** pin 台帳が「いまどうなっているか」を持ち、event が「そこに至った操作」を持つ。
公開ゲートを通した記録もここに入る。ファイルを含めるのは、公開状態の master が S3 側にあって Postgres に
履歴が残らないため。draft の破棄も記録する — draft 本体は何も残さずに消えるので、消えたことを言えるのが
event だけになる。

- **event は subject に外部キーを張らない。** research を削除しても、そこに至った操作の記録は残る
- **append-only は DB のロールで担保する。** schema を作る owner と、アプリが繋ぐ role を分け、アプリ側に
  event への UPDATE と DELETE を与えない。アプリ側の規律にもトリガにも頼らない — トリガを迂回できる権限が
  あれば、トリガ自身の記録も直せる。**副産物としてアプリはどのテーブルも TRUNCATE できない**ので、DB を
  空にする経路は owner に閉じる
- **記録は変更と同じトランザクションで書く。** 何も変えなかった操作は何も記録しない
- **ログインは記録しない。** 記録するのは公開されているものを変えた操作で、主体は event ごとに焼かれる
- **DB への直接の SQL を緊急避難の経路として残すなら、その分は event に載らないことを前提にする**

## 意図的にやっていないこと

| やらないこと | 理由 |
|---|---|
| 承認ワークフロー / review status | レビューは状態ではなく活動。「review 中は編集できない」はレビューの本体 (コメントを受けて直す) を止める |
| 悲観ロック | 実測で救う対象が無く、逃げ道の無いロックを持つ実装も無い。正しさは保存時の照合に寄せる |
| autosave | undo の目的が「弾かれた入力を捨てない」ことなので、明示保存の直前だけを積めば足りる |
| 編集フォームを JS 無しで動かすこと | 状態の切り替え・配列の並べ替え・409 の取り込みがどれも画面の中の操作。読む側の画面は JS 無しでも動く |
| コメントのテキスト範囲アンカー | 第一のユースケース (値の無いスロット) に届かず、再アンカーの実装が重い |
| 提供者を認可主体にすること | 認可を capability ベースにし、上流 DB からの ownership 導出を無くす |
| admin 以外の役割 | 実績が無い。Joomla は 6 段の編集役割を持ちながら 3 つが在籍 0 人だった |
| Keycloak の role で権限を表すこと | realm が他組織の所管で、付与が依頼になり交代に即応できない |
| session に access / refresh token を持つこと | 送る先が無い。public API に認証が無く、resource server も無い |
| 通知 | メール送信基盤が無い |
