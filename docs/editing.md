# 編集

編集は admin が draft に対して行う。データ提供者やレビュアは共有リンクから preview とコメントだけが
できる。draft を版にする側は [publishing.md](publishing.md)。

誰がサインインでき何を許されるかは [auth.md](auth.md)、モデルの側の不変条件は
[data-model.md](data-model.md) にある。ここは操作とその制約。

## 管理画面

23 画面ある。**識別子を要らないのは入口を含めて 9 つで、残る 14 は研究・下書き・記事・項目を 1 つ
選んだ先にある。**

| アドレス | 何の画面か |

| `/admin/research` | 研究の一覧 |
| `/admin/research/upstream` | データ提供申請の枝番を探す (下の「下書きを外から作る」) |
| `/admin/research/upstream/:applicationId` | 枝番 1 本の内容。研究がポータルに無ければ、ここから研究を作る |

| `…/draft/:draftId` | draft の research content を書く |

| `/admin/files` | `common/` の箱 (記事が貼る画像と PDF) |

**管理画面は日本語だけで、言語の prefix を持たない。** `/en/admin/…` は存在しない — ポータルを運用する
人たちのための画面で、英語版を置いても同じ画面が 2 つのアドレスで同じ語を答えるだけになる。ヘッダの
言語の切り替えもここでは出さず、英語の公開ページからこの区画へ入ると日本語の画面に着く。**画面が
日本語なのであって、扱う値は 2 言語のまま** — 記事とお知らせの本文、語彙のラベル、申請の題目はどれも
ja と en を持ち、この区画はその両方を編集する場所であり続ける。

**行き先の規則は [admin-ui.md](admin-ui.md) の「区画の枠」**にある。要点は 2 つ — **足す先は
`app/admin/navigation.ts` の 1 箇所**で、そこに載せた画面がバーと `/admin` の作業の一覧の両方に
出る。そして**一覧から開く画面はどれも、その一覧へ戻る道を 1 本持つ** — 親がバーに並んでいても持つ。

**research も dataset も identity で指す。** ラベルはまだ pin されていないことがあり、pin は訂正も
されるので、管理画面のアドレスをラベルに寄せると開けない研究と動くアドレスが生まれる。

**一覧の窓は直引きで、公開検索ではない。** 全文索引は公開分しか持たないのに、この一覧の主役は未公開の
方にある。窓は hum ラベル・dataset id・研究題目・提供者名に部分一致し、空白で区切った語はすべて含む
ものを探す。

**見せ方は公開側の一覧に揃える。** 条件は左のペインに立って畳め、**窓も公開側と同じもので、打ち
終わった時点で絞り込む。チェックも変えた時点で効き、確定させるボタンは持たない** — 押して初めて効く
形にすると、ペインの言うことと並んでいる行が食い違ったまま画面に残る。**ペインを持つかどうかは一覧
ごとに違うが、並び替え・表示件数・ページ送りの持ち方は揃える** ([ui.md](ui.md) の「行が並ぶ画面」)。
ページに切る一覧 — 研究・データ提供申請の枝番・記事・お知らせ・`common/` の箱・研究の箱・解析手法の語・
データセットを足す画面の枝番 — はどれも表示件数 (20 / 50 / 100) を持ち、記事を除いて並び替えも持つ
(研究は公開側と同じ更新日 / 公開日 / 研究 ID で、既定は更新日の新しい順)。解析手法の表はページに切らず、
どちらも持たない。**選んだものはどれもアドレスに載る。**

**並びそのものが意味を持つ一覧は、並び替えを持たない。** 解析手法の表は並びが公開ページの表の並びで
(下の「解析手法の表」)、記事の一覧は slug 順に並ぶことで木になる — `guidelines` の次の行が
`guidelines/data-sharing-guidelines` だから段を下げて描けるのであって、題名順に替えると 1 段下がった行が
親から離れ、段下げが手がかりでなくなる。**どちらも並びは選ぶものではなく、読むもの。**
**キーの値を持たない行は、順をどちら向きにしても末尾に沈む** — 未 pin のラベルや一度も公開していない
研究は日付やラベルの尺度に居場所がなく、空として扱うと順を返すたびに一覧を端から端へ移動する。

**絞り込みの値には件数を出し、数え方も公開側と同じにする — その軸の条件だけ外した集合で数える**
([public-pages.md](public-pages.md) の「絞り込み」)。全条件で数えると、1 つ選んだ瞬間に同じ軸の他の
値が 0 になり、選び直す道が画面から読めなくなる。他の軸と窓は効いたままなので、数字は「いま押したら
何件になるか」を指す。**ただし 0 件の値を消さない** — 公開側の facet は値がデータ由来で数千あるのに
対し、管理画面の軸は 2〜5 個の決まった値なので、0 件を落とすと軸そのものが画面から消える。
**この規則は管理画面の 5 つの一覧すべてに当てはまる** (研究・データ提供申請の枝番・記事・お知らせ・
解析手法の表)。

**解析手法の表は並びそのものを編集する一覧**なので、ページに切らず、並び替えも持たない。表の順は公開
ページの表の順で、**行を掴んで置くか、1 つずつ上げ下げして決める** — ページに切ると、動かした行の行き先が
画面の外に出る。**置くたびに保存する** (1 回の移動が 1 回の書き込み) ので、並べ替えの途中で画面を離れても
そこまでは残る。**答えの帯は何をどこへ動かしたかを言い、「元に戻す」で直前の 1 手を逆に打てる** — 戻した手も
また 1 手なので、その帯にも「元に戻す」が付く。履歴は持たない (draft の巻き戻しとは別の話。下の「意図的に
やっていないこと」)。掴み手はキーボードでも使え (Space でつかみ、矢印で動かし、Space で置く。読み上げはつかんだ
行と行き先の番号を言う)、**狭い画面では掴み手を出さず上げ下げだけ**になる — 触ってスクロールする画面で
掴めると、送るつもりの指が行を動かす ([ui.md](ui.md) の「押せるもの」)。**絞り込んでいる間は掴み手も上げ
下げも出さない** — 「1 つ上」は全体の中の 1 つ上であって、絞り込んだ表の中の隣ではないため。窓はコードと
2 つのラベルに当たる。**行を直す操作は表の中に開かない** — 一度に決めるものを行の隣に畳んで置くと、押した
行だけが他の行と高さの違う塊になる。

**選べる値の画面も同じ形で読む** — 表・行の右端で開く面・左のペインという組みは 2 つの画面で 1 つで、
一段降りたところで操作の探し方が変わらない。**違うのは 3 つだけ**。語は並びが意味を持たないので
並び替え・表示件数・ページを持ち (上の「管理画面」)、ペインは窓だけで軸を持たず、そして**使われている語は
消せない** — 公開済みか下書きの値がその語を指したままなので、消すと読めない値が残る。**削除の入口は行に
常に立ち、使われている語では押せない** — 理由は入口の hover が言う ([ui.md](ui.md) の「押せるもの」)。key の
削除も同じで、公開版か下書きに値のある key は押せない。**「使用件数」の列は、その語を持つ公開データセットの
数で、押すと公開側の一覧をその語で絞って開く** — 研究の検索行も同じ語を持つが数えない (開いた先の件数と
合わなくなる)。下書きも数えないので、0 件でも下書きが指していれば消せない。key の表も同じ列を持ち、その key に
値を書いている公開データセットを数える (こちらは押せない — 公開側の検索式に「その key に値がある」を絞る形が無い)。

**使われている語を畳むのは併合で、行の操作として持つ** ([data-model.md](data-model.md) の
「catalog と語彙」)。**行き先を選ばせる面が要る**ので、名前を直す面とは別の入口になる。**行き先に選べるのは
同じ語彙の中だけ**で、面は語彙が数百あっても選べるように窓を持つ。**押したら戻せない**ので、確認を挟んで、いくつの
値が書き換わるかを数えて見せる。

**ICD10 だけは辞書から引いて足す欄を表の下に持つ** — 語の綴りを人が考えないための入口で
([data-model.md](data-model.md) の「ICD10」)、他の語彙には無い。

**不備の絞り込みは、一覧の行を組むときに引ける 5 つ** — hum ラベルが未 pin、dataset id が未 pin、
未確定の値がある、未翻訳の field がある、データ提供申請と食い違う。pin の 2 つは台帳、食い違いは
hum ↔ accession のキャッシュ、残りは content の純関数判定で、**draft があればその content を、無ければ
最新公開版を見る** (直すのは draft の側なので)。境界は「content から導出できるか」ではなく「行を組む
ときに引ける範囲か」で、**述語は公開ゲートと同じものを共有する** ([publishing.md](publishing.md)) —
公開を止めるものを一覧が出さないと、curator は確認画面まで行かないと直す対象を知れない。

**5 つは OR で、status とだけ AND になる。** 3 つ選ぶのは「見るべき行を集める」ことであって、3 つ全部に
当てはまる珍しい行を探すことではない。**status も同じ形で、公開中と未公開のどちらも選べて OR。
何も選ばなければ全部**。言うのは公開中の版があるかどうかだけで、版を全部引っ込めた research は、
一度も公開していないものと同じく何も読めないので、そこに third state を作らない
(どの版が取り下げられているかは研究 1 件の画面が持つ)。

**公開状態を言う語は 1 組に揃える — 「公開中」と「未公開」** (en は `Published` と `Not published`)。
研究の版・記事・お知らせ・データセット・ファイルはどれも「いま読者から見えるか」を言っているので、
対象ごとに語を変えると同じことを画面ごとに読み直すことになる。**「公開済み」と「非公開」は使わない** —
前者は完了を言うので取り下げたものを指せず、後者は bucket の名前 ([files.md](files.md)) と混ざる。
**操作の動詞は対象ごとに違ってよいが、状態の語と噛み合わせる** — 「公開する」と「公開をやめる」で、
「非公開にする」とは書かない。

**外部データの取り込みの状態は `/admin` に出す。** ソースごとに最終成功の日・取り込んだ件数・直近の
失敗理由を並べ、`view-unpublished` を持つ人にだけ見せる。キャッシュは取得に失敗しても前回値が残るので
([data-model.md](data-model.md) の「外部キャッシュ」)、**画面に出さないと「更新が止まっている」が
誰にも見えない**。画面から取得を走らせることはできない — 走らせるのはプロセスと CLI
([development.md](development.md))。

**「上流」は画面に出さない。** doc とコードでは外部 master をそう呼ぶが、curator が読むのは申請管理
システム由来なら**データ提供申請**、DDBJ Search 由来なら**外部アクセッション**。`/admin` の節も
「外部データの取り込み」で、**表の行が名乗るのは取り込むもの** — 取得元は 2 つしかなく、止まって
いるものを探す人が見たいのは、どの値が古いか。

## draft

**1 つの research に draft を複数持てる。** draft は未公開の作業コピーで、履歴ではない。

- **content** — 編集中の research content。共有リンクはここに紐づく
- **メモ** — draft 全体に宛てた、admin だけが読み書きする平らな流れ。preview には出ず、解決を持たず、未解決の
  件数にも数えない。「この draft を何のために作ったか」「提供者に電話した」を残す場所で、提供者に伝えたいことは
  全体へのコメントかフィールドのコメントに書くので、経路が分かれる (下の「レビュー」)
- **dataset のエントリ** — 載せている dataset のぶんだけ持つ。保存と照合の単位で、experiment はこの
  中にいる。**draft はコピー元を覚えない** — 誰の派生かを持たないので、比べる相手はその都度選ぶ
  (「他の版や draft と比べる」)
- **新規 dataset の identity** — draft と運命を共にする。破棄すれば pin ごと消える
- **更新する版** — 版の行の「編集」で作った draft だけが持つ (下)。番号ではなく版そのものを指す

draft ごとにエントリを持つのは、draft を複数許す決定から導かれる。共有の 1 行にすると、並行する
2 つの draft が同じ dataset を別内容で持てない。

**draft の保存には完全性の制約を置かない。** 未確定を抱えたまま保存して共有するのが標準の作業状態で、
検査は公開操作のときだけ行う。

**下書きの面は 4 つ — 研究の内容、データセット、レビューと共有、公開の確認。** 画面もその 4 つで
(上の表の `…/draft/:draftId` とその下の `dataset` / `review` / `publish`)、**入口は研究の画面 (「研究の
編集」) が持つ。** 「バージョンと下書き」の表の下書きの行が、状態・更新日時・データセットの件数・レビュー
(共有中か、未解決のコメントの数。メモは数えない)・不備 (公開ゲートが止めるものと確認を求めるものの数) を
列に持ち、**その事実がそのままその面への道になる** — 「3 件」を押せばデータセットの画面に、「未解決 4」を
押せばレビューと共有の画面に着く。行の操作は編集 (研究の内容へ)・公開・削除。研究の内容の画面の頭の区画も
同じ事実と道を持つ ([admin-ui.md](admin-ui.md) の「編集画面」) — 書いている最中に他の面へ移るのが、研究の
画面へ戻ってからでは 2 手になるため。**段の列 (stepper) もタブも持たない** — 4 つは仕事の順に並んでは
いるが、どの面にも戻れ、レビューは飛ばせ、公開の面が足りないものを列挙する。番号を振った列は仕事の順を
答えて事実を添え書きにし、どの画面の頭でもパンくずに見えた。**公開ゲートは公開の確認画面だけでなく、研究の
画面と下書きのどの画面でも同じ述語で数える** ([publishing.md](publishing.md) の「公開ゲート」)。

**draft に値が入る道は「取り込む」の 1 つ。** 源の値を編集中の値として form に入れ、保存で draft に入る。
源は 3 つ — 版 (下の「他の版や draft と比べる」)、データ提供申請の枝番、accession 1 件 (下の「下書きを
外から作る」)。**版のコピーも、申請から研究を作るのも、公開版の編集も、「空の draft を作って取り込む」の
ショートハンド**で、経路が増えているのではない (公開版の編集だけは、作った draft が更新する版を指す)。研究そのものが無いときだけ「research と空の draft を作る」が
頭に付く。

**draft は研究の画面で作る。** 空の draft を作るか、版の行の「このバージョンから下書きの作成」で作る。**研究一覧の
「研究の作成」も研究の画面に着く** — research と空の draft を一度に作るが、作ったのは研究で、次に押すものは
下書きの行の 1 つしか無い。下書きの編集に直に着くと、研究ができたことは戻る道を押すまで見えない。申請から
作る新規だけは値の入った draft に着く (下の「下書きを外から作る」— 次にすることが、入った値を確かめること
だから)。**draft はどの版から来たかを覚えない** — 下書きは下書きで、版の番号を持つのは版だけ。公開ページへ直に書く経路は
持たない — 上流の値は語彙に当たらないことがあり、疾患は呼称が入らず、未翻訳の検査も要る。**番号は公開で
だけ決める** — 空いている番号を公開の確認画面で打ち、draft を作る入口でも取り込みの入口でも聞かない
([publishing.md](publishing.md))。**取り下げも draft を作る** — 版から番号を外してそのまま draft にする
操作で、コピーではなく行の移動になる。

**版の行の「編集」は、更新の draft を裏で作って開く。** 版はそのまま公開されていて、直しているあいだも
公開ページは元の姿を返す。**更新は版の状態で、draft は器** — 研究の画面はこの draft を下書きの行として
出さず、版の行が「更新中」と言い、共有と不備の欄にその draft の状態を出す。続きを開くのも「編集」、やめる
(draft を破棄する) のも「更新をやめる」で、どちらも版の行の操作。版 1 つに 1 つで、更新中の版は取り下げ
られない (先に更新をやめる)。編集画面は普通の draft と同じで、識別子の隣に「vN を更新中」の印を持ち、
保存は draft しか動かさない。**出口が違う** — 「公開」の代わりに「vN を更新する」が公開の確認画面へ導き、
そこでは番号を聞かず、通すと同じ番号の版が入れ替わる ([publishing.md](publishing.md) の「版番号」)。
比べる相手も差の印も、最新の版ではなく更新する版になる (下の「他の版や draft と比べる」)。

**公開は draft を消費する。** 版として出たものが draft としても残ると、同じ内容が 2 か所にあって
どちらが正かを言えなくなる。続きを書くときは最新の公開版から新しい draft を作る。

## 下書きを外から作る

研究の記述は申請書に既に書かれていて、dataset の identity は上流が発行している。**上流から引いた値で
埋めた content で draft を作る経路**を持ち、手で打ち直すところから始めない。

| 入力 | 出所 | 何ができるか |
|---|---|---|
| J-DS の承認枝番 | 申請管理システム DB | research content と、今回登録された JGAD の dataset |
| JGAD | 申請管理システム DB | dataset 1 件 (既存の draft に足す) |
| DRA の submission | DDBJ Search | dataset 1 件 (既存の draft に足す) |

**入力の単位は J-DS の枝番。** 枝番 1 本が登録 1 回 (JGAS 1 + JGAD n) に対応し、hum ラベルが付くのも
承認枝番になる。案件 (`J-DS`) は申請の窓口の単位で、1 hum が複数の案件にまたがることも 1 案件に複数の
hum が入ることもあるので、案件では「今回登録された分」が切れない。

**枝番を探す画面は、研究一覧と同じ見せ方にする** (上の「管理画面」)。条件は左のペインに立って畳め、
並び替え (承認日 / 申請番号) と表示件数はアドレスに載り、該当した枝番はすべて数えてページで送る。
**窓が当たるのは申請管理システムの側**で、hum ラベル・申請番号・研究課題名・研究代表者名 — 行が出している
値と同じものに部分一致する。**絞り込みの 2 軸はポータル側の答えで、上流は知らない**: 枝番の hum ラベルを
ポータルが持っているか (持っている / 無い / hum ラベル自体が未発行) と、データセットが登録されているか。
**一覧が出すのは JGAD だけで、JGAS は出さない** — JGAS だけを登録した枝番は無く、ポータルは JGAS から
何も作らない。
したがって**ページを切るのはポータル側**になり、該当した枝番は毎回すべて読む。上流の問い合わせは承認
枝番を全件組んでから切っているので、30 件でも全件でも値段は変わらない。

**上流のキャッシュを経由しない。** hum ↔ accession のキャッシュも accession の日付も公開済みしか
持たないが ([data-model.md](data-model.md) の「外部キャッシュ」)、下書きを作るのはこれから公開する
研究に対してなので、そこには届かない。JGAD の題目と種類も同じ理由で申請管理システム DB の登録 XML から
読む。**XML の取り出しは Postgres の `xpath()` で行い、アプリは parser を持たない。**

**`relation` を読まない。** index が無く 2,446 万行の seq scan になるので、要求のたびには叩けない。
枝番から accession へは登録単位の id と `accession.alias` が持つ JSUB 番号で辿る。同じ理由で JGAD から
JGAX (experiment) へは降りず、assay は JGAD 自身の `DATASET_TYPE` から取る — 1 JGAD あたり JGAX は
平均 381・最大 111,974 あり、全部の XML を読む形は成立しない。

### 何が入るか

**research content に入るのは、そのまま公開ページに出る値だけ。** 申請書は氏名・メール・電話・住所・
所属長・研究分担者を持つが、下書きに移すのは題目・研究目的・実験方法・対象者と、PI の氏名・所属に限る。キャッシュに引いた線 ([data-model.md](data-model.md) の「外部キャッシュ」) を content への
流し込みにも同じく適用する — content は連絡先 (メールアドレス・ORCID) を
持たないので、申請書の連絡先が外に出る経路はそもそも無い。

**dataset は 1 accession = 1 件で、experiment を 1 件持つ。** JGAD は `DATASET_TYPE` を label にした
1 件、DRA は library strategy ごとに 1 件。**DRX 1 本を 1 experiment にはしない** — DRA の submission は
DRX を数十から数百持つのに対し、ここでいう experiment は記事の分子データテーブル 1 枚の単位になる。
外部アーカイブの dataset なので日付は入らない — 上流の値がそのまま出るため ([data-model.md](data-model.md) の
「日付」)。

- **片方の言語しか無いときは、もう片方を空のままにする。** 両方が値を持ち片方だけが空であることが
  未翻訳の定義なので、公開ゲートがそれを列挙する。**`unknown` は立てない** — curator が明示的に立てた
  印なので、上流が黙っているだけの field をそれにすると意味が変わる
- **語彙は code で引き当て、当たらなければ英語ラベルで引き当てる (大小文字は問わない)。** 上流の綴りは
  catalog の語彙と揃っていない (INSDC の `WXS` に対して catalog は `WES`) が、機器名のように綴りが
  そのままラベルになっているものは当たる。**当たらなかった値は下書きを作る前に画面が列挙する**ので、
  その項目の語の画面で語を足してから取り直せる。**この経路が語彙値を作ることはない**
- **疾患は申請書の ICD10 欄から入れる。**欄は自由記述で、範囲・点付き・存在しないコードが混ざるので、
  移行と同じ正規化を通してから引き当てる ([data-model.md](data-model.md) の「ICD10」)。**下書きが作る
  のはコードだけで、呼称は curator が書く** — 申請書は疾患の名前を持たない。正規化で落ちたコードは
  当たらなかった語彙値と同じく列挙する
- **dataset のラベルは作ると同時に pin する。** pin しないと dataset が identity のまま並んで見分け
  られない。したがってこの操作は `edit-content` と `manage-labels` の両方を要求する
- **hum ラベルは上流が持っているときだけ pin する。** 承認が先でラベルが後になる枝番があり、未 pin の
  まま作った research は一覧の不備に並ぶので、後から pin する道はそこにある。**hum ↔ J-DS の master は
  申請管理システムで、ポータルからそこには書けない** — ポータルで pin しても上流の枝番が hum を持たない
  ままになるので、枝番の画面が上流にも書くよう促す

### 行き先

**枝番の値が入る先は、研究の画面に並ぶ下書きの 1 つ。** 枝番 1 本の画面 (「データ提供申請の内容」) は
読む画面で、状態を 2 つしか持たない:

| 枝番の hum の研究がポータルに | 画面が出すもの | 押すと |
|---|---|---|
| 無い | 申請の内容・研究に入る値・登録されたデータセットと、「研究の作成」 | 申請の値で埋めた research と draft と dataset を一度に作り、その draft の研究の内容に着く |
| ある | 同じ内容と、その研究の画面への道 | 取り込みはその研究の下書きの側から始める |

**行き先をこの画面で選ばせない。** 下書きが 6 つある研究では「下書きに入れる」が同じ字面で 6 行並び、
選んだ先で何が起きるかを読めない。取り込みは下書きを保存してから 3 段の面で確定するもの (下) なので、
入口は下書きの側にある。

**新規だけはこの画面で作る。** 突き合わせる相手が無く、画面が既に何が入るかを出しているので、research と
draft と dataset を 1 つの操作で作る。**その hum の研究がポータルに無いときだけ**で、台帳の一意性が pin を
弾くので、作った後に気づく形にしない。**版が上がるたびに承認枝番は増える**ので (hum0444 の `-003` と
`-004`、hum0290 の `-008` と `-009`)、2 本目以降が主になる。

**既にある研究への取り込みは、研究の内容の編集画面の頭の区画と、データセットの画面から
「データ提供申請の取り込み」へ入る** (`…/draft/:draftId/upstream`)。その画面は**この研究の hum を持つ
枝番を承認日の新しい順に並べ**、取り込み済みの枝番には印を付ける。1 つ選ぶと同じ画面が取り込みの面 (下)
になり、面の戻る道は枝番の表に戻る。**申請 ID を打つ窓を 1 つ持つ** — 承認が先でラベルが後になる枝番は
hum で引けないので、番号で指す道がここにしか無い。**研究 ID が枝番と下書きの研究で違っても止めない** —
違うことを画面が言うに留める。

**データ提供申請の一覧から下書きへ入れる道は持たない。** 一覧に下書きを覚えさせると、絞り込み・並び替え・
ページ送りのどれかで落ち、同じ枝番が「行き先を選ぶ姿」と「この下書きに入れる姿」の 2 通りで出る。一覧は
枝番を探して読む場所で、入れる先はいつも下書きの側が言う。

**データセットを足す画面は申請を選ぶ窓を持たない。** 枝番を探す画面が 2 つあると、片方だけが数え・絞り・
ページを持ち、同じ枝番が 2 通りの姿で出る。あの画面に残るのは accession (JGAD / DRA) を 1 件打つ窓だけで、
申請からは上の道で取り込む。

**版に入れるのも draft を通る。** 版を選ぶことは、その版のコピーの draft に入れることで (上の「draft」)、
公開ページへ直に書く経路は持たない。どの番号で出るかは公開でだけ決める。

**同じ枝番を何度でも取り込める。** 承認の時点では JGAD がまだ無い枝番が多く、登録は後から付く。1 回目は
content、2 回目は dataset という形で同じ枝番に戻ってくるので、取り込み済みを理由に止めない。**draft は
取り込んだ枝番を並べて持つ** — 承認は 1 件ずつ来るのに対し draft は長く開いたままになるので、1 つの版に
複数の枝番が入る。記録であって制約ではなく、枝番の表の印にだけ使う。

### 取り込みの面

**面は 3 段。** 項目ごとに「いまの下書きの値」と「データ提供申請の値」を読むだけの 2 列で並べ、その下に
書ける欄を 1 つ置く。**欄の初期値は申請の値、無ければ下書きの値、どちらも無ければ未確定。**「申請を採る」
のような選択の操作は持たない — **どちらでもない第 3 の値を書くことがある**ので、選ばせる形にすると書く
場所が無くなる。**同じ値の項目は畳む** — 版を上げるときに変わるのは数項目で、16 欄すべてを 3 段で出すと
差分が埋もれる。

**確定は保存。取り込みへ入る前に下書きを保存させる。** content を書く操作なので通常の保存に乗り、
照合がそのまま効く。書きかけを抱えたまま入ると、面が「いまの下書きの値」として読ませているものが保存済み
の値と食い違う。

**dataset は同じ確定に含める。** 今回登録された JGAD を一緒に足す。既にこの下書きにある dataset は畳んで
数だけ出す — 触らないものなので。content と別の操作にすると、版を上げるたびに同じ申請を 2 回選ぶことに
なる。

**面は編集画面と分ける** (`…/draft/:draftId/upstream`)。編集画面は 2 ペインで幅が無く、3 段を横に並べると
入らない。下書きの中の画面にすればデータセットの取り込みと同じ形になる。**同じ画面が枝番を選ぶ表も持つ**
(上の「行き先」) — 選ぶ前は表、選んだ後は面で、面の戻る道は表に戻る。

### 引くとき

- **確認画面と作成で 2 回引く。** 画面が送るのは何を作るかの選択だけで、値は server が引き直す。上流は
  日単位でしか動かないので、見た値を hidden field で運ぶ必要が無い
- **部分的に取れなかったものは列挙した上で作らせる。** 下書きは破棄できるので、止める側に倒す理由が
  無い。入力そのものが取れないときだけ作れない
- **申請管理システム DB への接続を持たない環境では、画面がそう言う。** 入口は消さない。本番以外から
  この DB には届かないので ([development.md](development.md))、設定が無いことを異常にしない。DRA は
  DDBJ Search なので同じ環境でも動く

## 保存の単位

**research と dataset は別々に保存する。** research の版は 1 つのものなので 1 画面ぶんをまとめて送るが、
dataset はそれぞれが identity を持ち、公開後は参照している全公開版に効く別の実体になる。1 研究が
200 を超える dataset を持つことがあり、1 つの衝突が残り全部の衝突になるのも正しくない。

したがって draft の下に可変な行は 2 種あり、**それぞれが自分の revision で照合される**。

| 保存するもの | 単位 | 照合する revision |
|---|---|---|
| research content | draft 1 つ | draft の revision |
| dataset content (experiment を含む) | エントリ 1 行 | そのエントリの revision |

**experiment は自分の revision を持たない。** dataset content の中の順序つきの要素なので、その編集は
属する dataset のエントリの照合で守られる。

## フォームの隣に立つ公開ページ

編集画面はフォームと公開ページを並べて見せる。守らないと壊れるものが 3 つある。

- **場所を指す語彙は path 1 本きり。** コメントの宛先も衝突の差分もページの印も同じ綴りで書かれて
  いるので (`app/admin/paths.ts`)、**編集画面のための対応表を別に作らない**
- **ページを描く経路を増やさない。** 並ぶページは公開ページでも共有リンクのプレビューでもなく、
  同じ純関数の出力を受け取る 3 つ目の読み手で、未確定値を残す引数はプレビューと同じ側を取る
- **空の欄も場所を持つ。落とすのは値であって欄ではない。** 公開表現は未確定を空にするだけで欄を
  消さないので、ラベルは値が無くても立っている。**下書きを埋める作業は空の欄を埋める作業**なので、
  ここが崩れると編集画面はいちばん要るときに指す先を失う。**塗りと押せることは編集の側だけ** —
  ページも共有リンクのプレビューも `annotate` を渡さないので、同じ場所に何も描かれない

**焦点の入った項目は、ページ側でその値のブロックが塗られて窓の中央に寄り、ページの値のブロックを押すと
その欄へ移る。** 押せる印を別に置かない。

**公開ページに出さない値を content に持たない。** 提供者の ORCID・メールアドレス・所在地がそれで、公開
ページに出さない値を content に置いても、埋める人の手間と外へ漏れる経路が増えるだけになる。したがって
フォームの欄はどれもページか一覧の行に対応する場所を持つ。

**短い要約は研究のページではなく一覧の行に出るので、ペインは一覧の行も持てる** (タブ「研究一覧の行」)。
フォームの節も同じ「研究一覧の行」と名乗って末尾に立つ。
ja と en の行を 1 つのタブに上下に置き、それぞれその言語の列見出しで読ませる — 行は短く、2 つは
突き合わせて読むものだから。**行も公開の一覧と同じ純関数 (`researchListRowView`) と同じ部品で描く**
(上の「ページを描く経路を増やさない」)。違うのは 3 つ — 公開の一覧が検索の行から読むアクセス種別と
プラットフォームは下書きのデータセットの content から読む、研究とデータセットの ID は押せず、カートの列を
持たない (下書きには開く先のページも、カートに入れる公開のデータセットも無い)、日付の 2 列は公開で決まる
ので空になる。**行には押せる印を付けない。**

## 編集フォーム

翻訳対は ja / en を上下に置き、状態は ja / en が独立に持つ。

- **節の名前と順はページの見出しそのもの。** 1 つの欄しか持たない節は見出しだけで、同じ語の欄の名前を
  重ねない。欄の名前が要るのは、ページがその節の中に小見出しを持つときだけ
- **状態は言語ごとに 2 つの印 (未確定 / 該当なし) で、どちらも押していなければ値** ([admin-ui.md](admin-ui.md) の
  「欄の状態」)

- **打ちかけの値は状態を変えても消えない。** 「未確定にする」を押した field の入力は画面に残り、
  **保存の時点で状態が値以外なら捨てられる**。押し間違いが入力の消失にならない
- **未翻訳は操作しない。** 両方の言語が値を持ち片方だけが空なら、自動でバッジが出る
- **版が載せる dataset とその順 (`datasetIds`) は、draft のデータセットの画面で決める。** フォームは
  持たない — dataset のことはその 1 画面に閉じ、載せる・外す・順を変えるは draft の revision で照合する。
  **他の research の dataset を並べる保存は拒む** — dataset は 1 つの research に従属するので、画面が
  出さないものは入力でもない

**dataset の値は catalog のキーの下にあり、持っているキーだけが画面に出る。** スロットが無いことは
「値が空」とは別のことで、その項目を持たないという意味になる。項目を足すのは catalog から選ぶことで、
**その場で新しいキーを作る経路は持たない** — キーの揺れは、打った文字列がそのまま catalog に載ることで
生まれてきた。

**入力の形はキーの型が決める。** 入力できるのは翻訳対の文 (`text`)・語彙の選択 (`vocabulary`)・数値
(`number`)・疾患 (`disease`) の 4 つで、catalog に実在するのもこの 4 つだけ。**他の型が現れたら
例外にする** — 画面に出せない値を黙って落とすと、開いて保存しただけで消える。

- **語彙は、選んだ値を並べて残りは窓で探す。** 語彙が 3 語でも 1 万語でも同じ形にする。一覧にすると
  ICD10 のような語彙で操作できる画面にならず、件数で形を変えると語彙が育った日に画面が変わる。
  **候補を出すのは server で、窓に打った文字を送って返ってきたものを出す** — 語彙を丸ごと画面へ
  送る形にすると、送る量が語彙の大きさに比例し、「3 語でも 1 万語でも同じ形」が画面の中だけの話に
  なる。**選んでいる値のラベルは別に解決する**ので、窓を 1 度も使わなくても選択は読める
- **疾患は 1 行が「識別子の選択 + 呼称の ja/en」で、行を並べて持つ。**識別子を選ばない行が正しい
  入力になる — 分類に載っていない疾患があるため。**コードは打っても選んでもよく、打った場合は
  正規化を通す** (点の有無と大小文字は問わない)。**辞書に無いコードは弾いて、削った先の候補を出す** —
  `K75.81` は ICD-10-CM なので `K758` を勧める。**呼称は候補を出さない**。記事に書かれた名前を
  そのまま入れる欄で、寄せる先を持たない ([data-model.md](data-model.md) の「ICD10」)
- **数値は値と単位で入力し、保存の時点でキーの正準単位へ換算する** ([data-model.md](data-model.md) の
  「catalog と語彙」)。**入力した値と単位はそのまま残す** ので、換算を後から直せる。キーが admit しない
  単位を送る保存は 400 — フォームが出さない入力だから
- **空の数値欄はスロットごと保存しない。** 文には「値ありで中身が空」があるが、数値にそれは無い。
  聞いている最中なら未確定、存在しないなら該当なしで、どちらも状態として持つ

## 文の保存

文は markdown で入力し、**保存の時点で木に落とす**。落とせない記法は弾き、黙って消さない
([data-model.md](data-model.md) の「値と文」)。

- 弾くのは見出し・箇条書き・引用・コード・強調・打ち消し・表・水平線・画像・参照リンク・脚注・生 HTML。
  残るのは段落と行とインラインのリンクだけ
- **弾いたら保存全体を止める。** どの field のどの言語の何行目かを返し、フォームの入力はそのまま残る。
  **1 つ目で止めず全部を返し、画面が並べる順に返す** — 1 回の編集を 2 往復にしないため
- **保存は書かれていないリンクを作らない。** 表を見分けるために GFM を有効にする必要があるが、GFM は
  裸の URL もリンクに変える。これを採ると URL を含む field を開いて何も変えずに保存しただけで content が
  変わるので、裸の URL は文字のまま残す。おかげで**一度保存を通った文は、編集画面に出して保存し直しても
  同じ木になる** — 衝突の差分にも版間の差分にも、誰も書いていない変更が出ない
- 移行の変換は逆に**畳む**。dump は自分を直せないが、人は直せる

## 同時編集

**排他しない。** 編集画面を開いている人を presence として表示するだけで、他者を read-only にしない。
正しさは保存時の楽観照合で担保する。

- **更新は `WHERE id = ? AND revision = ?` の形で行い、影響行数が 0 なら 409**
- **エントリの初回作成は「無ければ挿入」で行い、挿入されなければ 409。** 画面が持つ revision が
  「まだ無い」であることが、挿入と更新を分ける唯一の印になる
- **複数行にまたがる保存は 1 トランザクションで全部照合し、1 つでも 0 行なら全体を rollback する**
- **revision に `xmin` を使わない。** VACUUM FREEZE で値が変わるので照合の基準にならない
- **draft への書き込みを 1 つのモジュールに閉じ込め、既存の行を変える全関数が照合対象の revision を
  必須引数に取る。** DB のトリガでは守れない — 述語を忘れた更新も revision を増やせば通るので、防げるのは
  呼び出し側の形だけ。行を作る操作だけは照合の相手がいないので revision を取らない。**公開もここを通る**
  (draft を消費する操作なので)
- **409 では相手が変えた箇所を出し、手元の入力は捨てない。自動 reload はしない**

**衝突の差分は画面の側で取る。** 相手が変えた field は「この画面が開いたときの content」と「いまの
content」の比較で決まり、前者を持っているのは画面だけになる。server は現在の content を返すところまでを
受け持つ。取り込みは field 単位で、押した field だけが相手の値になる。

**差分が指す path は編集フォーム・コメントの宛先と同じ語彙で書く。** 配列の要素は位置ではなく identity で
指し (`dataProviders.{id}.name`)、値スロットの identity はその catalog キー
(`experiments.{id}.values.{keyId}`)。**差分が挙げた path を全部取り込むと差分が空になる**ことが、
差分と取り込みを結ぶ唯一の歯止めになる — この 2 つは型では結べない。

**破棄も revision を取る。** 元に戻せない操作なので、開いてから誰かが編集した draft は捨てさせない。

**答えの分け方が 3 つある。** payload が画面の送る形になっていなければ 400 (画面側の不具合で、人には
直せない)。文の記法が弾かれたら 422。revision が合わなければ 409。どれもフォームの中身は動かさない。

**catalog が知らないキー・場所違いのキー・型の食い違い・別の語彙の term も 400。** どれもフォームが
提供しない入力なので、人が直せる問題ではない。

### 誰が開いているか

presence は **(draft, セッション) を主キー**にし、保持者と期限の列を最初から持つ。値は当面 NULL で、
排他に上げる判断をしたときに列を足さずに済む形にしておく。

- **粒度は draft。** dataset の画面も同じ draft の presence を名乗るので、同じ人が研究本体と dataset を
  同時に開いていても 1 行になる
- **期限切れは読み取り時に除外する。** 掃除が走らなかったことが「まだ編集中の人がいる」に化けない
- **画面を閉じたときに消さない。** 閉じたことを確実に送る手段が無いので、期限に任せる

## 他の版や draft と比べる

**draft が抱えているのは自分のコピーだけで、誰の派生かを覚えない。** 公開は新しい版を作る操作なので、
別の draft が先に公開されてもこの draft の持ち物は動かない。踏まれるものが無いので、衝突として検出する
ものも無い。

**代わりに、比べる相手を選んで差を見る。** 既定は最新の公開版で、更新の draft では更新する版。相手だけにある変更は 1 操作でまとめて
取り込み、両方が触っている箇所は field 単位で選ぶ。取り込みは通常の保存を通るので revision で照合され、
取り込んだ時点から preview もその姿になる。取り込まずに公開することもできる。

**比較は 2 つの姿のあいだで行う。** 「どちらが変えたか」は答えず、違いを並べて人が選ぶ。共通の祖先を
持たないので、draft が古い版から作られていても相手は今の最新になる。

**公開はこれを自動では混ぜない。** draft には共有リンクが紐づいていて、提供者が preview で見た姿が
そのまま公開されることが約束になっている。公開の時点で merge すると、承認された姿と違うものが出る。

**代わりに、編集画面が取り込む操作を持つ。**

- **相手だけが変えた箇所は 1 操作でまとめて取り込む。** 手元の値を失わないので選ぶ必要がない
- **両方が変えた箇所は field 単位で選ぶ。** 409 の取り込みと同じ道具と同じ見た目になる
- **取り込みは通常の保存を通る。** revision で照合され、取り込んだ時点から preview もその姿になる
- **配列は、その中の要素をこちらが触っていたら「両方が変えた」に倒す。** 配列そのものを取り込むと中身ごと
  置き換わるので、まとめて取り込む側に入れると手元の編集が黙って消える
- 取り込まずに公開することもできる。その場合は公開ゲートが列挙する ([publishing.md](publishing.md))

## データセットを足す・消す

**新しい dataset は draft の中で作り、作った時点でその版の一覧に載る。** 作っただけで載せ忘れると
誰も見つけられなくなるので、作成と掲載を分けない。掲載を変えるのは draft の content を変えることなので、
**作成も draft の revision で照合される**。

**掲載から外すことと消すことは別の操作になる。**

| 操作 | 何が起きるか | どこでやるか |
|---|---|---|
| この版の一覧から外す | dataset は残る。過去版はそれを載せ続ける | research の編集画面 |
| 消す | identity ごと消える。エントリも pin も一緒に消える | データセットの一覧 |

**消せるのは、この draft が作って、まだ一度も公開されていない dataset だけ。** 公開実績のあるものは
それを載せた版から辿れるので、消すと過去版の一覧が黙って変わる。孤児 (どの版にも載らない dataset) が
生まれるのは版が全部取り下げられたときか research を削除したときで、掲載から外すことでは生まれない。

**掲載から外したまま公開すると、その dataset は draft と一緒に消える** — この draft が作って一度も
公開されなかったものだからで、破棄したときと同じことが起きる。

## ファイル

**箱の画面は draft の外にある。** 箱は research に 1 つで版も draft も持たず、ファイルの公開は research の
公開とは独立した操作なので、draft の下に置くと「draft を公開したらファイルも公開される」と読める。
research の画面には件数と入口だけを出す。

画面から何ができるか、dataset がどのファイルを選ぶかは [files.md](files.md) の「画面」。

## レビュー

Google Docs 的な共有にする。**draft ごとに 1 本のリンクを持ち、リンクを知っている人全員が preview +
コメントできる。人ごとにリンクを発行しない。** 共有リンクの相手にはデータ提供者を含む。

**流れは 2 往復で、連絡は system の外。** 提供者は共有リンクで preview を読み、決まっていない値や間違いを
その欄のコメントに書き、研究全体のことは全体へのコメントに書く。書き終えたら「コメントを書き終えた」の印を
押す。admin はコメントを読んで draft を直し、直した内容の確認をメールで頼む。提供者は読み直し、直すところが
無ければ「直すところは無い」の印を押す。admin はそれを見て、自身の判断で公開する。**「確認してほしい」
「もう一度確認してほしい」の連絡はメール**で、system は印が押されたことを記録して admin に見せるだけ
(メール送信基盤が無い)。**preview の頭にこの手順を番号付きで書き、2 つの印をその下に置く** — 初めて開いた
提供者が、読む前に何をすればよいかを知る場所はそこしかない。図にせず文で書くのは、読み上げでも同じ順に
届くため。

### 共有リンク

| アドレス | 中身 |
|---|---|
| `/preview/:token` | draft を公開後の姿で読む |
| `/preview/:token/dataset/:datasetId` | その版が載せるデータセット 1 件 |

**データセットは identity で指す。** draft が作ったばかりのものには dataset id がまだ pin されていない。

- **共有状態は private とコメント可の 2 値。期限は既定で無期限。** トークンは draft の列なので、
  private に戻してから再度有効化しても同じリンクが使える
- **トークンの再発行を持つ。** 外に漏れたときに旧リンクを止める手段がこれしかない。private は
  「いまは見せない」、再発行は「このリンクはもう使わせない」で役割が違う
- **共有の設定は revision で照合しない。** content ではないので、競合で失われるのは直前の設定だけで、
  最後に押したものが勝つのが正しい。照合に載せると、共有を切り替えただけで開いている編集画面の保存が
  409 になる。draft への書き込みでこれを免れるのは、この 2 つと presence だけ
- **preview の応答に `X-Robots-Tag: noindex` と `Referrer-Policy: no-referrer` を付ける。** 未公開の
  content を無認証 URL で配る以上、クローラに拾われる経路と、外部リンクを踏んだときに Referer で
  トークンが漏れる経路を塞ぐ
- **トークンの検証は server 側のデータ取得経路に置く。** 画面のルートに掛けた guard は、同じデータを
  返す別経路が到達できるので担保にならない。private・期限切れ・再発行後の旧トークンはどれも
  **存在しないリンクと同じ 404** で答える。「あるが閉じている」と答えると draft の存在が漏れる

**preview は公開ページそのもの** — 同じ公開表現、同じ view、同じ component で、違うのは未確定値を残す
引数だけ ([data-model.md](data-model.md) の「公開表現」)。第一の用途が提供者への確認なので、公開画面と
同じ姿を見せるといちばん聞きたいスロットが消える。**未確定のスロットは赤い「ご教示ください」の印で出る** —
提供者にとってそれは状態の名前ではなく依頼で、答えはその欄のコメントに書いてもらう (上の「流れ」)。admin の
画面の「未確定」と同じ状態の、読む人が違う呼び方 ([glossary.md](glossary.md))。

**ダウンロード一覧だけは、渡す箱の list も違う。** draft の段階では公開 bucket が空なので、公開側だけを
見せると一覧が丸ごと消える。代わりに公開と非公開を合成した list を渡し、**非公開の行は名前とサイズと
公開後の URL を文字で出すだけでリンクにしない。** 共有リンクは知っている人全員が読めるものなので、
非公開の byte をここから渡すと bucket の在籍が公開状態だという決定を迂回できてしまう。

### コメントの宛先

**フィールド単位と値スロット単位、それに draft 全体に付ける。テキスト範囲は持たない。** 場所を持つ宛先は
**(対象, path) の組**で、対象は research content かある dataset、path は編集フォームと衝突の差分が使う
語彙そのもの。値スロットも path の中で指すので、場所を持つ宛先の種類は 2 つしか要らない。**全体への
コメントは場所を持たない宛先**で、研究全体について言うことをそこに書く。共有リンクからも書ける。admin だけの
メモ (上の「draft」) も場所を持たないが別の宛先で、共有リンクからは読めず書けない。**配列要素は identity で
指す** — コメントの宛先の主戦場がここなので、順序で指すと並び替えで参照が壊れる。

**投稿された宛先は、それが名指す content に実在するかを server が確かめる。** 共有リンクは無認証なので、
どこにでもコメントを積める形にはできない。データセットは、共有リンクからはその版が載せているものだけ、
admin は研究が持つものすべてが対象になる。全体とメモは場所を持たないので実在の確認は無いが、**メモは共有
リンクから拒む**。

**読み取り側も同じ集合に絞る。** preview が返すコメントと未解決の件数は、いま描いているページの宛先だけ —
research のページなら全体と research content とその版が載せる dataset、dataset のページならその dataset。
版に載らない dataset のコメントは、解決済みかどうかによらず返さない。メモは返さない。**画面に描かれないものは loader の
戻り値にも載せない** — SSR の水和 JSON は共有リンクを持つ誰でも読めるので、描画側で絞ると本文がそこから
漏れる。

**画面が印を付ける場所と、view が値を覚えている場所は同じ集合でなければならない。** 印だけあって値が
無ければ「変わった」と言いながら何が変わったか出せず、値だけあって印が無ければ数えた差が読者に見えない。
型では結べないので、**描画が出したアンカーと view が記録したアンカーが一致する**ことを test で守る。

### コメントの扱い

コメントはリンクを持つ人全員に見え、**返信を持たない**。1 つの場所のコメントは書かれた順に平らに並び、
続きを言うなら同じ場所に次のコメントを書く。返信の入れ子は、同じ場所に会話を 2 本以上立てて「どちらに
書くか」を選ばせるだけで、欄単位の宛先ではその選択に意味が無い。**解決はコメント 1 件ごとに、手で付ける**。

- **解決できるのは `edit-content` を持つ admin だけ。** 閲覧者は書いて読むところまで
- **編集されたことを自動でコメントに反映する仕組みは持たない。** 未確定値の解消は「コメントの付いた
  箇所を編集する」操作そのものなので、自動で解決にすると確認の機会が消える。解決を取り消せるのは、
  解決がクリック 1 つで、クリックは間違えるため
- 解決済みにしてもコメントは消えない。**共有リンクの期限が切れても残る。** 消えるのは draft を破棄した
  ときだけ
- **通知は無い。** メール送信基盤が無いので、admin が管理画面でコメントを見る

**一覧は draft 単位。** コメントも共有リンクも draft に紐づくので、同じ research に draft が 2 つあれば
中身が違う。混ぜると「どちらの話か」が消える。**編集画面と preview の欄の印は面を開き、面の中で読み・書き・解決する** ([admin-ui.md](admin-ui.md) の
「コメントの面」) — 直しながら閉じるのに画面を行き来させないため。面はページを離れずに答えが返る経路
(`…/draft/:draftId/comments`) へ投げる。レビュー画面は自分のページに投げて redirect で戻るので、
JavaScript が無くても書ける。JavaScript が無くても書ける。

### 投稿者

画面を開いた時点でサインインか自己申告の名前の入力を促す。サインイン済みなら Keycloak の
`preferred_username` を出して DDBJ アカウントの印を付け、未サインインなら自己申告の名前を
**sessionStorage に置く** (共有端末で前の人の名前が残るのを避ける)。**名前は必須** — 誰に聞き返せばよいか
分からないコメントはコメントではない。

閲覧者が押せる印は 2 つで、どちらも承認権限ではない。**「コメントを書き終えた」**は「読んで書いたので、次は
事務局が読む番だ」の意思表示、**「直すところは無い」**は「この内容で問題ない」の意思表示。**語は初めて開いた
人が読んで分かる長さにし、略語 (LGTM) は使わない** — 「コメントを書き終えました。事務局に確認をお願いします」
「直すところはありません。この内容で問題ありません」。押した人と日付を admin が研究の画面とレビューの画面で
見る。サインインしている場合にだけ本人性が伴う。サインイン済みの人は印ごとに 1 人 1 件に畳まれ、押し直すと
日付が動く。未サインインは押すたびに 1 件になる — 見分ける手がかりが無いのに畳むと、リンクを共有した別人
どうしが 1 人になる。

### 公開版との差

**preview と編集画面で、公開版と差がある箇所に印を付け、印を開くとそこが公開版で何と言っているかを
出す。** 何が変わったかを探させないためで、レビューの第一の仕事がそこにある。

- 比較の相手は**最新公開版**、更新の draft では**更新する版**。公開版が 1 つも無い research では
  印を出さない (比較の相手が無い)。dataset は版を持たないので、相手は「その版が持つ記述」になる
- **preview に印が付くのは公開ページが出す場所だけ。** catalog が公開ページに出さないキーは
  preview に出ないので、差の全体は編集画面の側で見る
- **配列は membership が動いたときに配列そのものが差になる**ので、そこに出す値は無い。印だけが立つ
- 差の取り込み (上の「他の版や draft と比べる」) とは別物。あちらは書き換える操作、これは読む側の印で、
  押しても content は動かない

## サイトコンテンツ

document / news / alert は research とは別の流れで編集する。版も pin も draft も無く、locale ごとに本文 1 つと
公開状態を持つ ([data-model.md](data-model.md) の「サイトコンテンツ」)。**全部の操作が `manage-site-content` を
要求する。**

| アドレス | 何の画面か |
|---|---|
| `/admin/documents` | document の一覧。語で絞り、新しい記事を作る |
| `/admin/documents/:documentId` | document 1 件。slug と、locale ごとの本文と公開状態、記事の削除 |
| `/admin/documents/series/:seriesId` | 系列 1 件。版の一覧、指し先の張り替え、版の追加、系列の削除 |
| `/admin/alert` | alert の全件。本文の対と、表示するかどうか |
| `/admin/news` | お知らせの一覧 (未公開を含む) |
| `/admin/news/:newsId` | お知らせ 1 件。公開日と、locale ごとの本文と公開状態、お知らせの削除 |
| `/admin/files` | `common/` の箱 |

**alert は両方の言語が揃うまで表示できない。** 保存はできる — 書きかけのあいだ片方ずつ進められる —
が、表示する操作だけが両方を要求する。alert は全ページに出るので、片方しか無いものを出すと、その言語の
読者に読めない箱を渡すことになる ([data-model.md](data-model.md) の「サイトコンテンツ」)。画面では 2 つの
欄が必須の印を持ち、片方が空のあいだ「表示」は押せず、理由は入口に pointer が乗るか focus が入ると出る
([ui.md](ui.md) の「押せるもの」)。**移行も同じ約束を守る** — v1 の CMS は片方だけのアラートを持てるので、
表示されているものの空いた側は `migration/input/alert-translations.json` の手で書いた訳で埋め、
**埋められなければ移行が止まる**。ポータルがアラートを書くことはできないため。

**表示の切り替えと本文の保存は、片方がもう片方を動かさない。** 表示する操作は画面にある本文をそのまま
書いてから表示するので、読まれていない文面が site に出ることがない。逆に本文だけを保存しても表示状態は
動かない — 表示中のアラートの誤字を直すのに、いったん下ろす必要はない。**並びは作った順**で、同じ時刻に
作られた 2 件も順番が入れ替わらない。

**一覧は 1 アドレス 1 行。** 版は `{slug}/version/{n}` なので系列の下に畳まれ、一覧に出るのは系列の行
だけになる。並びは slug 順で、位置を持たせない — 順序を人が決める需要が無く、持たせると slug と
食い違う。段の深さは slug そのものから数えるので、一覧を語で絞っても動かない。

**系列に効く操作 — 指し先の張り替え・版の追加・系列ごとの削除 — は系列の画面が持つ。** 一覧は記事を
探す場所で、そこから 1 件を選んだ先が書く場所になる。**画面は版なし slug を「代表アドレス」、その指し先の
版を「代表」と呼ぶ** — 読者が持つアドレスと、それが返す版の関係を、指す・指されるの語より先に言うため。
**系列の画面は代表アドレス (何であるか・張り替えは手で行うこと・張り替えの操作) を先に、版の一覧を後に
置く。** 版を持たない記事の画面は、バージョン管理へ移す操作 (下の「版に切り出す」) を頭の区画の 2 行目に
置く — 本文ではなく記事そのものに効く操作なので、言語の節に混ぜない。

**記事とお知らせの一覧は、どちらも研究一覧に揃える** (上の「管理画面」)。条件は左のペインに立って
畳め、表示件数はアドレスに載る。軸の中は OR、軸どうしは AND で、何も選ばなければ全件 (研究一覧と同じ
規則)。**並び替えを持つのはお知らせだけ** (公開日 / タイトル、既定は公開日の新しい順) — 記事は slug 順に
並ぶことで木になるので、並びを選ばせない (上の「管理画面」)。**軸は 3 つずつ**で、2 つは ja / en それぞれが公開されているか、残る 1 つは記事がバージョンを
持つかどうか、お知らせが公開日を持つかどうか。**窓が当たるのは行の見出しになっている 2 列** — 記事は
slug とタイトル、お知らせは公開日とタイトルで、`2026-06` と打てばその月のものが残る。

**locale ごとの操作は 2 つ** — 保存する / 公開状態を切り替える。**下書きの器は
持たない。保存は本文そのものを書き換え、公開中の記事なら保存した時点で公開ページが変わる。** 読まれない
まま書き進めたい改稿は、版を持つ記事なら次の版を未公開で書いて公開し、代表アドレスを張り替える (下の
「版に切り出す」)。版を持たない記事にその道は無く、保存がそのまま届く。

**記事とお知らせの編集画面は研究の編集と同じ 2 ペイン** ([admin-ui.md](admin-ui.md) の「編集画面」) —
左に言語 1 つのフォーム (編集 ja / 編集 en)、右にその言語の
公開ページの姿を打鍵に追随して描く。お知らせの日時と版への切り出しは頭の区画の 2 行目に立つ。描くのは
公開ページと同じ関数で、経路を増やさない (上の「フォームの隣に立つ公開ページ」と同じ線)。出さないのは見出しの
脇のリンクだけ ([admin-ui.md](admin-ui.md) の「編集画面」)。言語ごとに別の
form なので、描くのも言語ごと。本文の欄は code editor ([ui.md](ui.md))。

**公開状態は 1 つのボタンで、値は 2 つ。** 公開中なら「公開停止」、そうでなければ「公開」が立つ。2 つ
並べると、どちらかが必ずいまそうであることを名乗る。

**公開が出すのは画面にある本文。** 3 つが 1 つの form の中にあるので、押した時点で見えているものが
そのまま公開される — 「保存を忘れたので 1 つ前が出た」が起きない。

**確認を挟むのは削除だけ。** 公開と公開停止は隣り合う 1 つのボタンで往復でき、保存は打ち直せる。
**削除は記事 (お知らせ) そのものの 1 つだけで、言語の本文は削除しない。** 読ませたくない言語は公開停止に
すれば公開ページから消え、本文は手元に残る。本文だけを消す入口を言語の節に置くと、器の削除と同じ語が
同じ画面に 2 つ並び、どちらを押したかが読めない。**器の削除は画面の名前の右、戻る道の隣に 1 つ立つ**
([admin-ui.md](admin-ui.md) の「画面の名乗り」) — 作ったばかりの記事とお知らせは本文を 1 つも持たないので、言語の節の
中に置くと届かない。alert も同じで、1 件ごとの状態の行の右端に立つ。**版なし slug が指している記事は
消せない** — 消すと slug が答えられなくなるので、画面はその入口を出さず、server も撥ねる。系列ごと消す
入口も系列の画面の同じ場所に立つ (上の「系列に効く操作」)。

- **保存は revision で照合する。** research の draft と同じで、影響行数が 0 なら 409
- **保存の時点で本文を parse し、生 HTML と落とせないリンクの行き先を弾く。** 弾いたら保存全体を止め、
  どの locale の何行目かを返す。描画側は生 HTML を黙って落とすので、書いた人が気づける場所がここしかない
  ([public-pages.md](public-pages.md) の「本文の書式」)。**返すのは locale・種類・行番号だけ**で、その行の
  字面は返さない (欄の中でその行を見れば足りる)。**画面はその欄の下に、行番号・何が悪いか・その行へ移る道を
  出し、editor はその行に色を敷く** ([admin-ui.md](admin-ui.md) の「編集画面」)。同じ行の同じ種類は 1 つに
  畳む。画面の上の答えは「保存していない」と言うだけで、行は言わない
- **公開日** — document は初回の公開で今日が入り、以後は動かない。news は admin が入れる (一覧の並びで
  あり、告知そのものの日付になる)。**news だけは日時で、値は JST**。同じ日に複数出たときの前後を admin が
  決められる形で、欄も画面もそう名乗る。**公開日時が未来のあいだ、その news は公開側に出ない**
  ([public-pages.md](public-pages.md) の「何を根拠に『公開されている』と言うか」) ので、管理の一覧と
  1 件の画面は日時の隣でそれを告げる。**公開状態の語は「公開中 / 未公開」の 2 つのまま**で、予約は公開日の
  側が言う — 公開状態は locale ごとのもので、公開日時は identity の側に 1 つしかない。**日時を持たない
  news は書きかけ**で、公開側には出ない。管理の一覧では末尾に沈み (上の「管理画面」)、絞り込みの軸の
  1 つになる。**alert は日付を持たない** — 管理画面が状態の隣に出す「表示日」は、証跡に残る最後の
  「表示にした」操作の日で、表示中のあいだだけ出す。移行で立てた alert は操作の跡が無いので出ない

**slug の検査は 3 つ** — 形、route が持つアドレスとの衝突、`document` と `document_series` の両方での
重複。rename もできるが、**外部が焼き込んでいる slug を変えると参照が切れる**ので画面がそれを告げる。
**slug を打ち直す面は、記事も `common/` のファイルも 1 つの部品** (`components/contents.tsx` の
`SlugEditor`) — 欄は面の中にあり、画面に開いたままの欄を置かない。画面が持つのは入口だけで、記事では
名前の行に、ファイルでは行の中に立つ。

**画面の語は「slug」と「アドレス」を分ける。** slug は admin が打つ識別子で、欄・列・入口はこの語で
名乗る。アドレスは読者が開く URL (`/{slug}`、`/files/common/{slug}`) で、slug を変えたときに何が
起きるかを言う文と、URL そのものをコピーする操作だけがこの語を使う。slug の欄や節を「アドレス」と
名乗らない。

**版に切り出す。** 版を持たなかった document に版を作る操作は、いまの本文を `{slug}/version/{n}` へ移して、
空いた slug で指し先の行を作ること。本文のコピーが生まれない。以後は「次の版を作って書いて公開し、指し先を
張り替える」の繰り返しになる。**版番号は打ち直せる** — 画面が出すのは既定 (切り出しは 1、以後は最大 + 1)
だけで、本文の `Ver.` に合わせる必要があるため。使用済みの番号は slug の重複として弾かれる。

**版を持つのをやめる操作は無い** ([data-model.md](data-model.md))。**消すのは 2 通り** — 版 1 つを消すか、
系列を丸ごと消すか。前者で指し先を消すには先に張り替える。**版 1 つを消した後は系列の画面に戻る** —
一覧は版の行を持たないので、そこへ戻ると消した版の隣を見失う。後者は版なし slug と配下の全版を 1 操作で消す
ので、公開中のものを含むときは何を消すかを確認画面が列挙する。

**指し先がその言語で公開されていない版なし slug を、木が不備として出す。** 恒久的に応答し続ける必要が
あるのに、指し先の公開状態でそれが破れるのはここだけになる。

**`common/` の箱**は記事から参照する画像と PDF の置き場で、公開 bucket 固定。upload は research の箱と
同じ presigned URL の経路だが、**置いた時点で公開される**ので upload も削除も証跡に残る
([publishing.md](publishing.md) の「証跡」)。非公開に倒す操作は無い。

## 意図的にやっていないこと

本文の節と同じ順に並べる。

| やらないこと | 理由 |
|---|---|
| 下書きの画面に段の列 (stepper) やタブを置くこと | 面どうしの入口と事実は研究の画面の表と頭の区画が持つ。段の列は仕事の順を答えて事実を添え書きにし、パンくずに見えた |
| データ提供申請の一覧から下書きへ入れる道 | 一覧に下書きを覚えさせると絞り込み・並び替え・ページ送りのどれかで落ち、同じ枝番が 2 通りの姿で出る。取り込みは下書きの側の画面が枝番を並べる |
| 承認ワークフロー / review status | レビューは状態ではなく活動。「review 中は編集できない」はレビューの本体 (コメントを受けて直す) を止める |
| 語彙値を「選べない」状態にすること | 使われていない語は消せ、使われている語は統合で畳める。消しも畳みもせずに選ばせないだけの語を残す場面が、その 2 つで足りない形で出ていない |
| 下書きを外から作る経路が語彙値を作ること | 打った文字列がそのまま catalog に載ることが、キーの揺れを生んできた。当たらなかった値は列挙して、その項目の語の画面へ送る |
| 疾患の呼称に候補を出すこと | 記事に書かれた名前を持つ欄なので、寄せる先が無い。候補を出すと curator が既存の綴りに引き寄せられ、原文と違う名前が入る |
| 上流の値を content に自動で入れること | 取り込みの面が「いまの下書き」と「申請」を並べ、書くのは人。自動で混ぜると、承認された姿と違うものが下書きに入る |
| 申請書の関連論文・研究分担者・連絡先を下書きに入れること | 関連論文は承認枝番の半分がプレースホルダ (`N/A` / `投稿中`)。残る 2 つは公開ページに出ない値 |
| 編集画面から catalog にキーを足すこと | 同じ理由 |
| 編集フォームを JS 無しで動かすこと | 状態の切り替え・配列の並べ替え・409 の取り込みがどれも画面の中の操作 |
| 悲観ロック | 実測で救う対象が無く、逃げ道の無いロックを持つ実装も無い。正しさは保存時の照合に寄せる |
| autosave | 打鍵の途中が下書きの姿になると、共有リンクの preview がレビューの最中に勝手に動く。下書きを動かすのは明示保存だけ |
| draft の巻き戻し (undo) | 409 で弾かれた入力はフォームに残るので、失われるのは画面を閉じたときだけ。その 1 ケースのために、常時の UI と draft ごとのスナップショットの蓄積を抱えることになる |
| 公開時の自動 merge | draft は共有リンクが見せている姿そのもの。混ぜると承認された姿と違うものが出る |
| experiment に独立した revision を持たせること | dataset content の中の要素なので、属する dataset の照合で足りる |
| コメントのテキスト範囲アンカー | 第一のユースケース (値の無いスロット) に届かず、再アンカーの実装が重い |
| コメントへの返信 (入れ子のスレッド) | 欄単位の宛先では同じ場所に会話が 2 本立つだけ。続きは同じ場所に次のコメントを書けば足りる |
| コメントや印のメール通知 | メール送信基盤が無い。「確認して」「もう一度確認して」の連絡は人がメールで送り、system は押された印を admin に見せる |
| 人ごとの共有リンク | 相手を数えるためのものではない。誰に渡ったかは、返ってきたコメントの署名で分かる |
| サイトコンテンツの presence・共有リンク | 版が無いので比べる相手が無く、並行して同じ document を書いた実績も無い |
| サイトコンテンツの公開の予約 | research と同じ。日付は属性であって実行の引き金ではない |
| サイトコンテンツの言語ごとの本文の削除 | 読ませたくない言語は公開停止で足りる。本文だけを消す入口が器の削除と同じ画面に並ぶと、2 つの削除が同じものに読める |
| 通知 | メール送信基盤が無い |
