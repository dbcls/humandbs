# 編集

編集は admin が draft に対して行う。データ提供者やレビュアは共有リンクから preview とコメントだけが
できる。draft を版にする側は [publishing.md](publishing.md)。

誰がサインインでき何を許されるかは [auth.md](auth.md)、モデルの側の不変条件は
[data-model.md](data-model.md) にある。ここは操作とその制約。

## 管理画面

| アドレス | 何の画面か |
|---|---|
| `/admin/research` | 研究の一覧 |
| `/admin/research/:researchId` | 1 研究。pin されたラベル・公開版・draft・データセット |
| `/admin/research/:researchId/files` | 研究の箱。upload・公開状態の切り替え・削除 (下の「ファイル」) |
| `…/draft/:draftId` | draft の research content を書く |
| `…/draft/:draftId/dataset` | その draft から見たデータセットの一覧 |
| `…/draft/:draftId/dataset/:datasetId` | データセット 1 件を書く (experiment を含む) |
| `…/draft/:draftId/publish` | 公開の確認 ([publishing.md](publishing.md)) |
| `…/draft/:draftId/review` | 共有リンクとコメント (下の「レビュー」) |

公開ページと同じく ja / en の両方にアドレスを持つ。

**research も dataset も identity で指す。** ラベルはまだ pin されていないことがあり、pin は訂正も
されるので、管理画面のアドレスをラベルに寄せると開けない研究と動くアドレスが生まれる。

**一覧の窓は直引きで、公開検索ではない。** 全文索引は公開分しか持たないのに、この一覧の主役は未公開の
方にある。窓は hum ラベル・dataset id・研究題目・提供者名に部分一致し、空白で区切った語はすべて含む
ものを探す。並びは最後に触れた順。

**不備の絞り込みは content から導出できる 3 つだけ** — hum ラベルが未 pin、未確定の値がある、未翻訳の
field がある。判定は純関数で、**draft があればその content を、無ければ最新公開版を見る** (直すのは
draft の側なので)。「上流の対応と食い違う」はキャッシュを要するので公開ゲートの側に置く。

## draft

**1 つの research に draft を複数持てる。** draft は未公開の作業コピーで、履歴ではない。

- **content** — 編集中の research content。共有リンクはここに紐づく
- **メモ** — draft 全体に対する自由文。admin だけが読み、preview には出ない。提供者に伝えたいことは
  コメントで書くので経路が分かれる
- **parent** — 派生元の ContentSnapshot への参照。公開時に「派生元が最新でない」を検出する。版ではなく
  スナップショットを指すのは、fix が版番号を変えないため
- **変更エントリ** — 触った dataset だけが実体を持つ (copy-on-write)。**派生元の published content も
  併せて持つ**ので、衝突の差分は 3-way になる
- **新規 dataset の identity** — draft と運命を共にする。破棄すれば pin ごと消える

draft ごとに変更エントリを持つのは、draft を複数許す決定から導かれる。共有の 1 行にすると、並行する
2 つの draft が同じ dataset を別内容で持てない。

**draft の保存には完全性の制約を置かない。** 未確定を抱えたまま保存して共有するのが標準の作業状態で、
検査は公開操作のときだけ行う。

**draft が作られる経路は 2 つ。** 新しい研究を作る (identity と空の content を同時に作る) か、既存の
research から作る (最新公開版の ContentSnapshot を parent にして content をコピーする)。公開版が 1 つも
無い research では空から始まり parent を持たない。

**公開は draft を消費する。** 版として出たものが draft としても残ると、同じ内容が 2 か所にあって
どちらが正かを言えなくなる。続きを書くときは最新の公開版から新しい draft を作る。

## 保存の単位

**research と dataset は別々に保存する。** research の版は 1 つのものなので 1 画面ぶんをまとめて送るが、
dataset はそれぞれが identity を持ち、公開後は参照している全公開版に効く別の実体になる。1 研究が
200 を超える dataset を持つことがあり、1 つの衝突が残り全部の衝突になるのも正しくない。

したがって draft の下に可変な行は 2 種あり、**それぞれが自分の revision で照合される**。

| 保存するもの | 単位 | 照合する revision |
|---|---|---|
| research content とメモ | draft 1 つ | draft の revision |
| dataset content (experiment を含む) | 変更エントリ 1 行 | そのエントリの revision |

**experiment は自分の revision を持たない。** dataset content の中の順序つきの要素なので、その編集は
属する dataset のエントリの照合で守られる。

## 編集フォーム

翻訳対は左右 2 カラムで、状態は ja / en が独立に持つ。

- **打ちかけの値は状態を変えても消えない。** 「未確定にする」を押した field の入力は画面に残り、
  **保存の時点で状態が値以外なら捨てられる**。押し間違いが入力の消失にならない
- **未翻訳は操作しない。** 両方の言語が値を持ち片方だけが空なら、自動でバッジが出る
- `datasetIds` はこの research の既存 dataset から選んで並べる。**他の research の dataset を並べる
  保存は拒む** — dataset は 1 つの research に従属するので、画面が出さないものは入力でもない

**dataset の値は catalog のキーの下にあり、持っているキーだけが画面に出る。** スロットが無いことは
「値が空」とは別のことで、その項目を持たないという意味になる。項目を足すのは catalog から選ぶことで、
**その場で新しいキーを作る経路は持たない** — キーの揺れは、打った文字列がそのまま catalog に載ることで
生まれてきた。

**入力の形はキーの型が決める。** いま入力できるのは翻訳対の文 (`text`) と語彙の選択 (`vocabulary`) の
2 つで、catalog に実在するのもこの 2 つだけ。**他の型が現れたら例外にする** — 画面に出せない値を黙って
落とすと、開いて保存しただけで消える。単位の換算と入力欄は、その型を catalog に足す層で一緒に作る。

## 文の保存

文は markdown で入力し、**保存の時点で木に落とす**。落とせない記法は弾き、黙って消さない
([data-model.md](data-model.md) の「値と文」)。

- 弾くのは見出し・箇条書き・引用・コード・強調・打ち消し・表・水平線・画像・参照リンク・脚注・生 HTML。
  残るのは段落と行とインラインのリンクだけ
- **弾いたら保存全体を止める。** どの field のどの言語の何行目かを返し、フォームの入力はそのまま残る。
  **1 つ目で止めず全部を返し、画面が並べる順に返す** — 1 回の編集を 2 往復にしないため
- **保存は書かれていないリンクを作らない。** 表を見分けるために GFM を有効にする必要があるが、GFM は
  裸の URL もリンクに変える。これを採ると URL を含む field を開いて何も変えずに保存しただけで content が
  変わるので、裸の URL は文字のまま残す。おかげで**一度保存を通った文は、編集画面に出して保存し直しても
  同じ木になる** — 衝突の差分にも版間の差分にも、誰も書いていない変更が出ない
- 移行の変換は逆に**畳む**。dump は自分を直せないが、人は直せる

## 同時編集

**排他しない。** 編集画面を開いている人を presence として表示するだけで、他者を read-only にしない。
正しさは保存時の楽観照合で担保する。

- **更新は `WHERE id = ? AND revision = ?` の形で行い、影響行数が 0 なら 409**
- **変更エントリの初回作成は「無ければ挿入」で行い、挿入されなければ 409。** 画面が持つ revision が
  「まだ無い」であることが、挿入と更新を分ける唯一の印になる
- **複数行にまたがる保存は 1 トランザクションで全部照合し、1 つでも 0 行なら全体を rollback する**
- **revision に `xmin` を使わない。** VACUUM FREEZE で値が変わるので照合の基準にならない
- **draft への書き込みを 1 つのモジュールに閉じ込め、既存の行を変える全関数が照合対象の revision を
  必須引数に取る。** DB のトリガでは守れない — 述語を忘れた更新も revision を増やせば通るので、防げるのは
  呼び出し側の形だけ。行を作る操作だけは照合の相手がいないので revision を取らない。**公開もここを通る**
  (draft を消費する操作なので)
- **409 では相手が変えた箇所を出し、手元の入力は捨てない。自動 reload はしない**

**衝突の差分は画面の側で取る。** 相手が変えた field は「この画面が開いたときの content」と「いまの
content」の比較で決まり、前者を持っているのは画面だけになる。server は現在の content を返すところまでを
受け持つ。取り込みは field 単位で、押した field だけが相手の値になる。

**差分が指す path は編集フォーム・コメントの宛先と同じ語彙で書く。** 配列の要素は位置ではなく identity で
指し (`dataProviders.{id}.name`)、値スロットの identity はその catalog キー
(`experiments.{id}.values.{keyId}`)。**差分が挙げた path を全部取り込むと差分が空になる**ことが、
差分と取り込みを結ぶ唯一の歯止めになる — この 2 つは型では結べない。

**破棄も revision を取る。** 元に戻せない操作なので、開いてから誰かが編集した draft は捨てさせない。

**答えの分け方が 3 つある。** payload が画面の送る形になっていなければ 400 (画面側の不具合で、人には
直せない)。文の記法が弾かれたら 422。revision が合わなければ 409。どれもフォームの中身は動かさない。

**catalog が知らないキー・場所違いのキー・型の食い違い・別の語彙の term も 400。** どれもフォームが
提供しない入力なので、人が直せる問題ではない。

### 誰が開いているか

presence は **(draft, セッション) を主キー**にし、保持者と期限の列を最初から持つ。値は当面 NULL で、
排他に上げる判断をしたときに列を足さずに済む形にしておく。

- **粒度は draft。** dataset の画面も同じ draft の presence を名乗るので、同じ人が研究本体と dataset を
  同時に開いていても 1 行になる
- **期限切れは読み取り時に除外する。** 掃除が走らなかったことが「まだ編集中の人がいる」に化けない
- **画面を閉じたときに消さない。** 閉じたことを確実に送る手段が無いので、期限に任せる

## 公開されている内容が動いたとき

draft が抱えているのは、始めた時点の公開内容のコピーになる。その間に別の draft が公開されると、
3 者 — 始めた時点 / いまの公開内容 / この draft — が揃い、「相手が変えた箇所」と「自分が変えた箇所」を
切り分けられる。research content は `parent`、dataset は変更エントリの派生元がその起点。

**公開はこれを自動では混ぜない。** draft には共有リンクが紐づいていて、提供者が preview で見た姿が
そのまま公開されることが約束になっている。公開の時点で merge すると、承認された姿と違うものが出る。

**代わりに、編集画面が取り込む操作を持つ。**

- **相手だけが変えた箇所は 1 操作でまとめて取り込む。** 手元の値を失わないので選ぶ必要がない
- **両方が変えた箇所は field 単位で選ぶ。** 409 の取り込みと同じ道具と同じ見た目になる
- **取り込みは通常の保存を通る。** revision で照合され、undo にも積まれ、取り込んだ時点から preview も
  その姿になる
- **配列は、その中の要素をこちらが触っていたら「両方が変えた」に倒す。** 配列そのものを取り込むと中身ごと
  置き換わるので、まとめて取り込む側に入れると手元の編集が黙って消える
- 取り込まずに公開することもできる。その場合は公開ゲートが列挙する ([publishing.md](publishing.md))

## draft の巻き戻し

draft ごとに undo を持つ。**目的は 409 で弾かれた入力を捨てないことで、履歴を残すことではない。**

- 記録するのは明示保存の直前状態と、409 で弾かれたフォームの内容
- 粒度は draft 全体。research content とメモと全変更エントリを 1 つのスナップショットにする。
  **深さの上限は 10。保持期間の上限は持たない**
- **スナップショットを行として積み、11 件目を入れるときに最古を消す。** 1 つの JSONB 値にまとめると、
  1 回の保存がスタック全体の書き換えになる
- draft と運命を共にする。破棄・公開すれば undo も消えるので、永続する履歴にはならない
- autosave は持たない。差分表示は 409 の画面と共用する

**戻すことは書き戻すことではない。** 選んだスナップショットは今開いている画面のフォームに入るだけで、
DB は動かない。保存を押せば通常の経路を通り、revision で照合される。409 で弾かれた分を書き戻す形にすると
**その経路だけが照合を素通りする**ことになり、相手の保存を黙って上書きできてしまう。dataset の画面は
スナップショットからその dataset の分だけを取る。

## データセットを足す・消す

**新しい dataset は draft の中で作り、作った時点でその版の一覧に載る。** 作っただけで載せ忘れると
誰も見つけられなくなるので、作成と掲載を分けない。掲載を変えるのは draft の content を変えることなので、
**作成も draft の revision で照合される**。

**掲載から外すことと消すことは別の操作になる。**

| 操作 | 何が起きるか | どこでやるか |
|---|---|---|
| この版の一覧から外す | dataset は残る。過去版はそれを載せ続ける | research の編集画面 |
| 消す | identity ごと消える。変更エントリも pin も一緒に消える | データセットの一覧 |

**消せるのは、この draft が作って、まだ一度も公開されていない dataset だけ。** 公開実績のあるものは
それを載せた公開版から辿れるので、消すと過去版の一覧が黙って変わる。孤児 (どの公開版からも参照されない
dataset) が生まれるのは公開版が全部取り下げられたときか research を削除したときで、掲載から外すことでは
生まれない。

**掲載から外したまま公開すると、その dataset は draft と一緒に消える** — この draft が作って一度も
公開されなかったものだからで、破棄したときと同じことが起きる。

## ファイル

**箱の画面は draft の外にある。** 箱は research に 1 つで版も draft も持たず、ファイルの公開は research の
公開とは独立した操作なので ([data-model.md](data-model.md) の「ファイル」)、draft の下に置くと「draft を
公開したらファイルも公開される」と読める。research の画面には件数と入口だけを出す。

**upload は server が発行する presigned URL で行い、byte はアプリを通らない。**

- **画面はまず名前とサイズと種類を送り、URL を受け取ってから PUT する。** 署名にサイズと種類が入って
  いるので、送るものが決まる前に URL を出せない
- **64 MiB を超えるものは multipart になる。** part の PUT だけが presigned で、開始と完了は server 側。
  進捗と中断を出し、**ページを閉じた後の再開は持たない** (途中の part は S3 側に残るので、入れ直せば
  同じ名前で上書きされる)
- **upload 直後は非公開。** 提供者から受領した瞬間に匿名で取得できる状態を作らない
- **同じ名前の upload は上書きになる。** 名前が key そのものなので、別物として並べる余地がない

**公開状態の切り替えと削除は複数選んでまとめて行う。** 切り替えは実バイトコピーの job なので画面は
待たず、実行待ちと実行中を list の上に出す。**公開実績のあるファイルの削除には確認を挟む** — 外部から
直接参照されている実績があり、参照関係を持たない以上その検査ができない。

**dataset がどのファイルを選ぶかは、dataset の編集画面で決める。** 箱の list に対する順序つきの選択で
([data-model.md](data-model.md) の「ファイル」)、選んだものを並べ、絞り込みの窓を持つ picker から足す。
**選択は dataset content の一部なので、保存も照合も他の値と同じ**変更エントリ 1 行の単位になる。
**draft の段階では公開 bucket が空**なので、選ぶ相手は公開と非公開を合成した admin 側の list。

## レビュー

Google Docs 的な共有にする。**draft ごとに 1 本のリンクを持ち、リンクを知っている人全員が preview +
コメントできる。人ごとにリンクを発行しない。** 共有リンクの相手にはデータ提供者を含む。

### 共有リンク

| アドレス | 中身 |
|---|---|
| `/preview/:token` | draft を公開後の姿で読む |
| `/preview/:token/dataset/:datasetId` | その版が載せるデータセット 1 件 |

**データセットは identity で指す。** draft が作ったばかりのものには dataset id がまだ pin されていない。

- **共有状態は private とコメント可の 2 値。期限は既定で無期限。** トークンは draft の列なので、
  private に戻してから再度有効化しても同じリンクが使える
- **トークンの再発行を持つ。** 外に漏れたときに旧リンクを止める手段がこれしかない。private は
  「いまは見せない」、再発行は「このリンクはもう使わせない」で役割が違う
- **共有の設定は revision で照合しない。** content ではないので、競合で失われるのは直前の設定だけで、
  最後に押したものが勝つのが正しい。照合に載せると、共有を切り替えただけで開いている編集画面の保存が
  409 になる。draft への書き込みでこれを免れるのは、この 2 つと presence だけ
- **preview の応答に `X-Robots-Tag: noindex` と `Referrer-Policy: no-referrer` を付ける。** 未公開の
  content を無認証 URL で配る以上、クローラに拾われる経路と、外部リンクを踏んだときに Referer で
  トークンが漏れる経路を塞ぐ
- **トークンの検証は server 側のデータ取得経路に置く。** 画面のルートに掛けた guard は、同じデータを
  返す別経路が到達できるので担保にならない。private・期限切れ・再発行後の旧トークンはどれも
  **存在しないリンクと同じ 404** で答える。「あるが閉じている」と答えると draft の存在が漏れる

**preview は公開ページそのもの** — 同じ公開表現、同じ view、同じ component で、違うのは未確定値を残す
引数だけ ([data-model.md](data-model.md) の「公開表現」)。第一の用途が提供者への確認なので、公開画面と
同じ姿を見せるといちばん聞きたいスロットが消える。

**ダウンロード一覧だけは、渡す箱の list も違う。** draft の段階では公開 bucket が空なので、公開側だけを
見せると一覧が丸ごと消える。代わりに公開と非公開を合成した list を渡し、**非公開の行は名前とサイズと
公開後の URL を文字で出すだけでリンクにしない。** 共有リンクは知っている人全員が読めるものなので、
非公開の byte をここから渡すと bucket の在籍が公開状態だという決定を迂回できてしまう。

### コメントの宛先

**フィールド単位と値スロット単位で付ける。テキスト範囲は持たない。** 宛先は **(対象, path) の組**で、
対象は research content かある dataset、path は編集フォームと衝突の差分が使う語彙そのもの。値スロットも
path の中で指すので、宛先の種類は 2 つしか要らない。**配列要素は identity で指す** — コメントの宛先の
主戦場がここなので、順序で指すと並び替えで参照が壊れる。

**投稿された宛先は、それが名指す content に実在するかを server が確かめる。** 共有リンクは無認証なので、
どこにでもコメントを積める形にはできない。データセットは、共有リンクからはその版が載せているものだけ、
admin は研究が持つものすべてが対象になる。

**画面が印を付ける場所と、view が値を覚えている場所は同じ集合でなければならない。** 印だけあって値が
無ければ「変わった」と言いながら何が変わったか出せず、値だけあって印が無ければ数えた差が読者に見えない。
型では結べないので、**描画が出したアンカーと view が記録したアンカーが一致する**ことを test で守る。

### コメントの扱い

コメントはリンクを持つ人全員に見え、スレッドで返信でき、**手動で解決済みにできる**。

- **解決できるのは `edit-content` を持つ admin だけ。** 閲覧者は書いて読むところまで
- **編集されたことを自動でコメントに反映する仕組みは持たない。** 未確定値の解消は「コメントの付いた
  箇所を編集する」操作そのものなので、自動で解決にすると確認の機会が消える。解決を取り消せるのは、
  解決がクリック 1 つで、クリックは間違えるため
- 解決済みにしてもコメントは消えない。**共有リンクの期限が切れても残る。** 消えるのは draft を破棄した
  ときだけ
- **通知は無い。** メール送信基盤が無いので、admin が管理画面でコメントを見る

**一覧は draft 単位。** コメントも共有リンクも draft に紐づくので、同じ research に draft が 2 つあれば
中身が違う。混ぜると「どちらの話か」が消える。**編集画面の field に付いたコメントからも解決できる** —
直しながら閉じるのに画面を行き来させないため。編集画面はそのために、ページを離れずに答えが返る経路
(`…/draft/:draftId/comments`) へ投げる。preview とレビュー画面は自分のページに投げて redirect で戻るので、
JavaScript が無くても書ける。

### 投稿者

画面を開いた時点でサインインか自己申告の名前の入力を促す。サインイン済みなら Keycloak の
`preferred_username` を出して DDBJ アカウントの印を付け、未サインインなら自己申告の名前を
**sessionStorage に置く** (共有端末で前の人の名前が残るのを避ける)。**名前は必須** — 誰に聞き返せばよいか
分からないコメントはコメントではない。

閲覧者は LGTM を押せる。承認権限ではなくレビュー済みの意思表示で、サインインしている場合にだけ本人性が
伴う。サインイン済みの人は 1 人 1 件に畳まれ、未サインインは押すたびに 1 件になる — 見分ける手がかりが
無いのに畳むと、リンクを共有した別人どうしが 1 人になる。

### 最新公開版との差

**preview と編集画面で、最新公開版と差がある箇所に印を付け、印を開くとそこが公開版で何と言っているかを
出す。** 何が変わったかを探させないためで、レビューの第一の仕事がそこにある。

- 比較の相手は**最新公開版**。公開版が 1 つも無い research では印を出さない (比較の相手が無い)。
  dataset は版を持たないので、相手は「いま公開されている記述」になる
- **preview に印が付くのは公開ページが出す場所だけ。** メモ・ORCID・catalog が公開ページに出さないキーは
  preview に出ないので、差の全体は編集画面の側で見る
- **配列は membership が動いたときに配列そのものが差になる**ので、そこに出す値は無い。印だけが立つ
- 3-way の取り込み (上の「公開されている内容が動いたとき」) とは別物。あちらは書き換える操作、これは
  読む側の印で、押しても content は動かない

## 意図的にやっていないこと

| やらないこと | 理由 |
|---|---|
| 承認ワークフロー / review status | レビューは状態ではなく活動。「review 中は編集できない」はレビューの本体 (コメントを受けて直す) を止める |
| 悲観ロック | 実測で救う対象が無く、逃げ道の無いロックを持つ実装も無い。正しさは保存時の照合に寄せる |
| autosave | undo の目的が「弾かれた入力を捨てない」ことなので、明示保存の直前だけを積めば足りる |
| undo が DB を書き戻すこと | 照合を素通りする経路になる。戻すのはフォームまでで、書くのは通常の保存 |
| 公開時の自動 merge | draft は共有リンクが見せている姿そのもの。混ぜると承認された姿と違うものが出る |
| experiment に独立した revision を持たせること | dataset content の中の要素なので、属する dataset の照合で足りる |
| 編集フォームを JS 無しで動かすこと | 状態の切り替え・配列の並べ替え・409 の取り込みがどれも画面の中の操作。読む側の画面は JS 無しでも動く |
| 編集画面から catalog にキーを足すこと | 打った文字列がそのまま catalog に載ることが、キーの揺れを生んできた |
| コメントのテキスト範囲アンカー | 第一のユースケース (値の無いスロット) に届かず、再アンカーの実装が重い |
| 人ごとの共有リンク | 相手を数えるためのものではない。誰に渡ったかは、返ってきたコメントの署名で分かる |
| 通知 | メール送信基盤が無い |
