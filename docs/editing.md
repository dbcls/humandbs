# 編集

研究の内容を admin が下書きとして書き、レビューを受けるまでの決まりをまとめる。下書きを公開してバージョンにする流れは [publishing.md](publishing.md)、記事とお知らせの編集は [site-content.md](site-content.md)、誰がどの操作をできるかは [auth.md](auth.md) にある。編集するのは admin だけである。提供者 (データ提供者と、その確認を頼まれた人) はアカウントを使わず、共有リンクからプレビューを読んでコメントを書く。

## 下書き

下書きは、研究の未公開の作業コピーである。公開した内容はバージョンとして別に保存されるので、下書きを履歴としては使わない。

- 1 つの研究に下書きを複数作れる。同じ研究の下書きは更新日時で見分け、下書きに名前は付けない。
- 下書きには、研究の内容、admin だけが読むメモ、下書きの中で書いたデータセットの内容、その下書きで作成したデータセットを置く。データセットの内容を下書きごとに分けるのは、並行する 2 つの下書きが同じデータセットを別の内容で書けるようにするためである。
- 保存のときに必須項目の検査はしない。未確定の項目を残したまま保存して共有するのが普通の作業の状態であり、検査は公開のときだけ行う。
- 下書きにはバージョン番号が無く、番号は公開のときに決まる。どこからコピーしたかも記録せず、取り込み元はその都度選ぶ。
- 下書きが変わるのは、明示的に保存したときだけである。自動保存も元に戻す機能も無い。入力の途中で下書きが変わると、レビューの最中に共有リンクのプレビューが変わってしまうためである。
- 公開すると下書きは消える。同じ内容がバージョンと下書きの両方に残ると、どちらが正しいのか決められないためである。続きを書くときは、バージョンから新しい下書きを作る。
- 下書きに値を入れる方法は、フォームに入力することと取り込むことの 2 つだけである。バージョンのコピー、申請からの研究の作成、公開中のバージョンの更新は、どれも「空の下書きを作って取り込む」操作をまとめたものである。公開ページに直接書き込む方法は無い。

### 公開中のバージョンの更新

公開中のバージョンを直す操作を「更新」と呼ぶ。更新のあいだも、そのバージョンは公開されたままである。

- バージョンの「編集」を押すと、そのバージョンの内容をコピーした下書きが作られ、更新中の内容はこの下書きに書く。画面ではこの下書きを下書きの一覧に並べず、元のバージョンを「更新中」と表示する。
- 1 つのバージョンにつき、更新の下書きは 1 つだけ作れる。更新中のバージョンは取り下げられないので、取り下げたいときは先に更新を中止する。
- 更新を公開すると、同じ番号のバージョンの内容が入れ替わる。直しているあいだ公開ページから消す方式は採らない。読者から見ると取り下げと区別が付かないためである。

## 同時編集と保存

複数の admin が同じ下書きを同時に開いてもよい。ロックはせず、保存するときに相手の変更と衝突していないかを確かめる。

### 更新番号による照合

下書きと、下書きごとのデータセットの内容には、それぞれ更新番号 (保存のたびに 1 増える整数、コード上は `revision`) がある。保存では、画面を開いたときの更新番号と今の更新番号を比べる。

- 研究の内容は下書きの更新番号で、データセットの内容 (解析手法を含む) はそのデータセットの内容の更新番号で照合する。1 つの研究に 200 を超えるデータセットが付くことがあり、1 か所の衝突で全体を保存できなくなるのを避けるためである。
- データセットの追加・削除・並べ替えは研究の内容を変えるので、下書きの更新番号で照合する。
- 更新は `WHERE id = ? AND revision = ?` で行い、一致する行が無ければ 409 を返す。データセットの内容を初めて保存するときは「無ければ挿入する」で行い、挿入できなかった側が 409 になる。
- 複数の行を書き換える保存は 1 つのトランザクションで全部を照合し、1 つでも一致しなければ全体を取り消す。
- 下書きの削除も更新番号を照合する。開いたあとに誰かが編集した下書きは削除できない。
- 更新番号に PostgreSQL の `xmin` は使わない。VACUUM FREEZE で値が変わるためである。
- 下書きへの書き込みは、公開の処理も含めてすべて `app/admin/drafts.server.ts` の関数を通し、既存の行を変える関数はどれも更新番号を必須の引数に取る。DB のトリガでは照合を強制できない (照合の条件を書き忘れた更新でも、更新番号を 1 増やせば正しく見えてしまう) ので、関数の引数の形で強制している。
- 共有リンクの設定だけは更新番号を照合しない。研究の内容の変更ではないので、照合すると、共有を切り替えただけで編集中の人の保存が 409 になってしまう。

### 衝突と入力の検査

- 409 の画面では、相手が変えた箇所を表示し、手元の入力は消さない。ページを自動で読み直すこともしない。
- 差分は、画面を開いたときの内容と今の内容から画面側で計算する。項目ごとに相手の値を採用できる。
- 項目の場所を表す文字列 (パス) は `app/admin/paths.ts` の 1 種類だけを使う。コメントの付け先、衝突の差分、取り込みの差分、プレビューの差分マークが同じ表記を使い、配列の要素は位置ではなく要素の ID で指す。並べ替えで指す先がずれないようにするためである。
- 差分に含まれるパスを全部採用すると差分は空になる。これは型では保証できないので、テストで確かめている。
- 形の合わない送信は 400、更新番号の不一致は 409 を返す。項目定義に無いキー、型の違う値、別の語彙の値は、フォームからは送られない入力なので 400 にする。
- 項目の状態を「未確定」などに切り替えても、入力途中の値は画面に残る。保存の時点で状態が値以外なら、その値は保存しない。
- 「未翻訳」は利用者が選ぶ状態ではなく、値から自動的に決まる ([data-model.md](data-model.md))。
- 空の数値欄は、項目の値ごと保存しない。数値には「空の値」が無いためである。

## 編集画面と公開ページ

編集画面では、フォームの隣にその下書きの公開ページを表示する。

- 公開ページの表示には、公開サイトやプレビューと同じ関数を使う。表示の方法を増やさないためである。
- フォームの欄は、どれも公開ページか一覧の行のどこかに表示される。公開ページに出さない値 (ORCID、メールアドレス、住所) は研究の内容に入れない。
- 未確定の欄や空の節も、見出しと場所を残して表示する。下書きを埋める人が、どこを埋めればよいか分かるようにするためである。
- データセットの項目のキーは項目定義から選ぶ。編集画面で新しいキーを作ることはできない。
- 語彙の欄は、語彙の大きさにかかわらず同じ形で、入力した文字列をサーバーに送って候補を受け取る。
- 疾患の欄は ICD10 のコードを入力しても選んでもよい。分類に無いコードには、末尾を削った上位のコードを候補に出す。疾患の呼称の欄には候補を出さない。

## 取り込み

取り込みは、他の内容と今の下書きを比べ、違う項目ごとに入れる値を人が決める操作である。

- 取り込み元は 3 種類ある。この研究の公開済みバージョン、同じ研究の他の下書き、データ提供申請の枝番である。取り込み先の下書き自身は取り込み元に選べず、サーバーも拒否する。
- 取り込み元は下書きと同じ形に変換してから比べ、違う項目だけを表示する。各項目は「現在の下書き」「取り込み元」「保存する値」の 3 行で表示し、保存する値は自由に書き換えられる。どちらでもない値を書くことがあるので、2 つから選ぶだけの形にはしない。
- 保存する値の初期値は取り込み元の値にする。ただし取り込み元が空の項目は、下書きの値を初期値にする。取り込み元が空であることは「空にせよ」という意味ではないためである。
- 配列は要素ごとに残すかどうかを選び、初期値は両方の要素を残す。
- データセットの一覧と並び順は取り込まない。どのデータセットを公開するかは研究側で決めるためである。
- 取り込みを始める前に下書きを保存させる。確定は通常の保存と同じ検査と更新番号の照合を通る。
- 公開のときに取り込み元の値を自動で混ぜることはしない。提供者がプレビューで確認した内容をそのまま公開するためである。

## 申請から研究を作る

研究の内容は申請書に、データセットの ID は申請管理システムや DDBJ Search に既にある。手で入力し直さずに、そこから値を読んで下書きを作れる。

- 入力は 3 種類ある。J-DS の承認済みの枝番からは研究の内容と登録済みの JGAD のデータセットを、JGAD からはデータセット 1 件を (いずれも申請管理システムの DB から)、DRA の submission からはデータセット 1 件を (DDBJ Search から) 作る。
- 入力の単位は J-DS の枝番である。枝番 1 つが登録 1 回に当たり、研究 ID が付くのも承認された枝番である。承認のあとからデータセットが追加されるので、同じ枝番から何度でも取り込める。
- 外部システムはその都度直接読み、ポータル内のキャッシュは使わない。キャッシュには公開済みのものしか入っていないためである。確認画面と作成で 2 回読み、画面からは「何を作るか」だけを送る。
- 下書きに入れるのは、公開ページに出る値だけである。研究題目・目的・方法・対象と、研究代表者の氏名と所属を入れ、連絡先・研究分担者・関連論文は入れない。
- データセットは 1 accession につき 1 件作る。解析手法は、JGAD からは 1 件、DRA の submission からはライブラリの strategy ごとに 1 件作る。この研究に既に登録済みのデータセットは作らない。
- 語彙の値は、コードで、見つからなければ英語の表示名で照合する。新しい語彙の値は作らない。疾患はコードだけを入れ、呼称は admin が書く。申請に書かれていたのに照合できなかった値は、その欄へのコメントとして残す。
- データセットの ID は作成と同時に割り当てる。そのため、この操作には `edit-content` と `manage-labels` の両方の権限が要る。研究 ID は外部システム側に既にあるときだけ割り当てる。研究 ID と J-DS の対応の正本は申請管理システムであり、ポータルからは書き込まない。
- 取得できなかったものがあれば一覧で示した上で作成させる。下書きは後から削除できるためである。申請管理システムに接続できない環境でもボタンは表示し、接続できないことを画面に表示する。

## レビュー (共有リンクとコメント)

レビューでは、admin が提供者に共有リンクを渡し、提供者がプレビューを読んでコメントを書く。

- 共有リンクは下書きごとに 1 つで、リンクを知っている人は誰でもプレビューを読んでコメントを書ける。人ごとのリンクは作らない。
- 承認の状態は無い。レビューは状態ではなく作業であり、「レビュー中は編集できない」とすると、コメントを受けて直す作業そのものが止まってしまうためである。
- 提供者は、コメントを書き終えたときと、修正を確認して直すところが無くなったときに、それぞれボタンを押す。押すたびに記録が残り、admin の画面に表示される。これは承認ではなく、公開するかどうかは admin が決める。「確認してください」という連絡は人がメールで送り、システムからメールは送らない。

### 共有リンク

- 共有は「共有中」と「共有停止」の 2 つの状態で、既定では期限が無い。期限を設定すると、その日の終わり (日本時間) まで有効になる。
- 共有を止めてから再開すると、同じ URL がまた使える。漏れたリンクを無効にするには、URL を再発行する。
- トークンの検証は、ページではなくデータを取得する処理で行う。停止中・期限切れ・再発行前のトークンには、存在しないリンクと同じ 404 を返し、下書きがあることを知らせない。
- 応答に `X-Robots-Tag: noindex, nofollow` と `Referrer-Policy: no-referrer` を付ける。ログイン不要の URL で未公開の内容を見せるので、検索エンジンと Referer からの漏れを防ぐためである。
- プレビューは公開ページと同じ部品と同じ表示データで描く。違いは未確定の欄の扱いだけで、提供者への問い合わせ (「ご教示ください」) として表示する。
- 公開済みバージョンがあれば、プレビューと編集画面の公開ページは、比較先 (最新の公開バージョン、更新の下書きなら更新元のバージョン) と違う箇所にマークを付ける。フォーム側にはマークを付けない。取り込んだあとに書き直した欄に、いつまでも「違う」と表示され続けるためである。

### コメント

- コメントの付け先は、研究の内容またはデータセットの欄と、下書き全体である。文中の範囲を指定するコメントは無い。admin だけのメモは別の付け先で、共有リンクからは読めず書けない。
- 付け先の欄が研究の内容に実在するかをサーバーで確かめる。共有リンクから書けるのは、その下書きに含まれるデータセットまでである。
- 共有リンクで読めるコメントは、表示しているページの付け先のものに絞り、それ以外はデータ取得の結果にも含めない。SSR の HTML に埋め込まれるデータは、リンクを知っている人なら誰でも読めるためである。
- 返信の機能は無く、同じ場所のコメントは書かれた順に並ぶ。解決はコメントごとに人が付け、付け先の値を編集しても自動では解決しない。
- 解決と削除ができるのは `edit-content` 権限のある admin だけである。削除は元に戻せない。提供者は自分のコメントでも削除できない。名前は自己申告で、本人であることを確かめられないためである。
- 名前は必須である。ログインしていればアカウントの名前を使い、していなければ入力した名前の後ろに `(anonymous)` を付けて表示する。
- コメントは下書きに属する。下書きが消えると一緒に消え、共有の期限が切れても消えない。
- 未解決のコメントを場所ごとに並べる画面 (研究の内容とデータセットの編集画面のダイアログ、レビューと共有、公開前の確認) は、場所を同じ名前で呼ぶ。名前は、編集画面の公開ページのペインでその場所に行き着くまでの見出しを大きい方から ` / ` でつないだもので、先頭は研究の hum ID かデータセット ID である。例: `hum0034 / 研究概要 / 目的`、`JGAD000001 / 解析手法 1 (RNA-seq) / プラットフォーム`。
  - 表の行になる要素 (提供者、研究プロジェクト、助成金、関連論文) は `行2 (日本医療研究開発…)` のように、1 から数えた行の番号と、表の 1 列目の値の先頭 10 文字で呼ぶ。1 列目が空なら `行2 (未入力)` である。値だけでは同じ機関の助成金を見分けられないため、番号を付ける。
  - 解析手法は、データセットのページで上から数えた番号と名前の先頭 10 文字で `解析手法 2 (WES)` と呼び、名前が空なら `解析手法 2 (未入力)` である。1 つのデータセットに同じ名前の解析手法が並ぶことがあるため、番号を付ける。名前そのものへのコメントは `JGAD000001 / 解析手法 2 (WES)` になる。
  - ID が未発行なら、研究は `研究 (ID 未発行)`、データセットは研究のデータセットの表と同じ番号で `データセット ID 3 (ID 未発行)` と呼ぶ。
  - コメントのあとで行・解析手法・データセットが削除されていれば、その部分は `削除済み`・`解析手法 (削除済み)`・`データセット (削除済み)` になる。コメントは付け先が消えても残るためである。

## やっていないこと

- 編集のロックや、開いている人の表示。衝突は保存時の照合と差分表示で扱う。開いている人の数は遅れて表示されるので、当てにならない。
- 自動保存と、下書きを元に戻す機能。409 のときも入力はフォームに残る。
- 公開時の自動マージ。提供者が確認した内容と違うものが公開されてしまう。
- 承認のワークフロー、コメントの返信、文中の範囲へのコメント、通知メール。
- 人ごとの共有リンク。誰が読んだかは、コメントに書かれた名前で分かる。
- 取り込みで語彙の値や項目定義のキーを作ること。入力された文字列がそのまま項目定義に加わると、キーの表記揺れが生まれる。
- JavaScript を使わない編集フォーム。状態の切り替え、並べ替え、409 のときの値の採用は、どれも画面内の操作である。
