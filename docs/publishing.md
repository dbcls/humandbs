# 公開

下書きを公開してバージョンにする操作と、公開中のバージョンを取り下げて下書きに戻す操作の決まりをまとめる。バージョン番号、公開前の確認、ID の割り当て、削除、操作の記録、Slack への通知の決まりもここに書く。下書きの書き方と公開中のバージョンの更新は [editing.md](editing.md)、保存形式と不変条件は [data-model.md](data-model.md)、ファイルの公開は [files.md](files.md) にある。検索用の行・未確定などの語の意味は [concepts.md](concepts.md) を参照する。

## バージョン番号

バージョン番号は、admin が公開の操作のときに決める。アプリは、内容が変わっても自動でバージョンを作らない。

- admin は、その研究の公開中のバージョンが使っていない 1 以上の整数を番号に選ぶ。番号の入力欄の初期値は、その研究にいまあるバージョンの最大の番号に 1 を足した値である。取り下げで空いた番号も選べる。
- アプリは、番号が連続することを保証しない。コードには、番号が連続していることを前提にした判定を書かない。バージョンが公開されているかどうかは、DB にバージョンの行があるかどうかで決まる。
- 公開中のバージョンの番号は選べない。公開中のバージョンを同じ番号のまま公開し直す方法は、公開中のバージョンの更新だけである。
- 更新を公開するとき、アプリは、下書きの削除、更新元のバージョンの行の削除、同じ番号の行の作成を 1 つのトランザクションで行う。そのため、同じ番号のバージョンの内容が 2 つある瞬間も、バージョンが公開ページから消える瞬間も無い。
- 更新を公開するとき、研究の内容・データセットの内容・データセットの順・公開日のどれも更新元のバージョンから変わっていなければ、アプリはエラーにする。公開しても公開ページが変わらないためである。
- 公開・更新・取り下げのどの操作でも、アプリはバージョンの行の内容を書き換えない。公開すると新しい行ができる。更新すると、更新元のバージョンの行が消えて、同じ番号の行ができる。取り下げると、バージョンの行が下書きに移る。公開中のバージョンの行の内容が変わるのは、画面から語彙の値を統合したときだけである ([catalog.md](catalog.md) の「画面から編集できる語彙」)。
- 公開日は、バージョンに書く日付であり、公開の予約ではない。公開日に未来の日付を入れても、admin が公開のボタンを押した時点で公開される。公開を予約する機能は無い。

### 1 回の公開で行うこと

admin が公開のボタンを押すと、アプリは 1 つのトランザクションで次の処理を行う。公開前の確認の検査をする。研究の内容とデータセットの内容をバージョンにまとめ、番号を付ける。操作の記録を書く。下書きを消す。その研究の検索用の行を作り直す。

- 同じ研究の公開は、1 つずつ順に進む。アプリは公開を進める前に、下書きと研究と研究のデータセットをロックし、研究とデータセットの ID の割り当てもロックする。そのため、同じ研究で同じ番号の公開が同時に 2 つ行われると、後から進んだ公開は、番号が使われているというエラーになる。
- バージョンに載せるデータセットは、研究の公開済みのデータセットと、この下書きで作成したデータセットである。並び順は、下書きのデータセットの並び順に従う。他の下書きで作成してまだ公開していないデータセットは載せない。
- 各データセットの内容は、この下書きで編集した内容があれば、その内容を使う。編集した内容が無ければ、公開中の内容を引き継ぐ。引き継ぐのは、更新ならば更新元のバージョンの内容である。更新でないときと、更新元のバージョンにそのデータセットが無いときは、そのデータセットを載せている最新のバージョンの内容を引き継ぐ。編集していないデータセットを空の内容として公開すると、何も直していない下書きを公開しただけで、公開済みのデータセットの内容が消えてしまうためである。
- 公開した内容がどこにも無く、この下書きでも編集していないデータセットだけは、空の内容で公開される。この下書きで作成して、まだ一度も編集していないデータセットが該当する。
- 下書きで作成したデータセットは、公開した時点で、作成した下書きではなく研究に属するものになる。公開したあとは、研究のどの下書きを削除しても、そのデータセットは消えない。
- アプリは、公開のときに取り込み元の値を自動で混ぜない ([editing.md](editing.md))。

## 公開前の確認

公開前の確認は、下書きを公開してよいかを検査する手順である。検査には、公開を止める検査と、admin が確認すれば通せる検査の 2 種類がある。

- アプリは、公開前の確認の画面を表示するときと、公開の操作のときの両方で検査する。最終的な判定は、公開の操作のときの検査で決まる。公開の操作では、下書きの行をロックしたまま検査する。そのため、admin が画面を見てから公開のボタンを押すまでのあいだに何が起きても、公開の操作では、アプリは古い検査結果で判定しない。
- 公開を止める検査は、ID が揃っているかどうかの検査である。研究に研究 ID が無いときと、バージョンに載せるデータセットに primary のデータセット ID が無いときは、admin が確認しても公開できない。
- 確認すれば通せる検査は、内容が未完成かどうかと、申請管理システムとの食い違いの検査である。アプリは、見つかったものを一覧に表示する。admin は一覧を確認して通す。アプリは、admin が通したことを、種類ごとの件数と一緒に操作の記録に残す。
- 一覧に表示するものは次のとおりである。
  - 未確定の値 (欄と言語ごと)
  - 未翻訳
  - 内容の無いデータセット
  - データセットに紐づけたファイルのうち、非公開のもの
  - 公開するバージョンのどのデータセットにも紐づけておらず、研究のページにも表示していないファイル
  - 申請管理システムのキャッシュに無い JGAD と JGAS の ID と、キャッシュでは別の研究 ID に対応している JGAD と JGAS の ID
- 1 つの不足を、未翻訳と未確定の両方として 2 度表示することはない。
- admin は、非公開のファイルを、公開前の確認の画面でまとめて公開に切り替えられる。アプリは、切り替えのジョブの完了を公開の条件にしない。
- 申請管理システムとの食い違いがあっても、アプリは公開を止めない。申請管理システムの値にも入力の誤りがあり、食い違いで公開を止めると、申請管理システムの値が誤っているあいだ、admin が研究を公開できなくなるためである。
- レビューの状態によっても、アプリは公開を止めない。共有中かどうか、未解決のコメント、提供者が押したボタンは、admin が判断するための情報である。公開するかどうかは admin が決める。

## ID の割り当て

admin は、研究 ID を研究の画面で、データセット ID をそのデータセットの画面で割り当てる。公開前の確認の画面では、ID が無い研究やデータセットに primary の ID を 1 つ割り当てることだけができる。ID の意味と一意性の決まりは [data-model.md](data-model.md) にある。

- admin が ID を割り当てると、下書きを保存しなくても公開しなくても、その時点で ID が有効になる。アプリは、ID を割り当てたときと解除したときに、その研究の検索用の行を作り直す。
- 研究 ID は、`hum` と 4 桁の数字の形でなければ割り当てられない。研究 ID が、公開ページの URL と、公開の bucket の研究ごとの prefix に使われるためである。
- primary の ID を付け替えると、前の primary の ID は secondary の ID として残る。1 つの研究やデータセットに複数の ID を割り当てられるようにしているのは、古い ID で参照されても同じ研究やデータセットにたどり着けるようにするためである。
- アプリは、既に使われている ID の割り当てを拒否する。secondary の ID として使われている ID も拒否する。
- 外部のアーカイブに登録しないデータセットには、admin が NHA ID を発行する。ID の入力欄に入力できるのは外部のアーカイブの accession だけで、アプリは NHA ID の形の文字列を拒否する。画面には次に発行する番号を表示するが、アプリは admin が発行の操作をした時点で番号を読み直す。そのため、発行される番号が画面の表示と違うことがある。
- データセット ID を解除したデータセットは、解除した時点で、公開中のバージョンのデータセットの一覧から消える。アプリはバージョンの行の内容を書き換えない。
- 研究 ID を付け替えると、アプリは公開の bucket の研究ごとの prefix を移動する。付け替えたあとも、元の研究 ID は secondary の ID として残る。admin は、移動が終わるまで元の研究 ID を解除できない ([files.md](files.md))。

## 取り下げと削除

取り下げは、admin がバージョンから番号を外して下書きに戻す操作である。取り下げたバージョンは、公開ページ・検索・JSON API から見えなくなる。「取り下げ済み」という状態も表示も無い。

- 取り下げたバージョンの内容は、そのまま下書きの内容になる。アプリは公開していた内容を別に保存しない。何が起きたかは操作の記録に残る。
- 更新中のバージョンは取り下げられない ([editing.md](editing.md) の「公開中のバージョンの更新」)。

### 操作ごとに消えるもの

どの操作も行を移すか消すだけで、コピーは作らない。そのため、同じ内容が 2 か所に残ることはない。

- 下書きの削除: 下書き、下書きの中のデータセットの内容、コメント、提供者が押したボタンの記録、共有リンク、その下書きで作成したデータセット (データセットの ID の割り当てを含む) が消える。公開ページ・検索・JSON API に表示される内容は変わらない。
- 下書きの公開: 下書きの削除と同じものが消える。ただし、その下書きで作成したデータセットは、バージョンに載って残る。
- 更新の公開: 下書きと更新元のバージョンの行が消え、同じ番号のバージョンは新しい行の 1 つだけになる。公開ページには、同じ URL で直した内容が表示される。
- 取り下げ: バージョンの行が下書きになり、バージョンの番号が空く。
- データセットの削除: データセットの行、ID の割り当て、下書きの中のデータセットの内容、そのデータセットに付いたコメント (どの下書きのコメントも) が消える。研究のすべての下書きで、データセットの並びと関連論文のデータセットから、そのデータセットの実体の ID が消える。下書きの保存ではその研究のデータセットしか指せないので、実体の ID が残ると、その下書きを保存できなくなるためである。アプリは、研究の検索用の行を同じトランザクションで作り直す。削除したデータセットは公開ページと一覧からその場で消えるが、バージョンの内容には当時のまま残る。他の下書きで作成したデータセットは、作成した下書きからしか削除できない。
- 研究の削除: 研究の配下のバージョン・下書き・データセットがすべて消え、ID の割り当ても解除されるので、その ID は再び割り当てられるようになる。操作の記録は残る。研究ごとの prefix にファイルが残っているあいだは、研究の削除はエラーになる ([files.md](files.md))。

## 操作の記録

アプリは、公開されているものを変えた操作と、admin の追加と削除、元に戻せない下書きの削除を、追記だけの操作の記録 (`event`) に残す。ID の割り当て表は ID の割り当てが「今どうなっているか」を表し、操作の記録は「そこに至った操作」を表す。

- 記録する操作は、公開・更新・取り下げ、研究とデータセットの削除、ID の割り当てと解除、ファイルの公開・非公開・削除、公開中のファイルのラベルの変更、公開中のファイルの研究ページへの表示と表示の解除、記事・お知らせ・アラートの公開の切り替え、admin の追加と削除、下書きの削除、公開前の確認を通したこと、語彙の値の統合である。記録する操作の一覧は `app/db/schema/audit.ts` にある。
- 下書きの削除を記録するのは、下書きの削除は元に戻せず、何が消えたかをあとから調べられるようにするためである。
- ファイルの操作を記録するのは、ファイルの公開状態の正本がファイルストアにあり、Postgres にはファイルの履歴が残らないためである。
- 記録しない操作は、ログイン、研究ごとの prefix (非公開の bucket) へのアップロード、統合以外の項目定義と語彙の変更である。項目定義と語彙は定義であり、公開されているものではないためである。語彙の値の統合だけは、公開中のバージョンの行の内容を書き換えるので記録する。
- 1 回の公開で、アプリは複数の記録を書く。バージョンに 1 つ、内容が変わったデータセットごとに 1 つ、公開前の確認を通したときはさらに 1 つである。データセットの内容がいつ、どの公開で変わったかを、バージョンをまたいで調べられるようにするためである。
- 操作の記録には、対象の行への外部キーを張らない。研究を削除しても、操作の記録が残るようにするためである。
- アプリは、操作の記録を変更と同じトランザクションで書く。何も変えなかった操作では、何も記録しない。
- 操作の記録が追記だけであることは、DB の role で保証する。schema の owner の role と、アプリが接続する role を分け、アプリが接続する role には `event` に対して INSERT と SELECT だけを与える。アプリが接続する role には、どの表にも権限を ALL ではなく 1 つずつ与えるので、アプリはどの表も TRUNCATE できない。
- DB に直接 SQL を実行して変えた内容が操作の記録に残らないことは、前提として受け入れている。
- 管理画面のトップの「操作の記録」に、操作の記録を新しい順に表示する。操作の種類・操作者・日付で絞り込める。画面から操作の記録を変えることも消すこともできない。
- 「操作の記録」の一覧には、対象を今の名前で表示する。対象が消えていれば、記録に書いた名前を表示する。記録にも名前が無ければ「削除済み」と表示する。対象が消えたあとも何が対象だったか分かるように、アプリは、お知らせの記録には題名を、アラートの記録には本文の先頭 40 字を書いておく。統合した語彙の値は統合のあとで消えるので、アプリは、語彙の値の統合の記録に統合元と統合先の表示名を書いておく。一覧には、統合の対象を、統合した時点の表示名で「統合元 → 統合先」と表示する。

## Slack への通知

アプリは、レビューで提供者が書いたコメントと押したボタン、研究の公開、記事・お知らせ・アラートの公開を、Slack のチャンネルに知らせる。admin が管理画面を開かなくても、提供者の反応と公開に気づけるようにするためである。

- 送るのは、共有リンクから書かれたコメント、提供者が押すボタン、研究の公開と更新の公開、記事・お知らせ・アラートの公開である。提供者が押すボタンは、コメントを書き終えたときに押すボタンと、直すところが無いときに押すボタンの 2 つである。取り下げ・削除・ID の割り当て・ファイルの操作・非公開への切り替えは送らない。
- admin が書いたコメントと、データの移行で作成したコメントは送らない。アプリは、書いた人が admin かどうかを、Slack に送る時点で調べる。共有リンクから書いたコメントでも、書いた人がその時点で admin ならば送らない。ボタンも同じ方法で調べ、admin が押したボタンは送らない。
- アプリは、決まった間隔ごとに、その間隔のあいだに起きたことを 1 通にまとめて送る。何も起きていなければ送らない。1 件ごとに送ると多すぎるためである。
- 間隔は `.env` の `HUMANDBS_SLACK_INTERVAL_MINUTES` (分、既定は 60) で決まり、区切りは JST の 0 時から数える。60 ならば、毎時 0 分の区切りまでの 1 時間に起きたことを 1 通にする。毎日同じ時刻に区切るため、1 日の長さを分で表した数 (1440) の約数でない値では、アプリは起動しない。
- アプリは、区切りの時刻から 1 分たってから送る (60 ならば毎時 1 分ごろ)。コメントなどの行に書かれた時刻が区切りより前でも、その行を書いている途中のトランザクションが区切りのあとに確定することがある。1 分待てば、区切りより前の時刻の行を必ず読めるためである。
- コメントについては、下書きごとに件数と書いた人の名前だけを送り、コメントの本文と場所は送らない。admin にはコメントが付いたことが分かれば足りるうえ、コメントの本文を Slack に残さないためである。ボタンについては、ボタンの種類ごとに押された回数を送る。コメントとボタンの通知には、その下書きの「レビューと共有」の画面へのリンクを付ける。
- 書いた人の名前は、下書きごとに 10 人まで並べ、11 人目からは「ほか N 人」とまとめる。共有リンクを知っている人は名前を自由に入力できるので、名前はいくらでも増える。すべて並べると Slack がメッセージの長さを理由に拒否し、そのメッセージもあとに続くメッセージも送れなくなるためである。
- 研究の公開の通知では、研究 ID とバージョン番号と公開した admin の名前を送り、そのバージョンの公開ページへのリンクを付ける。
- 記事・お知らせ・アラートの公開の通知では、記事・お知らせ・アラートを、管理画面のトップの「操作の記録」の一覧と同じ名前で表示する。記事とお知らせは言語ごとに公開するので、同じ人が公開した言語を 1 行にまとめ、言語ごとにその言語の公開ページへのリンクを付ける (`記事「about」 ja / en`)。アラートはどのページにも表示されるので、トップページへのリンクを付ける。
- 通知を送るのはアプリのプロセスで、通知の処理は公開などの操作とは別に動く。Slack が止まっていても操作は成功し、アプリは送れなかったものを次の回にまとめて送る。アプリはどこまで送ったかを DB に記録するので、再起動をはさんでも同じものを 2 度送らない。
- 送り先は、`.env` の `HUMANDBS_SLACK_WEBHOOK_URL` (Incoming Webhook の URL) である。`HUMANDBS_SLACK_WEBHOOK_URL` が空のあいだ、アプリは通知を送らない。空のあいだに起きたことは、あとで URL を設定しても送らない。

## やっていないこと

- 取り下げや更新で消えたバージョンの内容を、履歴として別に残すこと。バージョンは現在公開している内容で、履歴ではない。何が起きたかは操作の記録に残る。
- 他の下書きの公開でデータセットが変わったかどうかを検査すること。並行する 2 つの下書きで同じデータセットを編集すると、後から公開した下書きの内容で公開される。先に公開した内容は先のバージョンに残る。並行する下書きが同じデータセットを別の内容で書けることは仕様である ([editing.md](editing.md))。
