# 公開

draft を版にする操作と、それを取り消す操作。書く側は [editing.md](editing.md)、モデルの側の不変条件は
[data-model.md](data-model.md)、誰が何を許されるかは [auth.md](auth.md)。

## 公開の確認画面 (`…/draft/:draftId/publish`)

公開の入口はこの 1 枚で、読むための画面として作る。**直すのは元の画面に戻ってやる** — 唯一の例外が
ラベルの pin で、それは公開を止めているものであり、編集ではなく 1 つの値を入れる操作だから。

上から順に、公開できない理由 / 何を公開するか / 確認して通すもの / 何が変わるか。**公開できない理由が
先に来る**のは、pin が自分の form を持つため (form は入れ子にできない) でもある。

- **何を公開するか** — 新しい版として出すか、いまの版を差し替えるか。公開日は既定が今日で、admin が
  変えられる。差し替えは、この draft が版から作られているときだけ選べる
- **確認して通すもの** — 種類ごとにまとめ、その中を「どの画面で直せるか」で並べる。12 件を 12 行
  並べる代わりに「未確定の値 12 / 研究の記述 12」と出して、そこから編集画面へ行く
- **何が変わるか** — 研究の記述が何項目、どの dataset の記述が何項目、掲載の増減。dataset には
  **「この記述は N 件の公開版に効く」を必ず添える** (dataset は版を持たないので、直すと参照している
  全公開版の見え方が変わる)

## 版を切ることと fix

**版を切るのは編集者の明示的な操作**で、内容の変化から自動判定しない。**公開版番号は公開時に確定する**
ので、公開しなかった draft に由来する欠番が生じない。**次の番号は発行済みの最大 + 1** で、取り下げた版も
発行済みに数える。これは採番の規則であって、番号の連続性は保証しない。

**fix は版番号を増やさない。** 差し替えるのは **draft が派生した版**で、任意の版を選ばせない。効果範囲が
2 種類に分かれるので、モデルと event も分ける (UI では 1 つの操作に見せてよい)。

| fix の対象 | スコープ | 効果 |
|---|---|---|
| research content | その版 | 公開版が指す ContentSnapshot を差し替える |
| experiment / dataset content | identity | 参照している全公開版に効く |

**fix で差し替える前の公開内容は、外部から参照可能にしない。** 差し替え前の ContentSnapshot は行として
残るが、どの版もそれを指さなくなる。dataset content の側は上書きで、置き換えられた値は証跡に残る
([data-model.md](data-model.md) の「research / experiment / dataset」)。

**公開は 1 つのトランザクションで終わる。** 記述を書き、版を pin し、証跡を書き、draft を消費し、
検索用の行をその research のぶんだけ作り直す。**「公開したがまだ検索に出ていない」という状態は存在
しない。**

**公開する dataset の範囲は「その版が載せているもの」。** 載せていて誰も記述していない dataset は、
ゲートを通した上で空の記述として公開される — 載っているのに存在しない dataset を作らないため。

## 公開ゲート

検査は 2 種類に分かれる。

**公開を止める検査。** ラベルと関連の構造が揃っていないものは公開できない。確認では超えられない。

- research に hum ラベルが pin されている
- その版が持つ全 dataset に dataset id が pin されている

**列挙して通す検査。** 内容の未完成と上流との食い違いは公開を止めない。未解決を並べて admin が明示的に
通す形にし、**通した記録は証跡に残す** (件数の内訳だけを残す — どの field だったかは、その公開が書いた
スナップショットから読める)。

- 未確定 (unknown) とマークされた値
- 翻訳対 field の未翻訳
- content が空の dataset
- 直前の公開版が載せていて、この版が載せていない dataset
- 編集を始めてから、別の公開がその dataset の記述を変えたもの
- dataset が選択したファイルのうち非公開のもの
- hum ラベルと dataset id の対応が、JGA 申請管理システム由来のキャッシュと合わないもの

**dataset が版から落ちることを列挙するのは、それが記事の書き漏れとして実際に起きているため。** 移行元の
データには、同じ dataset が版をまたいで出たり入ったりしている研究がある。一方で登録先を BioProject から
JGA へ移した正当な入れ替えも同じ形で現れ、**両者を区別する規則は無い**。だから止めずに列挙する。

**状態は言語ごとに立つ**ので ([data-model.md](data-model.md) の「値の状態」)、未確定の列挙は
(field, 言語) の単位になる。未翻訳は「両方の言語が値を持ち、片方だけが空」のときだけ立ち、状態が
食い違うときは未確定として数える。**同じ 1 つの欠けが 2 行になることはない。**

**ファイルの列挙は「まとめて公開する」の入口を兼ねる。** ファイルの公開は research の公開とは独立した
操作で、切り替えは実バイトコピーの job になる。列挙されたものをその場でまとめて公開に倒せる形にし、
公開操作そのものは待たせない。

**上流との検算の対象は JGAD / JGAS に限る。** 申請管理システムが hum と JGAD / JGAS の対応の master
なので、そこに無い対応を pin しているのは疑わしい状態であり、不在も食い違いと同じく列挙する。上流には
typo や版違いでの食い違いの実績があるので、**上流を公開を止める側に置かない。**

**キャッシュが一度も取れていない間は、この検算を行わない。** 空を「上流に無い」と読むと全 dataset が
並び、列挙そのものが読まれなくなる。

**ゲートは画面と公開操作の両方で走る。** 画面が出すのは助言で、通してよいかを決めるのは書き込み側 —
draft の行を掴んだまま検査するので、画面を見てからの数秒に何が起きても判断が古くならない。

## ラベルを pin する

hum ラベルと dataset id は research の画面で管理する。公開の確認画面から打てるのは、まだ pin されて
いないものを 1 つ入れることだけ。

- **pin した時点で台帳に載る** ([data-model.md](data-model.md) の「identity と label」)
- **primary にすると、それまで primary だったラベルは secondary になる。** 旧いラベルが解決し続けるのが
  複数持てることの目的なので、付け替えは消すことではない
- **既に使われているラベルは弾く。** primary と secondary を合わせて一意
- **公開実績のあるラベルを別の identity に付け替えるときは警告を出す。** 止めはしないが、外部からの
  リンクが黙って別物を指す
- **外部アーカイブに登録しない dataset には `hum{NNNN}-NHA{nnn}` を提案する。** 提案であって規則では
  ないので、そのまま採ってもよいし書き換えてもよい。番号はその hum の中の通し番号で、飛んでも困らない
- **pin を外した dataset は、その時点で公開版の一覧から落ちる。** 落とすのは検索用の行で、
  ContentSnapshot は書き換えない — 版が載せた identity の列は当時の事実であり、いま何が見えるかは
  検索用の行が決める

## 取り下げと再公開

状態遷移は公開・取り下げ・再公開の 3 つで、取り下げと再公開は版の公開状態の切り替えとして表現する。
専用の状態を増やさない。

**取り下げは UI 上は単に見えなくなる。** データは残るので復旧できる。可視性は検索用の行から決まるので、
取り下げは「公開分を作り直したらそこに居ない」の結果として起きる。

**すでにそうなっている操作は何も書かない。** 公開中の版を再公開しても、行も証跡も動かない。

## 破棄と削除

| 操作 | データ | 外から見た挙動 |
|---|---|---|
| draft の破棄 | 関連ごと消える。draft が新規に作った dataset identity も消える | 元から見えていない |
| draft の公開 | draft は消える。作った dataset のうち版に載せたものは残り、載せなかったものは一緒に消える | 版として見えるようになる |
| 版の取り下げ | 残る。pin も台帳に残る | 見えなくなる。再公開できる |
| research の削除 | 配下の dataset / experiment ごと消える。hum ラベルと dataset id の pin も外れる。event は残る | 見えなくなる。どちらのラベルも再 pin できる |

draft の破棄で消えるのは、draft 本体・変更エントリ・undo・presence・コメント・共有リンク・その draft が
新規に追加した dataset の identity。既存の dataset に対する編集は変更エントリが消えるだけで、identity も
pin も動かない。

## 証跡

**公開・取り下げ・fix・削除・pin 操作・ファイルの公開状態の切り替え・admin の付け外しを append-only の
event として記録する。** pin 台帳が「いまどうなっているか」を持ち、event が「そこに至った操作」を持つ。
公開ゲートを通した記録もここに入る。ファイルを含めるのは、公開状態の master が S3 側にあって Postgres に
履歴が残らないため。draft の破棄も記録する — draft 本体は何も残さずに消えるので、消えたことを言えるのが
event だけになる。

**1 回の公開が書く event は 1 つではない。** 版に 1 つ、記述が実際に変わった dataset ごとに 1 つ、ゲートを
通したなら 1 つ。dataset を別に書くのは、その記述が版ではなく identity のものだから — 「この dataset は
いつ何によって変わったか」に答えられる形にしておく。

- **event は subject に外部キーを張らない。** research を削除しても、そこに至った操作の記録は残る
- **append-only は DB のロールで担保する。** schema を作る owner と、アプリが繋ぐ role を分け、アプリ側に
  event への UPDATE と DELETE を与えない。アプリ側の規律にもトリガにも頼らない — トリガを迂回できる権限が
  あれば、トリガ自身の記録も直せる。**副産物としてアプリはどのテーブルも TRUNCATE できない**ので、DB を
  空にする経路は owner に閉じる。公開が書き残す旧 dataset content も同じ扱いにする
- **記録は変更と同じトランザクションで書く。** 何も変えなかった操作は何も記録しない
- **ログインは記録しない。** 記録するのは公開されているものを変えた操作で、主体は event ごとに焼かれる
- **DB への直接の SQL を緊急避難の経路として残すなら、その分は event に載らないことを前提にする**

## 意図的にやっていないこと

| やらないこと | 理由 |
|---|---|
| 公開時に相手の変更を自動で混ぜること | draft は共有リンクが見せている姿そのもの。混ぜると承認された姿と違うものが出る |
| 任意の版を選んで fix すること | 訂正は draft が派生した版に対して起きる。選ばせると、どの版を直したのか分からない操作が作れる |
| 版番号の連続性を保証すること | 採番は台帳から導く規則で、可視性は公開状態から決まる。連続性に依存する判定を作らない |
| 公開の予約 | いま公開するかしないかの操作だけを持つ。日付は版の属性であって実行の引き金ではない |
| 取り下げた版に「取り下げ済み」と表示すること | 旧 Joomla では痕跡なく消えていた。データは残るが、外から見える形は変えない |
| 上流の食い違いで公開を止めること | 上流に typo の実績があり、上流が誤っている間ポータルが公開できなくなる |
