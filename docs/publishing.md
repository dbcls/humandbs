# 公開

下書きを公開してバージョンにする操作と、それを取り消す操作の決まりをまとめる。下書きの書き方と公開中のバージョンの更新は [editing.md](editing.md)、保存の形と不変条件は [data-model.md](data-model.md)、ファイルの公開は [files.md](files.md) にある。語の意味は [concepts.md](concepts.md) を参照する。

## バージョン番号

バージョン番号は、公開の操作のときに admin が決める。内容の変化から自動でバージョンを作ることはない。

- 番号には、公開中のバージョンが使っていない 1 以上の整数を選ぶ。初期値は今ある最大の番号の次で、取り下げで空いた番号も選べる。
- 番号の連続性は保証せず、連続性に頼る判定も作らない。
- 公開中のバージョンの番号は選べない。同じ番号で再公開する方法は、公開中のバージョンの更新だけである。
- 更新の公開は、下書きを消し、前のバージョンの行を消し、同じ番号の行を作るまでを 1 つのトランザクションで行う。バージョンの内容が 2 つある瞬間も、公開ページから消える瞬間も無い。
- 研究の内容・データセットの内容・データセットの順・公開日のどれも変わらない更新はエラーにする。公開しても公開ページが変わらないためである。
- 公開・更新・取り下げは、バージョンの行の内容を書き換えない。公開は常に新しい行を作り、更新は前の行を消して作り直し、取り下げは行を下書きに移す。公開中のバージョンの行の内容が変わるのは、語彙の値の統合のときだけである ([data-model.md](data-model.md))。
- 公開日は予約ではない。バージョンに書く日付で、未来の日付でも、押した時点で公開される。

### 1 回の公開で行うこと

公開は 1 つのトランザクションで終わる。公開前の確認をし、研究の内容とデータセットの内容をバージョンにまとめ、番号を付け、操作の記録を書き、下書きを消し、その研究の検索用の行を作り直す。

- 公開は研究ごとに直列になる。下書き・研究・そのデータセット・その ID の割り当てをロックしてから進むので、同じ番号の公開が同時に 2 つ来ると、後の方は番号が使えないとしてエラーになる。
- 載せるデータセットは、公開済みのものと、この下書きで作成したものである。並び順は下書きの順に従う。他の下書きで作成してまだ公開していないデータセットは載せない。
- データセットの内容は、この下書きで編集したものがあればそれを使い、無ければ公開中の内容 (更新ならば更新元のバージョン、それ以外は最新のバージョン) を引き継ぐ。編集していないものを空として公開すると、何も直していない下書きの公開が公開済みの内容を消してしまうためである。
- 公開された内容がどこにも無く、この下書きでも編集していないデータセット (この下書きで作成してまだ書いていないもの) だけが、空の内容で公開される。
- 下書きで作成したデータセットは、公開した時点で研究のものになり、以後は下書きを削除しても消えない。
- 公開のときに他の内容を自動で混ぜることはしない ([editing.md](editing.md))。

## 公開前の確認

公開前の確認は、公開してよいかを下書きについて検査する手順で、検査は 2 種類ある。

- 検査は画面と公開の操作の両方で行い、最終的な判定は公開の操作で行う。公開の操作は下書きの行をロックしたまま検査するので、画面を見てから押すまでに何が起きても判断が古くならない。
- 公開を止める検査は、ID が揃っていないものである。研究に研究 ID が無いとき、載せるデータセットに primary のデータセット ID が無いときで、確認しても通せない。
- 確認すれば通せる検査は、内容が未完成なものと申請管理システムとの食い違いである。一覧に表示し、admin が確認して通し、通した記録 (種類ごとの件数) を操作の記録に残す。
- 一覧に表示するのは、未確定の値 (欄と言語ごと)、未翻訳、内容の無いデータセット、データセットに紐づけたファイルのうち非公開のもの、JGAD と JGAS の ID が申請管理システムのキャッシュに無いか別の研究 ID に対応しているもの、である。未翻訳と同じ不足を未確定として 2 度表示しない。
- 非公開のファイルは、その画面でまとめて公開に切り替えられる。切り替えのジョブの完了は待たない。
- 申請管理システムとの食い違いでは公開を止めない。申請管理システムにも入力の誤りがあり、止めると、そちらが誤っているあいだポータルが公開できなくなるためである。
- レビューの状態でも公開を止めない。共有の有無・未解決のコメント・提供者が押したボタンは判断のための情報で、公開するかは admin が決める。

## ID の割り当て

研究 ID は研究の画面で、データセット ID はそのデータセットの画面で割り当てる。公開前の確認の画面からは、ID が無いものに primary の ID を 1 つ付けることだけができる。ID の意味と一意性の決まりは [data-model.md](data-model.md) にある。

- ID は割り当てた時点で有効になり、保存も公開も待たない。割り当てと解除は、その研究の検索用の行を作り直す。
- 研究 ID は `hum` と 4 桁の数字の形でなければ割り当てられない。公開ページの URL と、公開の bucket の研究ごとの prefix になるためである。
- primary の ID を付け替えると、前の primary の ID は secondary の ID として残る。古い ID をたどれるようにすることが、複数の ID を持てるようにしている目的である。
- 既に使われている ID は、secondary の ID として使われているものも含めて拒否する。
- 外部のアーカイブに登録しないデータセットには、NHA ID を発行する。欄に入力できるのは外部のアーカイブの accession だけで、NHA ID の形の文字列は拒否する。画面は次の番号を表示するだけで、番号は発行の操作の時点で読み直すので、表示と違う番号になることがある。
- データセット ID を外したデータセットは、その時点で公開中のバージョンの一覧から消える。バージョンの内容は書き換えない。
- 研究 ID の付け替えでは、公開の bucket の研究ごとの prefix の移動が伴う。移動が終わるまで元の研究 ID は外せない ([files.md](files.md))。

## 取り下げと削除

取り下げは、バージョンから番号を外して下書きに戻す操作である。「取り下げ済み」という状態も表示も無く、公開側からは単に見えなくなる。

- 取り下げたバージョンの内容は、そのまま下書きの内容になる。公開していた内容を別に保存することはせず、何が起きたかは操作の記録に残る。
- 更新中のバージョンは取り下げられない ([editing.md](editing.md) の「公開中のバージョンの更新」)。

## 操作ごとに消えるもの

どの操作も行が移るだけで、同じ内容が 2 か所に残らない。

- 下書きの削除: 下書き、下書きの中のデータセットの内容、コメント、共有リンク、その下書きで作成したデータセット (ID を含む) が消える。公開側は変わらない。
- 下書きの公開: 下書きが消え、その下書きで作成したデータセットはバージョンに載って残る。
- 更新の公開: 下書きと前のバージョンの行が消え、同じ番号のバージョンが 1 つ残る。同じ URL で直した内容が表示される。
- 取り下げ: バージョンの行が下書きになり、番号が空く。
- データセットの削除: データセットの行・ID の割り当て・下書きの中のデータセットの内容・そのデータセットに付いたコメント (どの下書きのものも) が消え、研究の検索用の行を同じトランザクションで作り直す。公開ページと一覧からはその場で消える。バージョンの内容は当時のまま残る。他の下書きで作成したデータセットは、その下書きからしか削除できない。
- 研究の削除: 配下のバージョン・下書き・データセットがすべて消え、ID の割り当ても外れるので、その ID は再び割り当てられる。操作の記録は残る。研究ごとの prefix にファイルが残るあいだはエラーにする ([files.md](files.md))。

## 操作の記録

公開されているものを変えた操作は、追記だけの操作の記録 (`event`) に残す。ID の割り当て表が「今どうなっているか」を、操作の記録が「そこに至った操作」を表す。

- 記録するのは、公開・更新・取り下げ、研究とデータセットの削除、ID の割り当てと解除、ファイルの公開・非公開・削除、公開中のファイルのラベルの変更、記事などの公開の切り替え、admin の追加と削除、下書きの削除、公開前の確認を通したことである。一覧は `app/db/schema/audit.ts` にある。
- ファイルを記録するのは、公開状態の正本がファイルストアにあり、Postgres に履歴が残らないためである。
- 記録しないのは、ログイン、研究ごとの prefix (非公開の bucket) へのアップロード、項目定義と語彙の変更である。項目定義と語彙は定義であり、公開されているものではないためである。
- 1 回の公開は複数の記録を書く。バージョンに 1 つ、内容が変わったデータセットごとに 1 つ、公開前の確認を通したなら 1 つである。データセットの内容がいつ何の公開で変わったかを、バージョンをまたいで調べられるようにするためである。
- 記録は対象に外部キーを張らない。研究を削除しても記録が残るようにするためである。
- 記録は、変更と同じトランザクションで書く。何も変えなかった操作は何も記録しない。
- 追記だけであることは、DB の role で保証する。schema の owner とアプリが接続する role を分け、アプリには `event` の INSERT と SELECT だけを与える。権限を 1 つずつ与えるので、アプリはどの表も TRUNCATE できない。
- DB に直接 SQL を実行した変更は記録に載らない。これは前提として受け入れている。

## やっていないこと

- 公開の予約。日付はバージョンの属性であり、実行のきっかけではない。
- 公開中のバージョンを直すあいだ、公開ページから外すこと。読者には取り下げと区別が付かない。
- 取り下げや更新で消えたバージョンの内容を残すこと。バージョンは現在公開している内容で、履歴ではない。何が起きたかは操作の記録に残る。
- 取り下げたバージョンに「取り下げ済み」と表示すること。
- バージョン番号の連続性の保証。公開されているかはバージョンの行の集合で決まる。
- 申請管理システムとの食い違いやレビューの状態で公開を止めること。
- 他の下書きの公開がデータセットを変えたかどうかの検査。公開した内容はバージョンの中にあり、他の公開がこの下書きの内容を書き換えることはない。
