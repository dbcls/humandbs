# 用語

この repo の docs とコードで使う語の意味と、語どうしの関係をまとめる。画面に出す文言 (日本語と英語) の正本は `app/i18n/messages.ts` であり、ここでは訳語を決めない。API と絞り込みに出る英語の値 (`Unrestricted-access` など) を変えないという保証は [public-api.md](public-api.md) にある。

## 研究とバージョンと下書き

ポータルが扱う単位は研究で、研究の内容は、公開したバージョンと未公開の下書きに分けて保存する。

### 研究

研究は、1 つの研究課題と、それに属するデータセットの集まりである。コード上は `research` で、この行には ID も内容も置かない。内容はバージョンと下書きに、研究 ID は ID の割り当て表に置く。研究 ID が決まる前に研究を作れるのは、申請の承認前から研究の内容を書き始め、ファイルをアップロードすることがあるためである。

### 研究とデータセットの実体

研究とデータセットの行 (`research`、`dataset`) は、外から見える ID とは別の、ポータルの中だけの同一性を表す。コード上は identity と呼ぶ。ID を直しても、実体を指す参照 (管理画面の URL、下書き、非公開のファイル) は壊れない。研究 ID は人が申請管理システムに入力する文字列で、入力の誤りの訂正が日常的に起きるので、この分け方にしている。

### バージョン

バージョンは、公開した時点の研究の内容である。コード上は `research_version` で、研究の内容と、載せた全データセットの内容を 1 つにまとめて保存する。

- バージョン番号は研究の中で一意で、公開のときに決まる ([publishing.md](publishing.md))。
- バージョンの行があることが「公開中」を意味し、公開の状態を表す列は無い。取り下げると、バージョンは下書きに戻る。
- バージョンの内容は書き換えない。直すときは、次の「公開中のバージョンの更新」を使う。

### 下書き

下書きは、研究の未公開の作業コピーである。コード上は `research_draft` で、1 つの研究に複数作れる。公開すると下書きは消えてバージョンになる。編集の決まりは [editing.md](editing.md) にある。

### 公開中のバージョンの更新

公開中のバージョンを、番号を変えずに直す操作である。直す内容はそのバージョンから作った下書きに書き、公開すると同じ番号のバージョンと入れ替わる。コード上は、下書きの `replacesVersionId` が更新元のバージョンを指す。

## データセットと解析手法

データセットは研究に属するデータの単位で、解析手法はデータセットの中でデータの作り方を書く要素である。

### データセット

データセットは、アーカイブに登録された 1 まとまりのデータである。コード上は `dataset` で、1 つの研究だけに属する。

- データセットにバージョンは無い。データそのものは変わらず、変わるのはデータセットの内容の訂正なので、訂正は研究のバージョンの更新で行う。
- データセットの内容は、バージョンの中と、下書きごとの行 (`draft_dataset_entry`) に置く。下書きごとに分けるのは、並行する 2 つの下書きが同じデータセットを別の内容で書けるようにするためである。

### 解析手法

解析手法は、データセットの中で、プラットフォームや試料などデータの作り方をまとめた 1 件の要素である。コード上は `experiment` で、画面では「解析手法」と表示する。データセットの内容の中に順序付きで並び、独立した行は無い。

### 公開区分

公開区分は、データセットを誰が使えるかの区分で、非制限公開・制限公開 (Type I)・制限公開 (Type II) の 3 つである。データセットの項目の 1 つ (語彙 `access-criteria`) の値としてデータセットの内容に入り、値の追加や言い換えは画面からできない。

## ID

外から参照される ID は、研究とデータセットの実体に後から割り当てる。

### 研究 ID

研究 ID は `hum` と 4 桁の数字 (`hum0014`) である。コード上は hum ラベル (label の種類 `hum`) と呼ぶ。

### データセット ID

データセット ID は 3 種類あり、どれも同じ割り当て表で管理する。

- JGAD は、JGA に登録された制限公開のデータセットの ID で、申請管理システムから読む。
- NHA ID は、ポータルが発行するデータセット ID で、`NHA` と 6 桁の通し番号 (`NHA000001`) である。発行の決まりは [data-model.md](data-model.md) の「NHA ID」にある。
- 外部 accession は、DRA など他のアーカイブの ID で、日付や登録内容を DDBJ Search から読む。

### ID の割り当て

ID を実体に付けることを、コード上は pin と呼ぶ。付けた ID (コード上は label) は `label_pin` の行になり、研究 ID とデータセット ID を 1 つの表で管理する。

- 1 つの実体に複数の ID を付けられ、そのうち 1 つを primary の ID とし、残りを secondary の ID とする (画面のバッジの語)。公開ページの URL と表示には primary の ID を使い、secondary の ID は、古い ID で参照されても同じ実体にたどり着けるように残す。データセットのページには secondary の ID も「Secondary ID」として表示し、一覧の検索は secondary の ID でも引ける ([public-site.md](public-site.md))。一意性と再利用の決まりは [data-model.md](data-model.md) の「実体と ID」にある。
- バージョン番号も外から見える番号だが、研究の中でだけ一意なので、この表ではなくバージョンの行に置く。

### データ提供申請と枝番

データ提供申請は JGA 申請管理システムに出される申請で、`J-DS` から始まる番号が付く。1 つの申請は枝番 (`J-DS000136-010` の末尾) ごとに書類が分かれ、承認された枝番 1 つが登録 1 回に当たる。ポータルは承認済みの枝番から下書きを作り、値を取り込む ([editing.md](editing.md))。申請管理システムは読むだけで、書き込まない。研究 ID と J-DS の対応の正本も申請管理システムにある。

## 研究の内容と項目

研究とデータセットの内容は、決まった型の JSON として保存する。

### 研究の内容とデータセットの内容

研究の内容とデータセットの内容は、公開ページに出す値の集まりで、コード上は `content` (JSONB の列) である (画面の語は「研究の内容」)。型は `app/content/types.ts` にあり、バージョンと下書きで同じ型を使う。型が同じなので、公開は値のコピーで済む。

### 公開用の表示データ

公開用の表示データは、研究の内容から公開してよい値だけを残したもので、型は研究の内容と同じである。公開ページ・プレビュー・全文検索はこれを使う ([data-model.md](data-model.md) の「公開用の表示データ」)。

### 項目定義と語彙

データセットと解析手法には、決まったキーの下に値を並べる。キーの一覧を項目定義と呼び、コード上は `content_key` (catalog) である。画面では key と表示する。

- キーには型があり、語彙と疾患の型のキーと、絞り込みのカテゴリを設定した数値の型のキーが、公開サイトの絞り込みの項目になる。それ以外のキーは自由記述である。
- 絞り込みのカテゴリ (`facet_category`) は、公開サイトの絞り込みの項目をまとめる見出しである。どの項目をどのカテゴリに入れるかは admin が決める。
- 語彙は、選択肢の値の集まりである (`vocabulary_set` と `vocabulary_term`)。研究の内容は語彙の値を ID で参照するので、表示名を変えても研究の内容を書き換えずに済む。
- 公開区分や ICD10 のように構造や外部の規格で決まる語彙は、画面から編集できない。データとともに増える語彙 (プラットフォーム、組織など) は admin が編集する。

### 値の状態

項目の値には、値があるほかに「未確定」と「該当なし」の状態がある。コード上は `unknown` と `not-applicable` で、日本語と英語で別々に決める。

- 未確定は、値があるはずだがまだ決まっていないことを表す。プレビューでは提供者への問い合わせ (「ご教示ください」) として表示し、公開前の確認で一覧に出る。
- 該当なしは、値が無いと確定していることを表し、公開ページに `N/A` と表示する。
- 空は状態ではなく、「値があって中身が空」である。まだ誰も書いていない欄はこれに当たる。
- 未翻訳は保存する状態ではなく、翻訳の組で片方の言語だけが空のときに値から決まる。

### 更新番号

更新番号は、下書きと、下書きごとのデータセットの内容に付く、保存のたびに 1 増える整数である。コード上は `revision` で、同時に編集した人の変更を上書きしないように、保存のときに照合する ([editing.md](editing.md))。

## 公開とレビュー

下書きは、提供者のレビューと公開前の確認を経てバージョンになる。

### 共有リンクとプレビュー

共有リンクは、下書き 1 つにつき 1 つの、ログインせずに読める URL である。リンクを開くとプレビュー (公開したときと同じ見た目の下書き) が表示され、各欄にコメントを書ける。

### 公開前の確認

公開前の確認は、公開の操作の前に下書きを検査する手順である。ID が揃っていないものは公開できず、未確定・未翻訳・申請管理システムとの食い違いは一覧で示し、admin が確認した上で公開する ([publishing.md](publishing.md))。

### 検索用の行

検索用の行は、公開中の研究・バージョン・データセットごとに作る行である (`search_doc` など)。公開ページ・検索・JSON API はどれもこの行から公開中のものを読み、この行は公開や取り下げと同じトランザクションで作り直す ([data-model.md](data-model.md))。

## サイトの記事

研究とは別に、ポータルには記事・お知らせ・アラートがある。どれも研究のバージョン・下書き・ID の割り当てを使わず、公開中のものは保存した時点で公開ページが変わる。記事とお知らせは言語ごとに公開する ([site-content.md](site-content.md))。

- 記事は、URL が slug で決まるページ (ガイドラインなど) で、コード上は `document` である。改訂を残したい記事は、バージョンごとに別の記事として作る (バージョンのある記事)。記事のバージョンは slug の末尾の番号で、研究のバージョンとは別のものである。
- お知らせは、日付の付いた告知で、コード上は `news` である。公開日時が未来のものは、その日時まで表示しない。
- アラートは、全ページの上部に出す 1 文で、コード上は `alert` である。表示するかどうかの切り替えと、表示期間を持つ。お知らせとは別のものなので、画面でも「お知らせ」とは呼ばない。

## ファイル

データファイルは DB ではなくファイルストアに置き、公開と非公開の切り替えはジョブで行う ([files.md](files.md))。

### 研究ごとの prefix

研究ごとの prefix は、ファイルストアの bucket の中で 1 つの研究のファイルをまとめる key の先頭部分である。コード上は `app/files/prefix.ts` が扱う。

- 非公開の bucket (`private`) では研究の実体の ID で、公開の bucket (`files`) では研究 ID で prefix を作る。研究 ID が付く前にファイルがアップロードされることがあるためである。
- ファイル名は 2 つの bucket で同じにする。admin が 1 つの一覧として見られるようにするためである。

### ジョブ

ジョブは、時間のかかる処理を DB の行として登録し、app のプロセスが後から実行するものである。専用の worker は置かない。

- ファイルの公開と非公開の切り替え (`file_publish_job`) は、ファイルの中身を bucket 間でコピーするので、公開の操作とは別に実行する。
- 申請管理システムと DDBJ Search からの取得 (`upstream_refresh`) は、取得先ごとに 1 日 1 回実行する。
