# 項目定義と語彙

データセットと解析手法の値を並べるキー (項目定義)、選択肢の値 (語彙)、疾患 (ICD10) の 3 つについて、決まりをまとめる。語の意味は [concepts.md](concepts.md) の「項目定義と語彙」、値を研究の内容にどう保存するかは [data-model.md](data-model.md)、公開サイトの絞り込みでの使われ方は [public-site.md](public-site.md) の「絞り込み」にある。

## 項目定義

データセットと解析手法の値のキーは、項目定義 (`content_key`) で決める。キーには、キーを使う対象 (データセットか解析手法か)、日本語と英語の表示名、値の型、表示順がある。

- キーの名前の変更は表示名の変更であり、研究の内容は変わらない。研究の内容はキーを ID で指すためである。
- キーの追加は明示的な操作である。入力した文字列がそのまま項目定義に加わる経路は無い。編集画面からも、データ提供申請の取り込みからも、キーと語彙の値は作られない。入力された文字列がそのまま加わると、表記揺れが生まれるためである。
- admin が画面で追加・削除できるのは、解析手法の自由記述のキーだけである。名前の変更と並べ替えは、解析手法のキーなら型によらずできる。データセットのキーと、型が語彙・数値・疾患のキーの追加・削除・型の変更は、開発の作業である。これらのキーは絞り込みの項目になり、集計と入力欄が必要になるためである。
- 型が語彙か疾患のキーは、常に絞り込みの項目になる。型が数値のキーは、絞り込みのカテゴリ ([concepts.md](concepts.md)) を設定したキーだけが絞り込みの項目になる。絞り込みに使うかどうかはカテゴリの有無で表し、絞り込みに使うかどうかを表す別の列は無い。
- 公開日・更新日とファイル形式はキーではないが、絞り込みの項目になる。ファイル形式の絞り込みには、語彙 `file-type` の値を使う。検索式では `file-type:fastq` と書く。ファイル形式は、カテゴリ「データ」の先頭に並べる。
- キーの code と語彙の値の code は、検索の URL に入る (`?q=platform:hiseq-2500`)。そのため、code は英語の表示名から機械的に作り、admin には入力させない (`app/admin/catalog.ts` の `codeFrom`)。同じ code があれば、末尾に番号を付ける。組み込みの検索フィールドと同じ文字列は、code に使えない。ICD10 だけは、規格のコードをそのまま code にする。
- 使われているキーと、使われている語彙の値は、削除できない。公開中のデータセットの内容か下書きの内容に、そのキーの値があれば、キーは使われているとする。公開中のデータセットの内容か下書きの内容が、その語彙の値を指していれば、語彙の値は使われているとする。
- 項目定義や語彙を書き換えたら、検索用の行を全部作り直す。どの変更が検索用の行に反映されるかを操作ごとに判断すると、判断を誤った操作だけが反映されなくなるためである。作り直さない例外は、キーの並べ替えだけである。作り直すかどうかの判断は、項目定義の書き込みをまとめた 1 か所に書く。

### キーが無いもの

データセットのファイルや ID から決まる値には、キーを作らない。

- データセットそのものが accession になるアーカイブ (JGA、DRA、GEA、MetaboBank) の accession のキーと、ポータルが発行する NHA ID の accession のキーは無い。データセット ID がその accession なので、キーに同じ ID を書いても重複するだけである。アーカイブのデータセットのページには、DDBJ Search の entry へのリンクも表示する ([public-site.md](public-site.md))。ポータルにデータセットの無いアーカイブ (GEO、jPOST、INSDC、EGA) の accession のキーと、JGA が加工したデータのデータセット ID のキーはある。
- データセットの総データ量とファイル形式のキーは無い。どちらも、データセットのファイルから作る値である。JGAD・DRA・GEA・MetaboBank では、取得元のファイルから作る ([upstream.md](upstream.md) の「データセットのファイルの大きさと形式」)。NHA では、ファイルの選択から作る ([files.md](files.md) の「データセットとファイルの対応」)。人が計算して書いた値は、データの追加で古くなり、形式や内訳の書き方も研究ごとに揃わないためである。

### キーの名前

キーの名前は、公開ページの表の見出しになる。型のあるキーでは、絞り込みの項目の名前にもなる。名前は次のように書く。

- 見出しは単数形で書く。値が複数あることは、見出しに書かない。
- 単位は入れない (`Read length (bp)` ではなく `Read length`)。数値は入力された単位のまま表示するため (`73 TB`)、見出しに単位を書くと値と食い違う。
- 「〜の別」「〜の単位」は使わず、値を表す名詞で書く。有無を表すキーは「〜の有無」とする。
- 括弧は半角で、前後に半角の空白を入れる (`カバレッジ (深度)`)。
- 型のあるキーの英語は文頭だけ大文字にし、略称と固有名詞の表記はそのまま残す (`Disease (ICD-10)`)。自由記述のキーには、この規則を適用しない。自由記述のキーはアーカイブ名を含むことがあるためである (`Gene Expression Omnibus Accession`)。
- 日本語の名前と英語の名前は、同じものを指す。
- これらの規則のうち、括弧・単位・「〜の別」の規則と、型のあるキーの英語の大文字の規則は、キーの追加と名前の変更のときにサーバーが検査し、規則に合わない名前をエラーにする (`app/admin/catalog.ts` の `keyLabelProblem`)。

## 語彙

語彙は選択肢の値の集まりで (`vocabulary_set` と `vocabulary_term`)、1 つの語彙は 1 つのキーに属する。例外はファイル形式の語彙 `file-type` で、どのキーにも属さない。

- 語彙の値の表示名は、英語が必須で日本語は任意である。日本語が空でも未翻訳に数えない。同じ語彙の中でも、日本語で書かれるかどうかが値ごとに違うためである。
- 語彙には原則として階層が無く、階層があるのは ICD10 だけである。
- 製品を指す語彙の値では、会社名を `maker` 列に分けて保存する。会社名を親の値にすると、絞り込みの一覧に会社名が並んでしまうためである。表示名は会社名を含んだ全体のままで、`maker` 列を使うのは表示するときだけである。
- 1 つの語彙の値は 1 つのものを指す。
- 表示順 (`position`) は、編集フォームの候補と一覧のセルで使う。絞り込みの一覧は、件数の順に並べる。
- 公開サイトと JSON API の処理では、項目定義と語彙の値をアプリのプロセスの中に保持し、変更があったときだけ読み直す。ICD10 だけで値が 1 万を超え、リクエストのたびに読むと応答の時間の多くを占めるためである。
  - 変更は、DB の trigger が `NOTIFY` でアプリに知らせる。アプリは、リクエストのたびに、それまでの通知を受け取ってから、保持している項目定義と語彙の値を使う。そのため、admin の編集も、`tools` での ICD10 の取り込みも、commit のあとのリクエストには必ず反映される。
  - 通知を受ける接続が切れているあいだは、アプリは項目定義と語彙の値を保持せず、リクエストのたびに読む。

### 画面から編集できる語彙

admin が編集するのは、データとともに増える語彙 (プラットフォーム、組織など) だけである。

- 次の語彙は、画面から編集できない (`app/admin/catalog.ts` の `SETTLED_VOCABULARIES`)。値の集合がポータルの仕様として決まっている語彙 (公開区分、性別などの排他的な分類)、ICD10、ファイル形式である。ICD10 の見出し語は外部の規格で、ファイル形式はファイルの拡張子で決まるためである。編集できない語彙も DB に保存する。検索用の行が語彙の値の ID を参照するためである。
- 利用ポリシーの語彙 (`policies`) の値にだけ、記事 ([site-content.md](site-content.md)) を 1 つ指定できる。公開ページでは、記事を指定した値の表示名を、ポリシーの本文を書いた記事へのリンクにする。ほかの語彙の値には記事を指定できず、画面にも指定の項目を表示しない。組織やプラットフォームの値には指す記事が無いためである。語彙の値は、記事を slug ではなく記事の ID で指すので、記事の slug を変えてもリンクは切れない。記事を削除すると、指定は外れる。
- 使われている語彙の値を整理するときは、統合を使う。統合では、統合元の値を指している参照を全部統合先の値へ書き換えてから、統合元の値を消す。統合できるのは、同じ語彙の中だけである。
- 統合では、過去のバージョンの内容も書き換える。語彙の値は研究の内容そのものではなく、研究の内容が指す先だからである。公開中のバージョンの内容が変わるのは、統合のときだけである ([publishing.md](publishing.md) の「バージョン番号」)。統合は操作の記録に残す ([publishing.md](publishing.md) の「操作の記録」)。語彙の値に「選べない」状態は無い。

## 疾患 (ICD10)

疾患の値は、語彙の値への参照の並び (0 個以上) と、呼称 (日本語と英語) でできている。

- 参照が 1 つも無い値は正しい状態である。分類に載っていない疾患が実データにあるためである。
- 呼称は疾患の値に、見出し語は語彙の値に保存する。同じコードが、研究ごとに違う集団の定義として書かれる。呼称を語彙の値にまとめると、研究ごとの区別が失われるためである。表示するのは、呼称があれば呼称、無ければ見出し語である。
- 1 つの値は複数の分類の語彙の値を指せる。分類を足しても値の形は変わらない。
- 分類は、3 桁の分類を根とし、4 桁の分類を 3 桁の分類の子とする 2 階層である。絞り込みの件数は根で数える。
- コードは 3 桁と 4 桁だけを使う。移行でも、申請からの下書きの作成でも、同じ正規化 (`app/icd10/codes.ts`) を行い、語彙にあるコードになるまで末尾を削る。3 桁を 4 桁へ広げることはしない。書いた人が選ばなかった細分を補わないためである。
- 分類そのものが語彙である。`npm run icd10:import` が、3 桁と 4 桁の全コードを語彙 `icd10` に入れる。語彙とは別の辞書は作らない。再取り込みでは code で照合して上書きし、語彙の値の ID は変わらない。
- 英語の見出し語は WHO の ICD-10 (Version 2019)、日本語は e-Stat の基本分類から取る。日本語にしか見出し語が無いコードは、英語の欄にも日本語の見出し語を入れる (英語は必須のため)。英語にしか無いコードは日本語の欄を空にし、表示するときに英語の見出し語を使う。
- 参照が無い疾患の値からは、絞り込みの行を作らない。ただし、呼称は全文検索に入るので、キーワードでは見つかる。
