# JSON API

公開データを機械が取るための面。**この doc は endpoint の一覧もパラメータの表も持たない** — それは
`/api/openapi.json` が持っていて、二重に書けば必ずずれる。ここに書くのは document から読み取れない
規約と不変条件だけになる。

## 何のためにあるか

**画面はこの API を使わない。** loader / action が Postgres を直接読むので、画面のために API 面は
要らない。したがって存在理由は「再利用者が機械的に取れること」だけで、範囲もそこから決まる。

| 用途 | 面 |
|---|---|
| 個別取得 | `/api/research/{humId}`、`/api/research/{humId}/v{n}`、`/api/dataset/{datasetId}` |
| 検索 | `/api/research`、`/api/dataset` |
| 一括取得 | `/api/research.jsonl`、`/api/dataset.jsonl` |
| DDBJ Search への relation の供給 | `/api/dblink` 以下 |

**作法は [ddbj-search-api](https://ddbj.nig.ac.jp/search/api/docs) に合わせてある。** 同じ組織が同じ
利用者層に出している public API なので、そこで決まっているものを別に決め直す理由が無い。揃えたのは
RFC 7807 のエラー・CORS の全許可・NDJSON の Content-Type・そして「doc には document で表現しきれない
規約だけを書く」という分担の 4 つ。

## 認証を持たない

公開済みだけを返すので認証する対象が無い。**CORS はすべての origin に開く。** すべて `GET` で、独自の
header を要求しないので preflight も起きない。

## 何を公開されていると言うか

**集合は `search_doc` からしか引かない** ([data-model.md](data-model.md) の「検索用の行」)。個別取得も
検索も一括も、まずこの行に対象があるかを問う。

守ること:

- **公開されていないものと、存在しないラベルは同じ 404 を返す。** detail はオブジェクトの種類ごとの
  固定の文で、**ラベルを書き返さない** — status で隠したものを本文で明かさないため。`instance` は
  要求されたパスなので、呼び出した側が既に知っていること以上を言わない
- **secondary のラベルは redirect せず、そのまま答える。** 画面は「1 ページ 1 アドレス」のために
  redirect するが、引用を辿る機械に往復を増やす意味は無い。応答の `id` と `url` は primary のものに
  なるので、いま有効なラベルは本文から分かる

## 応答の形

### 言語

**ja と en を両方載せ、アドレスに言語を持たない。** 機械が取る以上、片方を落とす理由が無い。
**未翻訳のときにもう一方の言語へ倒すこともしない** — それは画面が読者のために持っている規則で、API が
やると「これが訳です」と誰も言っていない値を訳として返すことになる。

### 値があるかないか

| 見え方 | JSON |
|---|---|
| 値あり | 値 |
| 空 / 未確定 | **キーごと無い** |
| 該当なし | **`null`** |

公開表現が未確定を空へ倒すので ([data-model.md](data-model.md) の「公開表現」)、API に届く時点で空と
未確定は同じものになっていて、どちらも消える。残るのは「値が存在しないことが確定している」という、
言うことがある 1 つだけになる。

**配列は空でも必ずある。** `research.grants.length` を、キーの有無を確かめずに書けるようにするため。
これは ddbj-search-api の規約で、両方を読む人がどちらがどちらか覚えなくて済むようにしてある。

### 数

**数値のキーは数の配列を返す** (`numbers`)。1 つしか持たないキーも要素 1 つの配列で、**キーの型を見て
形を変えない** — 「1 つなら値、複数なら配列」にすると、読む側が両方を書くことになる。

各要素は正準単位の `value` と `unit` を持ち、**その数が何についてのものかを言う `label` と、数を
修飾する `note` は、あるときだけ載る** ([data-model.md](data-model.md) の「値と文」)。大半のキーは
どちらも持たないので、応答はこれまでどおり値と単位の 2 つになる。

**返すのは正準単位の値**で、打たれた単位ではない。画面は打たれたほうを出すが、API は比較できる 1 つの
単位で揃っているほうが使える。

### 文

**plain text で返す** ([data-model.md](data-model.md) の「値と文」)。content は行と span の木で持つが、
木をそのまま出すと応答の形が content モデルに縛られ、node を直すたびに破壊的変更になる。

**この変換で自由文の中のリンクは行き先が落ち、文字だけが残る。** 機械が使う参照 — accession・
dataset id・語彙・ファイル・研究概要 URL — は型付きの field として別に載るので、落ちるのは文の中に
書かれた外部サイトへの参照だけになる。

### identity

**内部の identity は出さない。** uuid も、配列要素の id も、語彙値の id も。**語彙値は code と両言語の
ラベルで返す** — code はアドレスに載る綴りと同じものなので、API で見つけた値でそのまま検索できる。

**疾患は識別子と 2 種類の名前を返す** ([data-model.md](data-model.md) の「ICD10」)。1 つの値が
`{ 識別子の並び, 呼称 ja/en }` で、識別子は体系ごとの code と見出し語を持つ。**識別子が空の値がある**
ので、消費側は ICD10 のコードが必ずあることを前提にできない。

値スロットは **catalog の表示順**で並ぶ。content 側に守るべき順序が無いので、順序を固定しておかないと
2 つの応答を比べられない。

## 個別取得と検索と一括は同じオブジェクトを返す

**投影は 1 本** (`app/api/view.ts`)。個別取得の応答も、検索の 1 hit も、一括の 1 行も同じ関数の出力で、
「どこまでが要約か」という線を API が別に持たない。

**research は配下の dataset を id の列だけで持つ。** dataset は独立した identity で独立したアドレスを
持つので、埋め込むと同じ情報が 2 箇所に出る。1 研究が 200 を超える dataset を持つこともある。網羅的に
欲しい側は一括取得を使う。

**research は自分の「更新日」を持たない。** 公開版の一覧を持つので、最後の要素がそれになる。

### 検索

**`?q=` はアドレスに載るのと同じ検索式**で、受け口は画面と同じ 1 本 (`app/search/dsl.ts`)。facet の
条件も同じ綴りで効く ([public-pages.md](public-pages.md) の「一覧と検索」)。**API のために 2 本目の
クエリ経路を作らない。**

- **1 ページ 20 件の固定。** 大きさの旋を持たない — 全件が欲しいなら一括取得がある。**公開画面は
  `?size=` で選べるが、この API はその綴りを読まない** — 約束しているのは応答の形なので、そこは動かさない
- **facet の集計は返さない。** パネルという画面の部品で、返すと呼び出しごとに「1 + 選択済み facet 数」
  回のクエリが走る
- **並びに関連度を持たない。** 画面と同じ 3 つのキーだけで、既定は更新日の降順
  ([public-pages.md](public-pages.md) の「並びと件数」)

### 一括

**NDJSON を流す。** 全件を 1 つの配列にすると読み手が全部メモリに載せることになり、途中から読むことも
できない。アドレスは検索と同じ名前に `.jsonl` を付けたものになる。

## 何を約束するか

**約束するのは URL の到達性だけで、内容の不変は約束しない。** fix は版番号を変えずに公開内容を
差し替えるので ([publishing.md](publishing.md))、同じ URL が同じ内容を返し続けることはそもそも保証
できない。**fix を外から検出する手段も持たせない** — 応答に載る日付は archive 由来の dataset の日付と
admin が設定する版の公開日で、どちらもポータルの content がいつ変わったかを表す値ではない。

**ファイルの URL は約束の対象にしない** ([data-model.md](data-model.md) の「ファイル」)。形は保つが、
ファイルは参照元と無関係な公開状態を持ち admin が切り替えられる。

**ストアが答えなければ箱は空として返す。** 公開ページはダウンロードの節ごと落とすが、無関係な系の
応答可否で JSON の形が変わるほうが悪い。箱の一覧は API が完全性を約束しているものではない。

## エラー

**RFC 7807 の problem details** (`application/problem+json`)。`type` は
`https://humandbs.dbcls.jp/problems/{slug}`。

| status | いつ |
|---|---|
| 404 | そのラベルで公開されているものが無い (未公開と不在の区別は付かない) |
| 422 | パラメータが読めない。読めない `?q=`、使えない `sort`、負のページ、扱わない accession type |

400 を使わない。この API が拒む理由はどれもパラメータの形の話で、ビジネスルールの違反にあたるものが
無いため。

## DDBJ Search への relation の供給

JGA accession ↔ hum ラベルの対応を返す。現在は a014 の cron が JGA 申請 DB から TSV を作って a012 に
scp している 3 段が、この endpoint に置き換わる。

**面は ddbj-search-api の DBLinks API をそのまま採ってある。** 受け手が同じ道具立てで、応答の `Xref`
型も `humandbs` という accession type も向こうに既にある。`/api/dblink` が扱う type を、
`/api/dblink/{type}` がその type の全件を NDJSON で、`/api/dblink/{type}/{id}` が 1 件を返す。

守ること:

- **source は上流のキャッシュ** (`hum_accession`。[data-model.md](data-model.md) の「外部キャッシュ」)。
  この対応の master は JGA 申請管理システムで、**ポータルの pin は master ではない**ので、キャッシュに
  無い対応は返さない
- **ポータルで公開されている hum の対応だけを返す。** JGA 側が public でもポータルが公開していない
  ものは返さない。返すと DDBJ Search の詳細画面に必ず 404 になるリンクが出るうえ、「公開されていない
  ものと存在しないラベルは同じ 404」がこの endpoint 経由で破れて、未公開の hum ラベルが外から列挙
  できるようになる。**したがってこの API に「公開済みだけを扱う」の例外は無い**
- **報告するのは primary のラベル。** 上流はラベルを人が手で打っていて typo の実績があり、訂正された
  ラベルは secondary の pin として残る。返すのは `/{humId}` が応答するほうになる
- **該当が無いときは 200 と空の一覧。** 存在しない accession も、公開していない hum に紐づく accession
  も同じ応答になり、これ自体が存在秘匿になっている

hum ラベルの行き先は `/{humId}` (裸の hum ID)。DDBJ Search が既にこの形でリンクを組んでいて、
恒久的に応答し続ける必要がある ([public-pages.md](public-pages.md))。

## OpenAPI document

**endpoint の配列 1 箇所から、route の登録と document の両方を出す** (`app/api/endpoints.ts`)。
アドレスが 2 箇所に書かれなければ、route と document がずれる余地が無くなる。React Router の `:name` と
OpenAPI の `{name}` の差は機械変換になる。

**応答の schema が型の SSOT** (`app/api/schema.ts`)。投影はこの型に対して書かれ、document は同じ schema
から出るので、document が約束するものとコードが作るものが 2 つに割れない。**実行時の検証は持たない** —
投影は全域関数で、コンパイラが schema に照らして確かめている。

## 意図的にやっていないこと

| やらないこと | 理由 |
|---|---|
| Swagger UI | v1 の Swagger UI は 33 時間でアクセス 0 件。UI を持つと CDN の script か self-host の依存が 1 つ増える |
| `X-Request-ID` | 突き合わせるリクエストログの仕組みが無いので、返しても照会先が無い |
| ページの大きさを変える旋 | 全件は一括取得がある。1 つの数を 2 箇所に置かない |
| facet の集計を返すこと | 集計は画面の部品。絞り込み自体は `?q=` で効く |
| 書き込みの面 | 編集は server 実行点で行う。API 化する受益者が特定できていない |
| 申請管理システムのラッパーを endpoint にすること | 受益者と置き換わる実装が特定できたものから出す。service account が「1 人 1 アカウント」と衝突する ([auth.md](auth.md)) |
| 版の一覧の endpoint | リリース情報は「隣り合う公開版の差」という画面のための導出。機械には research の応答に載る版の一覧で足りる |
