# テスト

何を test にし、どう分け、何を mock してよいか。回すコマンドは [development.md](development.md)。

## 階層

階層は道具ではなく**どの失敗を捕まえる担当か**で分かれる。同じ対象に複数の階層がかかってよい。

| 階層 | 捕まえる失敗 | 道具 | ファイル名 |
|---|---|---|---|
| 不変量 | 仕様どうしの矛盾、境界の見落とし | fast-check。純関数だけ | `*.pbt.test.ts` |
| 単体 | 仕様が実装されていない | vitest。純関数と component | `*.test.ts(x)` |
| schema | 制約が実際には効かない | 実 Postgres。アプリのコードを通さない | `*.db.test.ts` |
| 経路 | 部品は正しいが配線を間違えた | 実 Postgres + loader / action | `*.db.test.ts` |
| e2e | 画面が出ない、経路が通らない | Playwright。配置した実物 | `tests/e2e/*.spec.ts` |

ファイルは対象の隣に置く。vitest の project は走るのに何が要るかで分かれ、`unit` は source だけで走る
もの、`db` は compose の Postgres が要るもの (`vitest.config.ts`)。helper と fixture は `_` で始まる名前にして
collection から外す。

**「仕様自体が間違っている」は example-based の test では捕まらない** — test は仕様を実装へ写すので、
仕様の誤りを再生産する。捕まえられるのは、PBT の法則が反例を出すこと、実データを流して落ちること、
移行の保存則の 3 つ。

## 何を test にするか

**docs に書いた不変条件は、1 つ以上の test を持つ。** test 名を不変条件の文そのものにして、どの記述を
守っているかが読んで分かるようにする。形は `describe("対象") > it("条件と期待結果")`
(`assistant-api/` の Python は `test_<対象>_<条件>_<期待結果>`)。

- **カバレッジを判定に使わない。** 実行された行は、assertion が何を弾くかと独立している
- **通るだけの test を書かない。** 境界値・異常系・否定形を足せないなら書かない
- **「例外を投げない」を不変量にしない。** 入出力の意味のある制約だけを法則にする。arbitrary は
  `arbitraries/` に集める
- **見た目の中の、真偽の決まる命題は規則 test にする** — コントラスト、余白を画面が書かないこと、角丸の
  種類、部品カタログが本番に入らないこと。どれも source を読んで判定する ([development.md](development.md) の「画面の規則」)
- **型で結べない 2 つの対応は test で結ぶ。** 差分の path を全部取り込むと差分が空になること、描画が
  出したアンカーと view が記録したアンカーが一致すること
- **経路の階層には否定形を置く** — 未公開のものがどの公開経路からも出ない、共有リンクの検証が画面の
  guard を迂回しても効く、アプリの role が event を書き換えられず TRUNCATE もできない (実際にその role で
  発行して落ちることを見る)

## mock の境界

**mock してよいのはポータルの外側だけ** — Keycloak、S3、DDBJ Search、申請管理システム DB、時刻と乱数。
**Postgres・schema・content の型・内部の関数・loader / action は mock しない。** 設計の中心が schema の
制約と検索用の行の導出にあるので、DB を mock すると捕まえたい失敗が test の外へ出る。内部の mock が
要るように見えたら、test ではなく設計を直す。

## test 間の独立性

**状態を共有せず、実行順序に依存しない。**

- **DB を使う test は、開発用の名前に `_test` を付けた専用の database に対して回す。** 名前は設定で
  切り替えられない — 向き先を間違えると開発用データが消えるので、間違えようの無い形にする
- **走り出す前に、繋いだ先が `_test` で終わるかを実際の接続で確かめ** (`app/db/test-database.ts`)、
  違えば 1 件も実行せずに止まる
- **各 test は前に database を空にするので、ファイルは直列に回す** (`fileParallelism: false`)。空にするのは
  owner の接続で、test 本体はアプリの role で回す — 権限まで本番と同じ条件にするため
- **`test:db` を同時に 2 つ走らせない。** 直列が守るのは 1 つの run の中だけで、2 つ目の run が 1 つ目の
  行を消す。落ちる場所と数が run ごとに動くのが手がかり

## e2e

**配置した実物に対して回す。開発中にも CI でも回さない。** 実行が分単位なので、回すのはリリースの判定の
前。**e2e は読むだけで、公開しない** — 実物は 1 組の行しか持たないので、版を出すと他のシナリオが読んで
いるものが変わる。下書きを作るのだけは例外 (読者から見えるものは動かない)。**画面の名前や研究 ID を
コードに書かず**、一覧の先頭から辿って対象を決める — 回す先ごとに中身が違う。

**署名の要るシナリオ (`*.user.spec.ts`) はセッションを渡して回す。** ブラウザは外の認証画面を通れない
ので、回す先の実物の上でセッションを作り、環境変数で渡す。渡さなければ理由を言って skip する。この
セッションは作った時点で admin になるので、**回す先が本番であってはならない。**

## 意図的にやっていないこと

| やらないこと | 理由 |
|---|---|
| カバレッジの目標値・test の量の目標 | 実行された行数も書いた量も、欠陥の発見と相関しない |
| mutation testing | 効くのは純関数の階層だけで、壊れて困るのは実 DB を通る側 |
| 開発中と CI での e2e | 実行が分単位 |
| 移行の保存則を test にすること | 入力の snapshot に依存するので検証コマンドとして持つ。保存則を計算する関数は純関数として test する |
