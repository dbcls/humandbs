# テスト

何をテストにし、どう分け、何を mock してよいかをまとめる。テストを回すコマンドは [development.md](development.md) の「日常のコマンド」と「e2e」にある。

## 種類

テストの種類は、使うツールではなく、どの失敗を見つけるためのものかで分ける。同じ対象に複数の種類のテストを書いてよい。

| 種類 | 見つける失敗 | ツール | ファイル名 |
|---|---|---|---|
| 性質 (PBT) | 仕様どうしの矛盾、境界の見落とし | fast-check。純関数だけ | `*.pbt.test.ts` |
| 単体 | 仕様が実装されていない | vitest。純関数と component | `*.test.ts(x)` |
| schema | 制約が実際には機能していない | 実際の Postgres。アプリのコードを通さない | `*.db.test.ts` |
| 経路 | 部品は正しいが、つなぎ方を間違えた | 実際の Postgres と loader / action | `*.db.test.ts` |
| e2e | 画面が表示されない、操作が最後まで通らない | Playwright。配置した環境 | `tests/e2e/*.spec.ts` |

- テストのファイルは対象のファイルの隣に置く。helper と fixture は名前を `_` で始め、テストとして集めないようにする。
- vitest の project は、走るのに何が要るかで分ける (`vitest.config.ts`)。`unit` は source だけで走るテスト、`db` は compose の Postgres が要るテストである。
- 仕様そのものの誤りは、例を並べるテストでは見つからない。テストは仕様をそのままコードに書き直したものなので、仕様の誤りも同じように含むためである。見つけられるのは、PBT の性質が反例を出すとき、実データを流して失敗するとき、移行の前後で件数などが保たれているかを確かめるときの 3 つである。

### e2e

e2e は配置した環境に対して回し、開発中にも CI でも回さない。実行に分単位の時間がかかるので、回すのはリリースを判断する前である。

- e2e は読むだけで、公開しない。配置した環境には公開中のデータが 1 組しかなく、あるシナリオが公開すると他のシナリオが読む内容が変わるためである。下書きを作ることだけは例外で、読者から見える内容は変わらない。
- 画面の名前や研究 ID をコードに書かず、一覧の先頭から順にたどって対象を決める。回す先ごとにデータが違うためである。
- ログインが要るシナリオ (`*.user.spec.ts`) は、セッションを環境変数で渡して回す。ブラウザは外部の認証画面を通れないので、回す先の環境でセッションを作る。渡さなければ理由を表示して skip する。
- このセッションの利用者は作った時点で admin になるので、回す先を本番にしてはいけない。

## 何をテストにするか

docs に書いた不変条件には、それぞれ 1 つ以上のテストを書く。テスト名には不変条件の文をそのまま使い、docs のどの文を確かめているテストかを読んで分かるようにする。形は `describe("対象") > it("条件と期待結果")` で、`assistant-api/` の Python は `test_<対象>_<条件>_<期待結果>` である。

- カバレッジを判断に使わない。実行された行かどうかと、assertion が何を検出するかは関係が無い。
- 通るだけのテストを書かない。境界値・異常系・否定形を足せないなら、そのテストは書かない。
- 「例外を投げない」を PBT の性質にしない。入力と出力の間の意味のある制約だけを性質にする。fast-check の arbitrary は、対象の dir の `arbitraries/` に集める。
- 見た目のうち真偽を決められるもの (コントラスト、画面ごとに余白を書かないこと、角丸の種類) は、source を読んで判定するテストにする ([development.md](development.md) の「画面の規則のテスト」)。
- 型では結び付けられない 2 つの対応はテストで結び付ける。例として、差分のパスを全部取り込むと差分が空になること、描画したアンカーと表示用のデータに記録したアンカーが一致すること、がある。
- 経路のテストには否定形を入れる。未公開のものがどの公開の経路からも出ないこと、画面の guard を通らなくても共有リンクの検証が適用されること、アプリの role が操作の記録を書き換えられず TRUNCATE もできないこと (実際にその role で実行して失敗することを確かめる) である。

## mock の境界

mock してよいのはポータルの外側だけである。対象は Keycloak、ファイルストア、DDBJ Search、申請管理システムの DB、時刻と乱数である。

- Postgres・schema・研究の内容 (content) の型・内部の関数・loader / action は mock しない。設計の中心は schema の制約と検索用の行の作り方にあるので、DB を mock すると見つけたい失敗がテストの外に出てしまう。
- 内部の mock が要るように見えたら、テストではなく設計を直す。

## テスト同士の独立

テストどうしで状態を共有せず、実行順序に依存させない。

- DB を使うテストは、開発用の database 名に `_test` を付けた専用の database に対して回す。この名前は設定で変えられない。向き先を間違えると開発用データが消えるので、間違えようのない形にしている。
- 走り始める前に、実際に接続した database の名前が `_test` で終わるかを確かめ (`app/db/test-database.ts`)、違えば 1 件も実行せずに止まる。
- 各テストは始める前に database を空にするので、ファイルは直列に回す (`fileParallelism: false`)。空にするのは owner の接続で、テスト本体はアプリの role で回す。権限まで本番と同じ条件にするためである。
- `test:db` を同時に 2 つ走らせない。直列になるのは 1 回の実行の中だけで、2 つ目の実行が 1 つ目の行を消す。失敗する場所と数が実行ごとに変わるときは、これを疑う。

## やっていないこと

- カバレッジやテストの数の目標。実行された行数も書いた量も、欠陥が見つかるかどうかとは関係が無い。
- mutation testing。役立つのは純関数のテストだけで、壊れて困るのは実際の DB を通る側である。
- 開発中と CI での e2e。実行に分単位の時間がかかる。
- 移行の前後で保たれるべき件数などをテストにすること。入力の snapshot に依存するので、検証のコマンドとして実行する。それを計算する関数は純関数としてテストする。
