# テスト

階層は道具ではなく **どの失敗を捕まえる担当か** で分かれている。同じ対象に複数の階層がかかるのは
普通のことで、階層どうしは置き換えの関係にない。

| 階層 | 捕まえる失敗 | 道具 | いつ回す |
|---|---|---|---|
| 不変量 | 仕様どうしの矛盾、境界の見落とし | fast-check。純関数のみ | 保存ごと |
| 単体 | 仕様が実装されていない | vitest。純関数と component | 保存ごと |
| schema | 制約が実際には効かない | 実 Postgres。アプリのコードを通さない | commit 前 |
| 経路 | 意図しない動作 | 実 Postgres + loader / action | commit 前 |
| e2e | 画面が出ない、経路が通らない | Playwright。deploy 済みの実物 | リリース判定の前 |

**肝は 1 行目。** 「仕様自体が間違っている」は example-based の test では捕まらない — test は仕様を実装へ
写す装置なので、仕様が誤っていれば test も同じ誤りを再生産する。捕まえられるのは 3 つだけで、
**PBT の法則が反例を出すこと**、**実データを流したときに落ちること**、**移行の保存則**。実際にこの型の
誤りを捕まえた実績はどちらも example-based ではない — 移行の変換が実 dump に対して未知のキーで throw
する形と、「未確定のスロットを生まない」を任意の入力で確かめる PBT。

## 何を test にするか

**docs に「守る」と書いた不変条件は、必ず 1 つ以上の test を持つ。** 逆向きも成り立たせる — test 名を
不変条件の文そのものにして、docs のどの記述を守っているかが読んで分かるようにする。層を書き終えたら
その層の docs を読み直し、対応を確かめる。**これが「test が足りているか」の唯一の判定になる。**

**カバレッジは判定に使わない。** 上がるのは実行された行の話で、assertion が何を弾くかとは独立している。
line / branch が 100% で mutation score が 4% だった実測例がある — 全行を実行しながら、うるう年の分岐の
ような角を 1 つも弾いていない状態が普通に成立する。

**「通るだけの test」を書かない。** 正常系をなぞるだけのものは、境界値・異常系・否定形を足せないなら
書かない。

## 不変量 (PBT)

法則を書く。**「例外を投げない」は不変量として書かない** — 入出力の意味のある制約だけを書く。

効くのはこの形のもの。

- content ⊃ 公開表現 (公開表現は落とすことしかしない)
- 公開表現に未確定 (unknown) のスロットが出てこない
- 公開表現が変えるのは未確定だったスロットだけで、確定している言語には触らない
- 未翻訳が立つのは、両方の言語が値を持ち片方だけが空のときに限る
- 単一値から翻訳対への拡張は機械的に行える (逆向きは判断を伴うので法則にならない)
- 全文の平坦化が content に無い文字列を作らない
- 文の serializer が行の数を変えず、リンクの行き先は許した形のものしか返らない
- 一度保存を通った文は、編集画面に出して保存し直しても同じ木になる
- 衝突の差分が挙げた field を全部取り込むと、差分が空になる (差分と取り込みは型では結べない)
- サイトコンテンツの描画が markdown で書けない要素を出さない (許可リストを持たないことの言い換え)
- サイトコンテンツの変換が生 HTML を残さず、非空の本文を空にしない
- 検索行を 2 度作り直すと同じ行になる

arbitrary は毎回書かず `arbitraries/` に集約する。`fc.sample` で生成例を見て、入力空間がドメインを
覆っているかを目で確かめる。反例は shrink された形が debug の起点になる。

## 単体

純関数と component。ミリ秒で完走する速度を保ち、watch モードで保存ごとに回す。

test 名は `<対象>_<条件>_<期待結果>` が読み取れる文にする。describe / it の入れ子は浅く保ち、
ネストで条件分岐を表現しない。

## schema

**アプリのコードを通さない。** insert を直接呼び、制約が弾くことだけを見る。書き方は
「制約が無ければ通ってしまう操作が弾かれる」の形にする。

「別の identity が既に持っているラベルを拒む」「同じ identity に primary を 2 つ置けない」「取り下げた版と
その番号が残る」「draft を破棄すると変更エントリ・undo・コメント・presence が一緒に消える」がこの階層。

## 経路

loader / action を通し、実 DB に対して回す。ここに置くのは **否定形の不変条件** — 部品が個々に正しくても
配線を間違えると破れるもの。

- 未公開の research がどの公開経路からも出てこない
- 版を取り下げると公開画面と検索から同時に消える
- revision の合わない保存が 409 になり、手元の入力が残る
- 変更エントリの初回作成は「無ければ挿入」で、挿入されなかった側が 409 になる
- undo の深さが 10 を超えず、11 件目で最古が落ちる
- 期限の切れた presence が読み取りから外れる (行を消す掃除に依存しない)
- 共有リンクの検証が server 側のデータ取得経路にかかっている (画面の guard だけでは通れない)
- 公開操作が検索行を同じトランザクションで更新する
- admin を外すと、同じ cookie の次の要求で効く (認可を cookie に焼いていないことの言い換え)
- **アプリが繋ぐ role が event を書き換えられず、消せず、TRUNCATE もできない。** これは権限の性質なので、
  「アプリが UPDATE を発行しない」を確かめても意味がない。実際にその role で発行して落ちることを見る

## e2e

**deploy 済みの実物に対して回す。開発中も CI でも回さない。** 実行が分単位なので、回すのはリリース
判定の前に限る。対象 URL は環境変数で切り替え、開発中に確かめたいときだけローカルの proxy に向ける。

ローカルで再現できないのは TLS と Secure cookie だけで、`X-Content-Type-Options` /
`Content-Disposition` / `/files/` の配信 / 8080 の redirect URI はローカルの compose も同じ経路を通る。

**シナリオは doc に先に書く。** ただし画面の形が決まる前に書けるのは「誰が」「何を貫通するか」
「何が成り立つべきか」までで、手順の具体は画面が決まってから足す。

| ペルソナ | 誰 | 認証 |
|---|---|---|
| P-ANON | 未認証の閲覧者 | なし |
| P-PROVIDER | データ提供者 | なし。共有リンクを持つ |
| P-ADMIN | curator | DDBJ アカウント |

画面の形に依存せず決まっている経路:

- P-ANON — 検索 → research → 版 → dataset → ファイルの取得
- P-ANON — 裸の hum ID が最新公開版に解決する。**JS を実行しないクライアントでも**
- P-ANON — 取り下げた版と未公開の research がどこからも見えない
- P-ANON — 版番号を持たない document の slug が恒久的に応答する
- P-PROVIDER — 共有リンク → preview に未確定値のスロットが見える → コメント → LGTM
- P-PROVIDER — private に戻すと読めない / 再度有効化すると同じリンクが戻る / 再発行すると旧リンクが死ぬ
- P-ADMIN — サインイン → draft → 編集 → 公開ゲート → 公開 → 公開画面に出る
- P-ADMIN — 2 つのセッションで同じ draft を編集すると、後の保存が 409 になって入力が残る
- P-ADMIN — draft の中で dataset を作る → experiment を書く → 版の一覧に載っている
- P-ADMIN — 保存 → 履歴から直前を読み込む → 保存し直すと元に戻る
- P-ADMIN — ファイルを upload → 非公開のまま → 公開に倒す → 公開 URL で取れる
- 配信 — 画像と PDF 以外に `Content-Disposition: attachment` が付く
- preview — `X-Robots-Tag: noindex` と `Referrer-Policy: no-referrer` が付く

## mock の境界

**mock してよいのは v2 の外側にあるものだけ。** 内部を mock した瞬間に、test は設計の鏡ではなくなる。

| | 対象 |
|---|---|
| mock してよい | Keycloak (OIDC の redirect と token の検証) |
| mock してよい | S3 (SeaweedFS) |
| mock してよい | DDBJ Search / JGA 申請管理システム DB |
| mock してよい | 時刻・乱数 |
| **mock しない** | **Postgres** |
| mock しない | schema 定義、content の型 |
| mock しない | 内部の関数・module・component |
| mock しない | loader / action |

**Postgres を mock しないのが v2 では特に効く。** 設計の中心が schema の制約と検索行の導出にあるので、
DB を mock すると捕まえたい失敗がそのまま test の外へ出る。loader / action も同じ理由で mock せず、
route ごと組んだ状態で回して、その内側の HTTP だけを境界として mock する。

内部の mock が必要に見えるときは、test ではなく設計を直す。

## test 間の独立性

状態を共有しない。実行順序に依存しない。

- DB を使う 2 階層は 1 つの開発 DB を共有し、各 test が前に空にする。したがって**ファイル並列は切る**
  (`fileParallelism: false`)。空にするのは owner の接続で、アプリが繋ぐ role には TRUNCATE が無い
  ([editing.md](editing.md) の「証跡」)。**test 本体は必ずアプリの role で回す** — 権限まで含めて
  本番と同じ条件にするため
- 直列で 60 秒を超えたら、worker ごとに DB を複製する形に切り替える (`CREATE DATABASE ... TEMPLATE` は
  数十 ms で終わる)
- **test は開発用 DB を空にする。** 開発用データは test の後に入れ直す
  ([development.md](development.md))
- helper と fixture は collection から外すため `_` prefix のファイル名にする

## 実行

```bash
docker compose exec app npm test              # 4 階層すべて
docker compose exec app npm run test:unit     # 不変量 + 単体 (DB 不要)
docker compose exec app npm run test:db       # schema + 経路
```

階層はファイル名で分ける。配置は対象ファイルの隣。

| 名前 | 階層 |
|---|---|
| `*.pbt.test.ts` | 不変量 |
| `*.db.test.ts` | schema と経路 |
| `*.test.ts` | 単体 |
| `tests/e2e/*.spec.ts` | e2e |

## 意図的にやっていないこと

| やらないこと | 理由 |
|---|---|
| カバレッジの目標値 | 実行された行数は、assertion が何を弾くかと独立している |
| mutation testing | 効くのは純関数の階層だけで、壊れて困るのは実 DB を通る側 |
| 開発中と CI での e2e | 実行が分単位。回すのはリリース判定の前 |
| 移行の保存則を test にすること | 入力の snapshot に依存するので検証コマンドとして持つ。ただし保存則を計算する関数そのものは純関数として test する |
| test の量を目標にすること | 書いた量と欠陥の発見に相関が無い |
