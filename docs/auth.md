# ログインと権限

誰がログインでき、何を許されるか、ログインと権限の状態をどこに保存するかをまとめる。公開ページは認証を求めず、ログインしても見える内容は変わらない。共有リンクでプレビューを読む提供者もアカウントを使わない ([editing.md](editing.md))。

## 誰が何をできるか

認証には DDBJ が管理する Keycloak を使い、権限はポータル側で管理する。運用の決まりとして、1 人に 1 アカウントを使い、共有アカウントは使わない (コードでは強制していない)。アカウントを共有すると、操作の記録から誰が操作したかが分からなくなるためである。

- 人を識別するのは Keycloak の `sub` である。名前は表示と操作の記録にだけ使う。変わりうる値で識別すると、名前を変えたときに、権限と操作の記録がその人と結び付かなくなるためである。
- 画面と操作の記録に表示する名前は、本名 (`name`)、無ければ `preferred_username`、それも無ければ `sub` である。名前はログインの時点でセッションにコピーする。そのため、名前を変えた人は次のログインから新しい名前になり、過去の記録は書いたときの名前のまま残る。
- admin かどうかはポータルの PostgreSQL で管理し、Keycloak の role は使わない。realm は他の組織が管理しており、role を使うと、role の付与を依頼することになって、admin の交代にすぐ対応できないためである。
- 権限は、リクエストのたびにサーバーで判定し、cookie には入れない。admin から外せば、次のリクエストから反映される。
- 役割は admin の 1 つだけで、認可のコードは権限 (コード上は capability) の単位で書く。admin はすべての権限を持ち、ログインしていても admin でない人は権限を 1 つも持たない。権限の一覧は `app/auth/capabilities.ts` にある。
- 必要な権限は、操作の名前で指定する。読むだけの画面なら `view-unpublished`、書く画面なら `edit-content` のように指定する。今は結果が変わらなくても、役割を増やすときに、権限を指定する呼び出し元を読み直さずに済むためである。
- 権限の確認は、対象が存在するかを調べるより先に行う。先に調べると、ログインしていない人に、何が存在するかを知らせてしまうためである。
- 認可の結果は 3 通りである。ログインしていなければ、ログインの画面へリダイレクトし、ログインが終わったら元のページに戻す。ログインしていて権限が無ければ、403 を返す (ログインし直しても変わらないのでリダイレクトしない)。権限があれば、処理を続ける。
- 403 の画面には、権限が無いことを表示する。ほかのエラーと同じ「時間をおいて、もう一度お試しください。」にしないのは、待っても結果が変わらないためである。

## セッション

cookie には推測できない値を 1 つだけ入れ、セッションの内容は PostgreSQL の行に保存する。cookie の中身が認可の根拠になる余地を無くすためである。

- 行には、cookie の値そのものではなくハッシュを保存する。行を読めても、その人になりすませないようにするためである。
- ログアウトでは、セッションの行を削除する。そのため、ログアウトはサーバー側ですぐに反映される。ログアウトは POST だけで受ける。他人が用意したリンクや画像で、セッションを終わらせられないようにするためである。Keycloak 側のセッションも終わらせる。
- 有効期限は、最後のアクセスから 7 日と、発行から 30 日の 2 つである。最後のアクセスの時刻は、1 時間より古いときだけ更新する。ページを読むたびに DB に書き込まないためである。
- Keycloak の token は保存しない。token を送る先が無いためである。例外は、Keycloak のセッションを終わらせるときの `id_token_hint` に使う id_token だけである。
- Keycloak の client は public client と PKCE (S256) で、長期の credential を使わない。
- ログイン後の戻り先は、サイト内のパスに限る。検査は、戻り先を組み立てた結果に対して行う。`/..//example.com` はパスとして解釈できても、`Location` に入れると別のホストを指すためである。
- cookie の `Secure` は、Keycloak に登録した redirect URI の scheme から決める。別の設定項目にしないので、本番で付け忘れることが無い。
- セッションの行は失ってもよい。全員がログインし直すだけなので、backup も移行もしない。

## CSRF

書き込みのリクエストは、同じ origin から来たものだけを受け付ける。

- GET・HEAD・OPTIONS 以外のリクエストは、`Sec-Fetch-Site` が `same-origin` か `none` で、`Origin` があるなら `Origin` がこのホストを指すときだけ通す。それ以外のリクエスト (別のホスト、`null`、どちらのヘッダも無い) には、理由を示さずに 403 を返す。ただし、ページを表示する route に別のホストか `null` の `Origin` で送られたリクエストには、React Router 自身の検査が先に 400 を返す。403 のときも 400 のときも、書き込みはしない。
- `Origin` と比べる相手のホストは、proxy が app に渡す `Host` である。proxy は、`Host` を `HUMANDBS_AUTH_REDIRECT_URI` の host に固定する ([deployment.md](deployment.md) の「構成」)。途中の中継が `Host` を書き換えても、ブラウザがアクセスしたアドレスと比べるためである。
- 検査は、root の middleware (`app/auth/csrf.ts`) の 1 か所で、全 route に適用する。React Router 自身の検査はページを表示する route にしか適用されず、`SameSite=Lax` の cookie は同じ登録ドメインの別のサブドメインからの POST にも付くためである。

## admin の追加と削除

admin の追加は招待リンクで行い、削除は管理画面のトップの「管理者」で行う。最初の 1 人だけは CLI (`npm run admin:grant`) で追加する。画面を使えるのは admin だけなので、admin が 1 人もいない DB では画面から追加できないためである。CLI に渡す `sub` は、admin でない人が `/admin` を開くと表示される (この画面を開くにはログインだけが要り、この画面に表示するのは本人の `sub` だけである)。

- 招待リンクは、admin が管理画面のトップで作り、追加する相手にメールや Slack で渡す。追加する相手がリンクを開いて Keycloak でログインすると、そのまま admin になり、管理画面のトップへ移る。`sub` と名前は Keycloak から取得し、誰も `sub` を手で入力しない。
- 招待リンクは 1 回だけ使え、作ってから 7 日で使えなくなる。リンクの値はハッシュで保存し、作ったときに 1 度だけ表示する。セッションと同じく、DB を読めてもリンクを作り直せないようにするためである。使われる前の招待リンクは、どの admin も削除できる。
- 招待は、ログインしている人がリンクを開いたときに使われる。チャットのリンクのプレビューのように、人が開いていない読み込みは、ログインしていないリクエストである。そのため、ログインの画面へリダイレクトされるだけで、招待は使われない。すでに admin の人が開いたときも、招待は使わずに残す。
- 自分自身と、最後の 1 人は画面から削除できない。自分を削除するとその場で画面を操作できなくなり、最後の 1 人を削除すると画面から誰も追加できなくなるためである。CLI (`npm run admin:revoke`) では、どちらも削除できる。
- 一覧には、名前・`sub`・追加した日時・最後に使った日時を表示する。名前は Keycloak の名前 (上の「誰が何をできるか」にある、表示する名前) である。名前と最後に使った日時は、その人がログインしたときと、画面を使っているあいだ 1 時間に 1 回、更新する。名前は Keycloak の側で変わり、使われなくなったアカウントは最後に使った日時から見つけるためである。セッションの行はログアウトや期限で消えるので、日時は管理者の行に保存する。
- 追加と削除は操作の記録に残す ([publishing.md](publishing.md) の「操作の記録」)。招待による追加の操作者は、招待を作った人である。CLI による操作の記録には、予約された操作者の値を入れる。

## やっていないこと

- admin 以外の役割。必要になったことが無い。認可は権限の単位で書いてあるので、役割を増やすときも形は変わらない。
- データ提供者を認可の主体にすること。認可は権限の単位だけで行い、申請管理システムの DB から所有関係を導くことはしない。
