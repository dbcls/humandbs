# ログインと権限

誰がログインでき、何を許されるか、その状態をどこに置くかをまとめる。公開ページは認証を求めず、ログインしても見える内容は変わらない。共有リンクでプレビューを読む人もアカウントを使わない ([editing.md](editing.md))。

## 誰が何をできるか

認証には DDBJ が管理する Keycloak を使い、権限はポータルが決める。1 人に 1 アカウントを使い、共有アカウントは使わない。共有すると、操作の記録から誰が行ったかが分からなくなるためである。

- 人を識別するのは Keycloak の `sub` である。名前は表示と操作の記録にだけ使う。変わりうる値で識別すると、名前を変えたときに権限と記録の主体が切れるためである。
- 画面と操作の記録に表示する名前は、本名 (`name`)、無ければ `preferred_username`、それも無ければ `sub` である。名前はログインの時点でセッションにコピーするので、名前を変えた人は次のログインから新しい名前になり、過去の記録は書いたときの名前のまま残る。
- admin かどうかはポータルの PostgreSQL で管理し、Keycloak の role は使わない。realm は他の組織が管理しており、付与を依頼することになって交代にすぐ対応できないためである。
- 権限は要求のたびにサーバーで求め、cookie には入れない。admin から外せば、次の要求から効く。
- 役割は admin の 1 つだけで、認可のコードは権限 (コード上は capability) の単位で書く。admin はすべての権限を持ち、ログインしていても admin でない人は 1 つも持たない。権限の一覧は `app/auth/capabilities.ts` にある。
- 求める権限は操作の名前で指定する。読むだけの画面なら `view-unpublished`、書く画面なら `edit-content` のように指定する。今は結果が変わらなくても、役割を増やすときに呼び出し元を読み直さずに済むためである。
- 権限の確認は、対象が存在するかを調べるより先に行う。先に調べると、ログインしていない人に何が存在するかを知らせてしまうためである。
- 認可の結果は 3 通りである。ログインしていなければログインの画面へ送り、終わったら元のページに戻す。ログインしていて権限が無ければ 403 を返す (ログインし直しても変わらないのでリダイレクトしない)。権限があれば処理を続ける。

## セッション

cookie には推測できない値を 1 つだけ入れ、セッションの内容は PostgreSQL の行に置く。cookie の中身が認可の根拠になる余地を無くすためである。

- 行には cookie の値そのものではなくハッシュを保存する。行を読めても、その人になりすませないようにするためである。
- ログアウトは行を削除することで、サーバー側ですぐに効く。ログアウトは POST だけで受ける。他人が置いたリンクや画像でセッションを終わらせないためである。Keycloak 側のセッションも終わらせる。
- 有効期限は、最後のアクセスから 7 日と、発行から 30 日の 2 つである。最後のアクセスの時刻は 1 時間より古いときだけ更新する。ページを読むたびに DB に書き込まないためである。
- Keycloak の token は保存しない。送る先が無いためである。例外は、Keycloak のセッションを終わらせるときの `id_token_hint` に使う id_token だけである。
- Keycloak の client は public client と PKCE (S256) で、長期の credential を使わない。
- ログイン後の戻り先はサイト内のパスに限り、検査は組み立てた結果に対して行う。`/..//example.com` はパスとして解釈できても、`Location` に入れると別のホストを指すためである。
- cookie の `Secure` は、Keycloak に登録した redirect URI の scheme から決める。別の設定項目にしないので、本番で付け忘れることが無い。
- セッションの行は失ってもよい。全員がログインし直すだけなので、バックアップも移行もしない。

## CSRF

書き込みの要求は、同じ origin から来たものだけを受け付ける。

- GET・HEAD・OPTIONS 以外の要求は、`Sec-Fetch-Site` が `same-origin` か `none` で、`Origin` を送るならそれがこのホストを指すときだけ通す。それ以外 (別のホスト、`null`、どちらのヘッダも無い) は理由を示さずに 403 を返す。
- 検査は root の middleware (`app/auth/csrf.ts`) で全 route に 1 か所でかける。React Router 自身の検査はページを表示する route にしか効かず、`SameSite=Lax` の cookie は同じ登録ドメインの別のサブドメインからの POST にも付くためである。

## admin の追加と削除

admin の追加と削除は CLI (`npm run admin:grant` と `admin:revoke`) で行い、管理画面には追加や削除の画面を置かない。

- めったに行わない操作で、実行するのは DB の資格情報を持つ人なので、HTTP の認可を新たに作る理由が無いためである。CLI による操作の記録には、予約された操作者の値を入れる。
- 追加に使う `sub` は、admin でない人が `/admin` を開くと表示される。この画面はログインだけを求め、表示するのは本人の `sub` だけである。

## やっていないこと

- admin 以外の役割。必要になったことが無い。認可は権限の単位で書いてあるので、増やすときも形は変わらない。
- 管理画面からの admin の追加と削除。めったに行わず、CLI で足りる。
- Keycloak の role で権限を表すこと。realm は他の組織が管理している。
- セッションに access token や refresh token を保存すること。送る先が無い。
- データ提供者を認可の主体にすること。認可は権限の単位で閉じ、申請管理システムの DB から所有関係を導くことはしない。
