# データモデル

Postgres が唯一の store で、編集中のものと公開済みのものを両方持つ。別の検索エンジンに投影しない。
派生値は計算ロジックの側が SSOT で、値はいつでも作り直せる。

ファイルだけは第 2 のストア (S3) にあり、公開状態もそちら側が持つ。

```
Postgres
  research / experiment / dataset    identity + content + draft + pin ledger
  site content                       document / news / alert
  review                             comments (the share link is a draft column)
  external cache                     CAU / hum-to-accession / accession dates
  event                              append-only
  search rows                        full-text columns + facet rows (published only)
        |
        +-- loader / action --> SSR pages / editing / preview
        +-- resource route   --> public JSON API
        |
        v
S3 (SeaweedFS)
  public bucket / private bucket      membership IS the published state
  data files + assets referenced from article bodies
```

schema は `app/db/schema/`、content の型は `app/content/types.ts`。schema が固まるまで migration
file を持たず、`npm run db:push` が定義をそのまま DB に反映する。変えたら開発用データを作り直す。

## content と行

**content はすべて JSONB で持つ。** research content も、dataset content (experiment の列と値スロットを
含む) も、draft の変更エントリも、その派生元のスナップショットも。**published と draft で表現を変えない**
ので、公開は値のコピー、3-way 差分は同じ型どうしの比較で済む。

値スロットを列に割らないのは、**どの列が有効かが catalog の型に依存する**ため。翻訳対は ja/en、数値は
正準単位の値と入力単位、語彙は語彙値の id を持ち、どれが埋まるかはキーの型で決まる。列に割ると NULL
許容の列が並んで整合を schema で保証できないが、JSONB なら値の型の側で「数値スロットに ja/en は無い」を
落とせる。値の状態も同じ理由で値の型に入り、翻訳対では言語ごとに 1 つずつ入る (「値の状態」)。

行にするのは次の 5 つで、どれも content ではない。

| 行 | なぜ行なのか |
|---|---|
| 検索用の行 | facet を集計し、全文検索の index を張る |
| pin 台帳 | ラベルの一意性を DB の制約として守る |
| catalog と語彙 | キーの型の SSOT で、語彙値への参照整合性が要る |
| 外部キャッシュと ICD10 の辞書 | 取り込みが書き換える。curator の編集対象ではない |
| event・コメント・job | 追記されるもの |

**experiment は dataset content の中の順序つきの要素**で、独立した行ではない。identity はその要素が
持つ代理キーで、コメントの宛先はこの id で指す。集計のために行にする必要は無い —
facet も全文検索も検索用の行が公開分だけを別に持つ。

## identity と label

内部の同一性と、外に見せる名前を混ぜない。research と dataset は抽象的な identity を持ち、**hum
ラベル・公開版番号・dataset id はそこに後から pin する label**。label が無くてもオブジェクトを作れ、
label が変わっても参照が壊れない。

ラベルの一意性の規則は 3 系統で共通だが、置き場は形の違いで分かれる。

| ラベル | 置き場 | 一意性 |
|---|---|---|
| hum ラベル / dataset id | `label_pin` | 種別と文字列で全体に一意 |
| 公開版番号 | `research_version` | research の中で一意。公開状態を併せ持つ |

守る不変条件:

- **可視性は公開状態にある版の集合から判定し、版番号の大小比較で行わない。** 番号に gap があると
  `v1..latest` の列挙は未公開の版を素通しする
- **pin を外したラベルは再利用できる。欠番を作る規則を持たない。** hum 番号は JGA 申請管理システムに
  人手で入力される自由文字列が起点で typo の実績があるため、訂正は日常の操作になる
- **dataset id から読むのは「ポータルが発行したものか」の 1 点だけ。** ポータルが発行する id は `hum` で
  始まり、外部アーカイブの accession はどれも別の prefix を持つので、**primary の綴りの頭**でこの区別が
  付く。それ以外の構造 — 版番号・トークン・通し番号 — には意味を読み込まない。この 1 点を読むのは、
  dataset がファイル選択を持てるかがそこで決まるため (「ファイル」)

**1 つの identity に複数の id が pin される。1 つが primary で、残りが secondary。** primary と
secondary を合わせて台帳で一意で、一意性と再利用の規則はどちらにも同じく適用される。旧 id への外部参照を
解決し続けるための仕組み。primary が identity ごとに 1 つであることは部分 unique index が守る。
**ポータル発行かどうかの判定に使うのは primary だけ** — 移行が既存の NHA ID を secondary に残すので、
secondary を混ぜると外部アーカイブの dataset までポータル発行に見える。**primary が未 pin の間は外部
として扱う。**

**どちらの系統も pin した時点で台帳に載る。公開を待たない。** hum ラベルは research identity に付く
(research は draft の親なので、draft が何本あっても hum は 1 つ)。dataset id は dataset identity に付き、
draft が新規に追加した dataset は identity ごと draft と運命を共にするので、draft を破棄すればその pin も
消えて accession は再び使える。同じ accession を 2 つの draft が pin しようとしたら 2 つ目が弾かれる —
台帳の一意性がそのまま収束を強制するので、公開時に identity を寄せる処理は持たない。

公開時に載せる形は採れない。公開を止める検査が「その版が持つ全 dataset に dataset id が pin されて
いる」を台帳に問うので ([publishing.md](publishing.md))、載せる時期を公開時にすると検査の相手が draft 側の
「予定の id」になり、一意性の検査が 2 箇所に分かれる。

## research / experiment / dataset

```
Research (identity)                    <- hum label pinned in the ledger
|
+-- ResearchVersion (number)  --> ContentSnapshot (immutable)
|     published versions only            body + ordered list of dataset identities
|
+-- ResearchDraft (mutable)            <- unpublished working copy; several allowed
|     +-- content
|     +-- note                            admin only; never reaches preview
|     +-- parent (ContentSnapshot)        detects "derived from a stale snapshot"
|     +-- change entries                  copy-on-write for touched datasets
|     +-- new dataset identities          enter the ledger on publish
|
+-- Dataset (identity)                 <- dataset id pinned in the ledger
      +-- content (JSONB)              <- experiments live in here, ordered
```

**dataset は versioning しない。履歴も持たない。** identity と、公開されている content を 1 つ持つ。
dataset の実体 (アーカイブに登録されたデータ) は不変で、変わるのは記述の訂正・充実・表記統一なので、
最新が正しい。

**ただし公開が置き換えた dataset content は証跡の側に丸ごと残す** (`replaced_dataset_content`)。履歴では
ないので番号を持たず、公開版から辿れず、画面にも出ない — 残す理由は、上書きされた記述を復元できる先が
他に無いことだけ (draft の undo は公開した時点で draft ごと消える)。差分ではなく丸ごとにするのは 1 件が
平均 8 KB と小さいためで、深さの上限は持たない (積まれる回数はその dataset を含む公開の回数)。

**ContentSnapshot が持つのは dataset identity の順序つき列だけで、experiment の集合も順序も持たない。**
したがって過去版を開くと、dataset の一覧は当時のもの、各 dataset の記述と experiment の一覧は最新になる。
版を公開した後にその dataset へ追加された experiment も、過去版から辿った dataset のページに出る。

**experiment は dataset content の中にあり、関係は 1 dataset : n experiment。** dataset ごとに違う値は
experiment の値スロットが持つので、どの dataset の experiment かは従属関係そのものが表す。experiment に
版は持たせない。

**dataset は 1 つの research に従属する (composition)。** 複数 research から参照される dataset は無い。

判定はすべて 1 つの根拠に閉じる。

| 判定 | 根拠 |
|---|---|
| dataset が公開されているか | `dataset_content` に行があるか |
| research の過去版から辿れるか | その版の ContentSnapshot が持つ dataset identity の列に入っているか |
| experiment が公開画面に出るか | 属する dataset が出ているか |
| 検索用の行に載るか | 公開版が参照しているもの |

**どの公開版からも参照されなくなった dataset (孤児) は削除しない。** identity の行は残り、公開 content の
行だけが消えるので、公開ページには出ず管理画面から復旧できる。research 自体を削除したときだけ、
composition に従って配下の dataset も消える。

**research 版のページには experiment を出さない。** dataset の一覧を出し、experiment は dataset のページで
見る。

## 言語

**公開の単位は research の版であって言語ではない。** ContentSnapshot は ja/en を一体で持つ。版は
「その時点の研究の姿」であり、翻訳は同じ姿の別表現なので、言語で割れると版の意味が壊れる。

**片言語が未翻訳のまま公開できる。** 英語版がそもそも存在しない研究が実在するので禁止は採れない。
代わりに公開ゲートが未翻訳を列挙して確認させる ([publishing.md](publishing.md))。

**未翻訳は欠損ではなく状態として扱い、値から導出する。** 翻訳対の field で**両方の言語が値を持ち、
片方だけが空**なら未翻訳。両方空は未入力で、unknown と該当なしはそれぞれ別の状態 (「値の状態」)。
状態が食い違うとき — ja が値を持ち en が unknown — は未確定として扱い、未翻訳には数えない。同じ 1 つの
欠けが公開ゲートの列挙に 2 度出ないようにするためで、これが空と unknown を分けたことの帰結になる。
フラグを別に持たないので実態とずれない。

field は 3 種に分かれ、**分類は content の型が持つ** (`app/content/types.ts`)。一覧としてこの doc に
持たない。

| 分類 | 基準 | 翻訳状態 |
|---|---|---|
| 言語を持たない単一値 | 原典が 1 つの表記しか持たない (数値・語彙値・accession・論文タイトル) | 持たない |
| 翻訳対 | 言語ごとに正しい表記が存在する (本文・要約・機関名・研究課題名) | 持つ |
| 言語ごとに別の値 | 対応する外部リソースが言語ごとに別に存在する。**URL だけ** | 持たない |

**表示する言語を選ぶのは `app/i18n/locale.ts`** で、まず欲しい言語の状態が答えを決める。

- **該当なしはその言語の答えとして返り、もう一方を見ない**
- **unknown もフォールバックしない。** 問いなので、もう一方の言語で埋めると preview から問いが消える。
  公開ページでは公開表現が先に空へ倒しているので、下の規則が代わりに効く
- **空の翻訳対はもう一方の言語にフォールバックし、未翻訳であることを添える** — 日本語しか無い研究も
  英語ページに出す必要があるため
- **言語ごとに別の値はフォールバックしない** — 2 つの側は別のリソースで、片方を出すと「これが訳です」と
  言っていない場所へ読者を送ることになる
- **上流のキャッシュ (CAU) は状態を持たず、未翻訳としても数えない** ので、専用の関数で解決する

**単一値から翻訳対への拡張は機械的に行える。これを不変条件として持つ。** 原典の言語に値を入れ、もう
片方は空のままにするだけで判断が要らないので、迷う field は単一値に寄せてよい。逆向きは ja/en の
どちらを採るかの判断を伴う。**両言語に同じ値をコピーしてはいけない** — 導出が全件を翻訳済みと判定する。

## 値と文

**書式を持つのは文だけ**で、境界は catalog のキーの型が決める (「catalog と語彙」)。値 — accession・
語彙・数値・疾患・単一値と、experiment の表示ラベル・研究題目・提供者名・機関名・研究課題名・研究費の
名称 — は書式を持たず、リンクも単位も語彙のラベルも型から導出して描画側が作る。**疾患だけは値が自分の
テキスト (呼称) を持つ**が、これも書式を持たない (「ICD10」)。文は型が `text` のキーと、
研究概要 (aims / methods / targets)・短い要約・リリースノート。

**一覧に出る要約 (`listingSummary`) は、詳細から導出しない。** 研究一覧の 3 列 — 解析手法・種別・
参加者 — はこれが持ち、curator が書く。**詳細の値を並べても作れない**: 詳細は experiment ごとに立つが
要約は研究 1 件につき 1 つで、語彙も違う。「配列決定 発現 メチル化」は分類語で、同じ研究の experiment が
名乗るのは `RNA-seq` や `WES`。「19＋4＋96症例」は人が足し合わせた表記になる。**導出した既定値を置く道は
持たない** — ほぼ全件が上書きされることになり、上書きされた値と導出のままの値が見分けられなくなる。

**文は行と span の木で持つ。行の列で、行は span の列、span は文字列か文字列と URL の対**
(`app/content/types.ts`)。**それ以外の構造は表現できない** — 見出し・表・箇条書き・順序リスト・強調・
コード・引用・上付き / 下付き・生 HTML はどれも入らない。理由は 3 つ。

- **許す集合が型そのものになる。** markdown 文字列で持つと中身は parse するまで分からず、許可集合が
  保存時の検査と表示時の sanitize の 2 箇所に出る。それ自体が二重管理になる
- **生 HTML の sanitize が要らない。** ポータルと同じ origin で描画する以上避けられなかった stored XSS の
  経路が消える。残るのはリンクの URL だけで、そこは scheme の検査で足りる
  ([public-pages.md](public-pages.md))
- **markdown の escape が値から消える。** v1 の値には `call rate \< 0.95` のように escape が焼き込まれて
  いて、値として読むと `\<` が混じる

**入力は markdown のまま受け、保存の時点で木に落とす。落とせない記法はエラーで弾き、黙って消さない。**
表示側だけで落とすと、curator は書けたつもりのまま公開まで進む。**単一の改行は行の区切り**で、markdown が
読むような空白ではない — 公開されている値はそこで項目を並べている。

**出力は 3 方向** (`app/content/richtext.ts`)。画面は木をそのまま描き、plain text は public API と全文
検索の列が使い、markdown は編集画面に返すときに使う。**HTML 文字列を作る経路は持たない。**

翻訳対の規則は文でも同じで、**行に文字が 1 つも無ければ空**として未翻訳を導出する。

**数値のキーは数を 1 つではなく列で持つ。** v1 は 1 つのセルに表を書いていた —
`常染色体: 5,961,600 SNVs` の次の行に `X染色体: 147,353 SNVs`、`GWAS: 123 MB` の次に
`Phenotype データ: 2.4 MB`。**半分以上のセルがそうなっている** (バリアント数の 77%、データ量の 56%)。
数を 1 つしか持てないと、こういうセルは文として持つしかなく、文は絞り込めないので、**絞り込むための
数値キーが同じ概念の隣にもう 1 本立つ** — 同じ事実が 2 か所に住み、curator は 2 か所を直すことになる。

**数のそれぞれが「何の数か」と「但し書き」を持つ。**前者はゲノムの部位・データ製品の名前のような、
その数を他と分けるもの。後者は `平均`・アセンブリ名のような、数を修飾するが数ではないもの。
**1 つしか数を持たないキーはどちらも持たない**ので、大半のキーの姿は変わらない。

検索側は元からこの形だった — `search_facet_number` は `(doc, key, value)` の 1 値 1 行で、
複数の数を持つ dataset を最初から想定している (「検索用の行」)。**足りていなかったのは持ち方だけ。**

**サイトコンテンツにはこの規則を当てない** (「サイトコンテンツ」節)。ガイドラインとポリシーでは見出しと
表が文書の構造そのものなので、markdown 文字列のまま持ち、CommonMark と GFM の表を許す。版も pin も
持たず、公開表現・公開検索・public API のどれも対象にしないので、規則が 2 系統あっても交わらない。
**生 HTML はどちらの規則でも持たない**ので、許可リストの sanitize はどちらにも要らない。

## 値の状態

値は 4 通りの見え方を持つ。research content の名前つき field も、catalog のキーの下に付く dataset と
experiment の値スロットも、同じ型で同じ扱いをする。

| 見え方 | 意味 | 公開画面 | 検索・facet | preview |
|---|---|---|---|---|
| 値あり | | 値を出す | 載せる | 載せる |
| 空 | 誰もまだ触っていない | 出さない | 載せない | 出さない |
| unknown | 値があるはずだが確定していない | 出さない | 載せない | 状態を出す |
| 該当なし | 値が存在しないことが確定している | 項目を出し、該当なしを表す表示を置く | 載せない | 状態を出す |

値スロットではキーの不在が 5 番目として加わり、「その項目がその実験では話題にならない」を表す。
項目ごと出さない。

**空は独立した状態ではなく「値ありで中身が空」として持つ。** 状態にすると「空の状態」と「空の値」の
2 通りができ、どちらで書くかの問題が生まれる。必須項目の検査は空を見て行い、unknown は curator が明示的に
立てた「提供者に聞いている」の印になる。両者を同じものにすると、公開ゲートが列挙すべきものと、そもそも
入力が始まっていないものが混ざる。

unknown と該当なしの違いは、解決されるべきかどうか。unknown は公開前に潰す対象で、該当なしは確定した
情報なので公開ゲートの列挙に載らない。

**状態は言語ごとに持つ。** 翻訳対と URL は ja と en がそれぞれ独立に 4 通りを取り、言語を持たない値
(単一値・accession・語彙値・数値) の状態は 1 つ。片方の言語だけが確定していない状態が実在するため —
公開前の版には `ご教示ください(英語タイトル)` のように英語表記そのものを聞いているものがある。

**状態の置き場は 1 つに保つ。** 翻訳対の外側に共通の状態を置いて内側にも言語ごとの状態を持つ形は
採らない。値スロットも同じで、状態は値 (`ContentValue`) の中にあり、キーと値を結ぶ側には無い。

**該当なしの表示文字列は値として持たない。** 状態として持ち、表示は描画側で生成する。値として書かせると、
該当なしの表明と、表を使い回したときの埋め草が文字列から区別できなくなる。値が無いこと自体は言語に
依存しないので、片方の言語だけ該当なしにする意味は無く、UI は両言語にまとめて立てる。

## catalog と語彙

dataset と experiment の値スロットのキーは catalog (`content_key`) が持ち、統制語彙の安定した id を
identity とする。catalog は表示ラベル (ja/en)・値の型・表示順を持つ。

- **キーは dataset に付くか experiment に付くかの scope を持つ。** 公開区分やデータ種別は dataset の値、
  分子データの記述は experiment の値で、どちらも同じ形のスロットになる
- **rename は表示ラベルの変更であり、データに伝播しない**
- **表示順は catalog が持つ。** データから復元できるグローバルな順序は存在しない
- **数値型のキーは正準単位と、入力で選べる単位の集合を持つ。** 保存の時点で正準単位へ換算し、
  **入力で選ばれた単位は換算後も残す** — 換算を後から直すときに元の入力が要り、**画面に出るのも
  打たれたほう**になる (誰も `1351.68 GB` とは書いていない)。**換算は `app/content/units.ts` の
  1 箇所だけ**にあり、同じ量を測る単位どうしのときしか通らない。**データ量は 1024 で刻み、配列の
  長さは 1000 で刻む** — 同じ接頭辞に見えて別物で、`GB` はファイルシステムの表示から書かれ、`kbp` は
  塩基を千数えたもの。1 つの規則で両方を扱うと、量が 7%、リード長が 2.4% ずれる
- **正準単位を持たないキーもある。** 数えるキーの単位は尺度ではなく「何を数えたか」(`SNVs` / `indels` /
  `x`) なので、換算する先が無い。書かれた単位がそのまま単位になる
- **キーの追加は明示的な操作。** 一致しない文字列を打った拍子に catalog へ登録される経路を持たない
- **併合は値の一致だけで判定しない。** 同一 experiment 内での共起衝突を検査する

**キーの型が facet を決める。** 型が語彙・数値のキーが facet の source になり、それ以外は自由文。
したがって**キーの型を変えることが facet を増やす操作**で、そこだけが開発の作業になる。

**例外は日付 2 つだけ。** 公開日と更新日は検索用の行の列であってキーではないが、絞り込みパネルには出る
([public-pages.md](public-pages.md) の「絞り込み」)。パネルの側が名指しで 2 つを持ち、catalog には何も
足さない。

**facet のカテゴリはラベルを持たなくてよい**。そのときは見出しの無い箱として描かれる。ラベルは両言語
そろっているか、どちらも無いかのどちらか — 片方の言語でだけ見出しが出る箱は、読者が言語を切り替えると
形が変わる。

| 誰が | 何を |
|---|---|
| admin | 自由文キーの追加・編集・削除・並び替え、facet のラベル・カテゴリ・並び、公開ページに出すかどうか、語彙値の追加・rename・非活性化 |
| 開発 | キーの型を変えること、ICD10 の辞書の取り込みと更新、語彙値の併合 |

管理画面 (`/admin/catalog`) が守ること:

- **使われているものは消せない。** キーは公開・draft のどちらかの content が値を持てば使用中で、
  語彙値は値が指していれば使用中。語彙値は代わりに**非活性化**する — 入力の候補から外れるが、既に
  指しているデータからは引ける
- **すべての語彙値は編集できる。読み取り専用の語彙を持たない。** 外部標準を語彙として取り込むと、
  標準側の誤りも標準に無い綴りも直す経路が無くなる (「ICD10」)
- **catalog を書き換えたら検索行を作り直す** (「検索用の行」)。どの変更が行に届くかを操作ごとに
  判断させると、いつか判断を忘れる

**キーの code と語彙値の code はアドレスに出る。** 絞り込みは `?q=` に `platform:hiseq-2500` の形で
載るので ([public-pages.md](public-pages.md) の「一覧と検索」)、**組み込みの検索 field と同じ綴りの
code は作れない**。語彙値の code は外部標準の書き方 (`C349`) をそのまま使えるが、検索式にクオート
無しで書ける文字に限る。

語彙値のラベルは **en 必須・ja 任意**。日本語表記の要否は facet 単位では決まらない (同じ facet の中に
`メチル化アレイ` と `WGS` が同居する) ので、ja が空であることは欠損ではなく、公開ゲートの未翻訳の
列挙にも載せない。

**語彙は原則フラット。階層を持つのは ICD10 だけ。** 4 桁分類の値は 3 桁分類の根にぶら下がり、
**facet が数えるのは根だけ**になる ([public-pages.md](public-pages.md) の「絞り込み」)。木を持たせるのは
このロールアップのためで、**3 桁を根、4 桁をその子とする 2 層**。章とブロックは持たない — 標準の
配布物が章の名前を持たず、絞り込みに要るのは 3 桁と 4 桁の関係だけ。**5 桁は語彙値にならない**
(「ICD10」)。

**語彙値は、製品を指すものだけ「作った会社」を別に持つ** (`vocabulary_term.maker`)。プラットフォームの
値は上流が会社名と機種名で持っていて、`Illumina NovaSeq 6000` はその 2 つを繋いだもの。繋いだ後の
文字列からは割り直せない — 会社名の 3 分の 1 が空白を含む (`10x Genomics` / `Oxford Nanopore
Technologies`) ので、先頭の 1 語という規則が立たない。**ラベルは会社名を含んだ全体のまま**で、
検索・CSV・public API・絞り込みの照合はそちらを見る。分けるのは描くときだけ
([ui.md](ui.md) の `TermLabel`)。

**これを親子で持ってはいけない。** facet の集計は `ancestor_ids` の根で数えるので
(`app/search/counts.server.ts`)、会社名を親の語彙値にすると絞り込みパネルに並ぶのが機種ではなく
会社名になり、フラットな語彙は子を開く道を持たない。**`maker` が列であって木でないのはこのため。**

**1 つの語彙値は 1 つのものを指す。** プラットフォームの上流は自由文から機械が読み出した層で、
`HiSeq 2500/3000, NovaSeq 6000` のように 3 台を 1 つの値にしたものが混ざっている。移行はこれを機種
ごとに分け、綴りのゆれを寄せる (`migration/facets.ts`)。**区切りに見える記号は名前の一部でもある**
(`HiSeq X Ten` / `DNBSEQ-G400RS`) ので、分け方は表に書き出してあり、文字で判定しない。**寄せるのは
1 つの名前の書き方が違うものだけ** — `Ion S5` と `Ion S5 XL` のように別の製品でありうるものは、
判断の根拠が dump に無いので残す。併合は curator の操作になる。

**語彙値の表示順 (`vocabulary_term.position`) は、移行が「会社名 → ラベル」で振る。** 上流が値を
言い出した順は順序ではない。これを読むのは編集フォームの候補と、一覧の 1 つのセルが複数の値を持つとき
([public-pages.md](public-pages.md) の「一覧と検索」)。**絞り込みパネルはこれを読まない** — パネルは
件数の多い順に並ぶ。

## ICD10

**疾患は、識別子と 2 種類の名前を持つ値の並び**として持つ。1 つの値は語彙値への参照の並びと、呼称の
ja / en でできていて、**識別子を 1 つも持たない値が正しい状態**になる。分類に載っていない疾患が
実データにあり、それを登録できないポータルにはできない。

**呼称 (name) と見出し語 (label) は別のもので、責務が違う。**

| | 出所 | 誰が持つか | 何に使うか |
|---|---|---|---|
| 呼称 | 記事に書かれた名前 | **値** | 表示の既定・全文検索 |
| 見出し語 | 分類が持つ名前 | 語彙値 | 呼称が無いときの表示・全文検索・`/admin/catalog` |

**呼称を値の側が持つのは、同じコードが研究ごとに違う書かれ方をするため。**それは表記ゆれではなく、
`Colorectal cancer with liver metastasis` のようにその研究が対象とした集団の定義になっている。語彙値に
持たせると潰れる。**呼称は寄せない** — 記事がそう書いているものを、ポータルが書き換えない。

**識別子の体系は語彙 set そのもの。**ICD10 の語彙値は code がコード、ラベルが分類の見出し語で、他の
語彙と同じ形をしている。**1 つの値が複数の set の語彙値を指せる**ので、体系を足すときも set が 1 つ
増えるだけで値の形は動かない。**1 つの欄に「ICD10 を持つ疾患」「持たない疾患」「別の体系の疾患」が
混在する**ことが前提になる。

**コードは 3 桁分類と 4 桁分類だけを持つ。**書かれ方は原文の側で揺れているので、正規化して受ける。
routeA (移行) と routeB (申請管理システムからの下書き) は同じ規則を通る。

1. `ICD10` / `ICD-10` / `ICD 10` を同じものとして読む
2. **中身が `code` だけの注記は見出しであって疾患ではない。**`40疾患(ICD10 code)` は次の行から
   始まる列挙を宣言していて、その列挙は `ICD10` を繰り返さず裸の括弧にコードを書く。**宣言を見た
   後は、その欄の残りの括弧もコードとして読む**
3. 角括弧の中は捨てる — `C20 [NG80]` の `NG80` はガイドライン番号であってコードではない
4. カンマ・全角読点・スラッシュ・空白で分ける
5. **ハイフン範囲は、同じ英字で展開後 10 コード未満なら展開する** (`C18-20` → C18, C19, C20)。
   それ以外は捨てる — `Q00-Q99` はブロックを名指ししていて疾患ではなく、展開すると 1 つの疾患が
   100 コードに膨らむうえ、**3 桁分類は連番ではないので存在しないコードが生まれる**
6. 点を落とし、大文字に揃える
7. **辞書に当たるまで末尾を削る** (5 桁 → 4 桁 → 3 桁)。実データの 5 桁は打ち間違いではなく
   ICD-10-CM で、WHO ICD-10 では書けない疾患をアメリカ版で書いたもの。丸めても呼称が残る
8. **3 桁でも当たらなければコードを捨てる。**呼称だけの値になる

**3 桁を 4 桁へ広げない。**`C34` と書かれていたら `C34` のまま持つ。細分は書き手が選ばなかった情報で、
機械が補うと嘘になる。

**識別子を持たない値は facet の行を作らない。**絞り込みの単位は語彙値なので、指す先が無い値は数えられ
ない。**全文には呼称が入る**ので、検索窓からは引ける (「検索用の行」)。

**分類の本体は語彙とは別の辞書 (`icd10_reference`) として持つ。** (コード, 英語名, 日本語名) だけの
表で、使い道は 3 つとも編集の側にある。

- 語彙値を作るときの **見出し語の初期値**
- **コードの存在検査** — 上の規則の 6 と 7 がこれを引く
- `/admin/catalog` で **コードから語を探す**

**辞書は語彙に触らない。** 再取り込みは辞書だけを入れ替えるので、admin の手修正が消える経路が無い。
これが「語彙値に読み取り専用のものを持たない」を成り立たせている。

**出所は 2 つ。英語は WHO の ICD-10 2019 Meta、日本語は e-Stat の「疾病、傷害及び死因の統計分類
(基本分類)」= ICD-10 (2013年版) 準拠。** 版が違うので片方しか無いコードが出るが、辞書なので欠けを
許す。**どちらも repo に置かず、`npm run icd10:import` が取得する** (手順は
[development.md](development.md))。取り込むのは 3〜5 桁のコードと名前だけで、章・ブロック・索引・
注記は入れない。

## 公開表現

`app/content/public.ts`。**公開表現は content から純関数で作り、経路を 1 本に保つ。** 公開ページも
共有リンクの preview も同じ関数の出力を受け取る。違いは未確定値を残すかどうかの引数だけで、公開ページ側の
経路にこの引数は届かない。

**公開表現は content の形を変えない。落とすことしかしない。** field 名を変えず、構造を平坦化せず、値の
表現も変えない。content 由来の部分については **content ⊃ 公開表現**で、content は公開表現に編集時だけ
要る情報 (翻訳状態、revision) が足されたもの。**したがって返り値の型は content の型そのもの**にする —
未確定が出てこないことを型で落とすと公開用に狭い型がもう 1 系統でき、下の 3 経路が受け取る形が分岐して、
同じ表示を 3 回書くことになる。「公開表現に未確定値のスロットが出てこない」は法則として守る。

落とすのは 3 つ。

| 落とすもの | 理由 |
|---|---|
| 未確定のスロット (preview では残す) | preview で残すのは、共有リンクの第一の用途が「そこを埋めてほしい」と提供者に頼むことだから。公開の姿を見せると聞きたい欄が消える。**該当なしは確定した情報なのでどちらにも残る** |
| 公開ページに出さないキーの値スロットと、catalog が知らないキーの値スロット | 出してよいと言っているのは catalog だけなので、知らないキーは出さない側に倒す |
| 箱の list に無いファイル選択 | 存在の源は list 1 本。腐った参照は黙って消え、非公開に倒したファイルも同時に消える |

**入力は content だけではない。** content に加えて、catalog、外部キャッシュ (CAU と外部 accession の
日付)、ストアの箱の list (ダウンロード一覧) を取る。**関数はこの 4 つを引数に取り、外部を自分で叩かない** —
叩くと外部の可用性が描画に直結する。

**catalog は落とすかどうかの判断にだけ使う。** 表示ラベルの解決と catalog の表示順による並べ替えは
ここでやらない。どちらも content に無いものを足すか順序を変えるかで、「落とすことしかしない」から外れる。

CAU・ダウンロード一覧・日付は content に無いので、公開表現の**外側に足される**。dataset の日付だけは
ここで 1 つに解決する — ポータルが発行した id は content の `releaseDate` を、外部 accession は上流の
キャッシュの値を使うので、**どちらが効くかを下流のどこにも判断させない**。解決するのはこの関数 1 つで、
検索用の行はここが解決した値を列に焼き (「検索用の行」)、公開ページ・一覧・JSON API はその列を読む。
共有リンクの preview は検索用の行を持たない draft を見るので、同じ関数をその場で通す。

| 経路 | 受け取るもの | 公開表現との差 |
|---|---|---|
| 公開ページ (research 系) | 公開表現 | — |
| 共有リンクの preview | 公開表現 | 未確定値のスロットが残る。箱の list も admin 側のものを渡す |
| admin の編集画面 | content | + 翻訳状態・revision・draft のメモ |
| 公開ページ (サイトコンテンツ) | content | 適用外。版も pin も持たない |

## 検索用の行

公開検索と facet が読む行を Postgres の中に持つ。**編集用の content から導出したもので、公開分しか
持たない。**

**何が公開されているかの判定をここ 1 つに閉じる。** 公開画面・public API・公開検索は、対象の集合をこの
行からしか引かない。本文そのものは ContentSnapshot と `dataset_content` から取るが、これらは**公開時に
しか行が生まれない**テーブルで、編集中の値は draft 配下の変更エントリに入る。編集用と公開用が同じ DB に
同居する以上、担保は物理的な分離ではなくこの 2 点で作る。

持つのは 3 種類。全文検索の列を持つ行 (`search_doc`)、語彙 facet の行、数値 facet の行。

- **公開操作と同じトランザクションで更新する。** 「反映されていない」という状態が存在しない
- **外部キャッシュの更新も同じ扱い。** 日次バッチがキャッシュを書き換えたら、影響する行を同じ
  トランザクションで作り直す
- **行が消える経路も 1 つに畳む。** 版の取り下げも research の削除も孤児も、専用の処理を持たず
  「公開分を作り直す」の結果として消える
- **全件再作成を常用の手段として持つ。** 検索用の行の作り方を変えたときも、catalog や語彙を触った
  ときも、まるごと作り直す
- **research 単位でも作り直せる。** 1 つの公開が動かせるものは全部その research の中に閉じる
  (dataset は 1 つの research に従属し、その版もラベルも同じ research のもの) ので、公開と pin の
  付け外しはこの単位で足りる。**キャッシュの更新は全件**で、上流のテーブルを丸ごと置き換える操作から
  「どの research が動いたか」を先に出すことになるため。**導出そのものは 1 つの関数**で、範囲が変わるのは
  どの行を捨ててどの行を読み直すかだけ
- **語彙値の表示ラベルは焼かない。** catalog を join して引く
- **ICD10 のロールアップは祖先の id の列で効かせる。** 3 桁を選ぶと配下の 4 桁がヒットし、**集計は
  祖先の列の末尾 (= 木の根) だけで数える**ので、パネルに 4 桁が並ぶことはない。フラットな語彙では
  祖先が空なので、根は語彙値そのものになる
- **facet の行は対象ごとに持ち、research の行は配下の公開 dataset の値の和集合を持つ。** 2 つの一覧が
  同じ形の述語と同じ形の集計で動く。研究一覧での絞り込みは「配下のどれかの dataset が持つ」の意味に
  なるので、2 つの facet を選ぶと別々の dataset が満たしていてもその研究は当たる

**全文は公開表現から作る。** content からではない。catalog が公開ページに出さないと決めたキーの値も、
未確定値も、公開表現の時点で落ちているので、**「公開表現に一度も出てこない文字で行がヒットする」が
構造的に起きない**。

**ただし語彙値のラベルは足す。** 公開表現が持つのは語彙値の id で、ラベルを解決するのは描画側なので
(「公開表現」)、公開表現をそのまま平坦化すると**画面に出ている語が索引に入らない**。公開表現に残った
値スロットの語彙値について、**code と両言語のラベル**を足す。落ちたスロット (公開ページに出さない
キー) の分は足されないので、上の包含関係は保たれる。code を両方の言語に入れるのは、ICD10 の
コードがどちらの言語の語でもないため。

**疾患は値が持つ呼称も足す。** 呼称は語彙値ではなく値に付いていて (「ICD10」)、**読者が疾患を探す
ときに打つのはその語**になる。見出し語だけを索引に入れると、`NASH` で引いた読者が
`その他の明示された炎症性肝疾患` に届かない。

**入れる範囲は opt-out で決める。** 公開表現の値は原則すべて連結し、外すのは 2 種類だけ。

1 つは**画面に文字として出ない値** — identity (uuid・配列要素の id・語彙値の id・キーの id)、値の種別と
状態を表す判別子 (描画の分岐にしか使わない)、リンクの行き先、数値の換算前の入力とその単位 (画面が出すのは
換算後の値のほう)、dataset のファイル選択、そして別に解決される dataset の日付。URL を外すのは、それが
画面に文字として出る値ではないため — URL がそのまま表示文字列になっているものはリンクの文字列の側が
残るので、ドメインで引く経路は消えない。

もう 1 つは**画面には出るが行を見分けない値** — 数値の正準単位。単位はキーごとに catalog が 1 つ決めるので、
入れるとそのキーを持つ行が全部その語で当たり、絞り込みの役に立たない。

逆に hum ラベルと dataset id は content に無いので pin 台帳から足す。

**ファイル名を索引に入れないのは、名前の原本が content ではなく箱の側にあるから。** 入れると行の
作り直しが S3 の list を要求して全件再作成が S3 の可用性に縛られ、公開切り替えの job が終わるたびに
行が古くなって「公開操作がコミットした時点で検索に出ている」が崩れる。名前の中身は NHA ID として
台帳から入っているので `hum0009.v1.CpG.v1.zip` は n-gram で引け、引けなくなるのは id を含まない名前だけ。

**文は plain の serializer で平坦化する。** span を区切り文字で連結しない。span の境界は語の境界では
ないので (`1.73m` + `²`)、間に何か挟むと連結された語で引けなくなる。

**research の行は配下の公開 dataset の全文を含む。** dataset は 1 つの research に従属するので複製に
ならず、「解析手法に書かれている語で研究を探す」が研究一覧の中で成立する。版の行は配下 dataset の
**ラベルだけ**を持つ — 版は公開集合の台帳であって、一覧が検索する対象ではない。

**facet の行だけは content から作る。** catalog が公開ページに出さないと決めたキーこそが facet の
source なので (「catalog と語彙」)、公開表現を通してから集めるとあるべき facet が消える。未確定値と
「該当なし」はどちらの側にも載らない。

**dataset の日付は公開表現が解決したものを焼く** (「公開表現」)。行に焼いてあるので dataset のページと
一覧と JSON API が食い違えず、キャッシュの更新は行の作り直しで全部に届く。

**全文検索の列は ja と en を連結した生成列**で、直接書き込めない。索引は PGroonga の n-gram
(`TokenNgram` の `unify_*` を全て false、`NormalizerNFKC150`) で、形態素解析を採らないのは
`JGAD000123` の語中一致と `糖尿病` の部分一致がどちらも要るため。**全文検索の述語は
`WITH ... AS MATERIALIZED` に閉じ込める** — 素直に書くとプランナが述語を nested loop の内側に落として
1 行ずつ再評価する。

研究題目だけは別の列にも持つ。`title:` で題目に絞れるようにするためで、索引は張らない — 短い列で
行数も数千なので、演算子は索引なしで働く。

## ファイル

**実体は S3 の 2 bucket にあり、公開状態は bucket の在籍そのもの。Postgres は公開状態を持たない。**
モデルの側から見て効くのはこの 1 点と、**dataset が箱の list に対する順序つきの選択を content の中に
持つ**こと。選択は存在を主張せず、源は箱の list 1 本だけになる。**外部アーカイブの dataset は選択を
持たない** — 判定は primary の dataset id の綴りで、そこが「identity と label」の 1 点を読む唯一の理由に
なる。

ストアの形・upload の署名・切り替えの job・一覧の作り方は [files.md](files.md)。


## 外部キャッシュ

外部 master から取った値は Postgres のキャッシュテーブルに置き、読み手はそこから読む。

| source | 上流 | 用途 |
|---|---|---|
| CAU (controlled-access user) | JGA 申請管理システム DB | 公開表現に載る |
| hum ラベル ↔ accession と、JGA の dataset → study の辺 | 同上 | 公開ゲートの検算、dataset のページ、DDBJ Search への供給 |
| JGAD の日付 | 同上 | 公開表現に載る |
| DRA / GEA / MetaboBank / BioProject の日付 | DDBJ Search | 同上 |

- **上流が止まっても公開ページは動く。** バッチが書き、読み手はキャッシュしか見ない
- **キャッシュなので失っても再取得でき、バックアップの対象外**
- **キャッシュに入れてよいのは、そのまま公開ページに出る値だけ。** 申請の中身 (連絡先・住所・所属長・
  member・collaborator・申請書の本文) は持ち込まない。**行を上流と照合するためのキー (J-DU の案件番号)
  だけが例外**で、公開表現にも public API にも出ない
- **CAU は content ではないので翻訳状態を持たない。** 上流の ja/en をそのまま出し、公開ゲートの
  未翻訳の列挙にも載せない。curator が編集できない値なので、直す経路は上流側にある
- **CAU の 1 行は 1 利用課題。** 人単位に丸めない (上流に person master が無く、名寄せが推測になる)。
  出すのは PI だけで、hum ラベルに紐づく。案件は複数の hum にまたがることがあるので、行が挙げる
  accession はその hum に属するものだけ
- **hum と accession は 1 : n。** 上流がこの対応の master で、ポータルは検算と DDBJ Search への供給
  ([public-api.md](public-api.md)) に使う。**ポータルの pin は master ではない**ので、キャッシュに無い
  対応を供給に足すことはしない
- **同じ source が JGA の dataset → study の辺も持つ。** 上流の `relation` を最新の entry に絞って
  辿った結果で、**JGAD : JGAS は 1 : 1**。hum ごとに畳んだ対応からは戻せない (1 つの hum が複数の
  study を持つほうが普通) ので、畳む前を持つ。辺を持つのは dataset の accession だけで、study の
  accession は持たない
- **JGAD の日付は公開状態が live になった日で、初回が公開日、最後が更新日。** live は内容が更新される
  たびに記録し直されるので、`datePublished > dateModified` が構造的に起きない。上流の履歴は 2020-09
  以降しか無く、それ以前に公開されたものは初回が一括記録の日になるが、**その値をそのまま出す** —
  どこまでが一括記録かの線引きはポータル側の推定になる
- **キャッシュが持つのは公開済みの accession だけ。** これは公開表現と DDBJ Search への供給が読み手
  だからで、そのどちらも公開済みしか扱わない。したがって**編集の入力に上流を使う経路はキャッシュを
  読まず、その場で上流を引く** ([editing.md](editing.md) の「上流からの下書き」) — 下書きを作る相手は
  これから公開する研究なので、キャッシュには載っていない

### キャッシュの更新

**更新の単位は上流の系で 4 つに分かれ、独立に失敗する。** 上の表の 4 行がそのまま単位になる。

- **取得に失敗したソースは前回値を残す。** 上流が一時的に応答しないことと、値を消したことを区別できない
- **成功したソースだけを 1 つのトランザクションで全置換し、同じトランザクションで検索用の行を作り直す。**
  日付は 2 つの上流が 1 つのテーブルを分け合うので、置換の範囲は source が決める
- **その source が今回返さなかった行は消える。** 上流がもう公開していない accession の日付が残らない
- **ソースごとに最終試行・最終成功・件数・直近の失敗理由を持つ。** 行ごとに取得時刻を持つ形では、今日も
  取れた状態と、失敗して前回値が残っている状態が区別できない。管理画面がこれを出す
  ([editing.md](editing.md))
- **回すのはアプリのプロセスで、専用の worker を立てない** (ファイルの切り替えと同じ)。CLI からも同じ
  ものを叩ける ([development.md](development.md))
- **申請管理システム DB への接続は read-only。** 他プロジェクトの所管なので schema も中身も変えない。
  **接続を持たない環境ではその 3 つを skip する** — 本番以外からこの DB には届かない。キャッシュは
  開発用データの投入が埋めるので、空の状態は運用にも開発にも現れない

## 日付

**日付は admin が設定するものとして持つ。** 版を変えずに fix するので、操作の記録をそのまま日付にすると
公開の実態を表せない。

| 日付 | 決め方 |
|---|---|
| research の版の release date | 公開操作時に today を default で入れ、admin が変更できる |
| research の初公開日 / 最終公開日 | 公開版の release date から導出する。独立に持たない |
| dataset の公開日 / 更新日 | **どの master が持つ accession かで決まる** (下) |

**dataset の日付は 3 つの master に分かれる。**どれが答えるかは accession の綴りが決め、公開表現が
1 つに解決する ([public-pages.md](public-pages.md))。

| accession | master | 取り方 |
|---|---|---|
| `JGAD…` | JGA 申請管理システム | 公開状態が live になった日。初回が公開日、最後が更新日 |
| `DRA…` / `E-GEAD-…` / `MTBKS…` / `PRJDB…` | DDBJ Search | 上流が答える 2 つの日付をそのまま |
| NHA ID (`hum0343.v1` など) | **ポータル自身** | content が公開日を持つ。**更新日は同じ値** |

上の 2 つは外部キャッシュ経由 (「外部キャッシュ」)。**content には持たない** — 上流が master のものを
content にも置くと、同じ事実の出所が 2 つになる。

**NHA dataset は日付を 1 つしか持たない。** ポータルは dataset を版管理しないので、公開の後に「更新」と
呼べる出来事が無い。公開日をそのまま更新日として出す — 空にすると、他のすべての dataset が埋める列に
穴が開き、別の日を作ると誰もしていない更新を主張することになる。

**その公開日は admin が設定でき、default はその dataset を出した版の release date。** 版の release date は
公開操作の時点で初めて決まるので、**default が書かれるのもそこ** (`app/admin/publish.server.ts`)。一度
入った値は後の公開が触らない — v4 に持ち越された dataset は v4 の日に公開されたのではない。

**書式は `YYYY-MM-DD`。暦日は JST で切る。日付は言語を持たない。** 上流由来の日付をポータル側で
補正しない — 補正すると上流が直ったときに二重の推定が残る。ポータルの content がいつ訂正されたかを表す
値はどこにも持たない。

## サイトコンテンツ

**document と news は版も pin も持たない。draft と公開状態だけを持つ。** research の版・pin 台帳・fix は
適用せず、公開表現の純関数の対象にも公開検索の対象にもならない。

- **locale ごとに content と公開状態を持つ。** 版を持たないので「公開の単位は版であって言語ではない」が
  当てはまらない。公開されていない言語は**もう一方に倒れず 404 になる**
- **draft は locale ごとに 1 つで、公開中の本文の隣に置く。** 公開はその写しを本文へ移すことになる。
  research の draft が持つ道具 (undo・presence・共有リンク・3-way) は持たない — 版が無いので比べる相手が
  無く、並行して同じ document を書いた実績も無い
- **news は document と別のエンティティ。** identity + locale ごとの content + 公開日 + draft。公開日は
  identity の側に 1 つで、一覧の並びそのものになる
- **本文は markdown 文字列。** 生 HTML は持たない (「値と文」)
- **alert は on / off だけを持ち、期間を持たない。** ja/en の対を 1 つ持つ。**立っている alert は必ず
  両方を持つ** — 全ページに出るものなので、片方しか無いまま立てると、その言語の読者は読めない箱を
  渡される。これは入口が 2 つとも見張る: admin は両方揃うまで on にできず
  ([editing.md](editing.md))、移行は立っている alert の空いた側を手で書いた訳で埋め、埋められなければ
  止まる。**off のあいだは片方だけでよい** — まだ誰にも何も言っていないため

**画面は document ではない。** 提供・利用・問い合わせの入口はボタンと短い文だけで本文を持たないので、
コードが持つ ([public-pages.md](public-pages.md))。トップだけは枠がコードで、本文が `home` document に
なる。**navigation も DB に持たない** — admin が編集する UI が無いので、置く理由が無い。

### ガイドラインの版

**版も独立した document で、slug は現行の URL をそのまま採って `{slug}/version/{n}`。最新版も番号の slug を
持つ。** 各版は全文を持つ自己完結した本文なので、版機構を持たなくても壊れない。

**版なし slug は本文を持たず、現在の版を指す行 (`document_series`) として持つ。** 指し先の張り替えは
admin の操作で、publish に連動した自動退避はしない。

- **document は本文を持つか、指し先を持つかのどちらか一方。** 版なし slug と最新版が同じ本文の 2 つの
  写しになる形を作らないため。**本文の原本は 1 か所**に留まる
- **指し先は NOT NULL で、指されている document は単独では消せない。** 「最新を指す行があるのに指して
  いない」状態を作らない。系列を畳むときは指し先の行と配下の全版を 1 操作で消す — 1 件ずつ消す形だと
  指し先だけが最後に残り、消す手段が無くなる
- **指し先の候補は `{slug}/version/{n}` の形をした document だけ。** 親子は slug の prefix が表すので、
  関係を列で持たない
- **版なし slug の公開状態は指し先のもの。** 指し先がその言語で公開されていなければ、版なし slug も
  その言語で 404 になる。**版なし slug は恒久的に応答し続ける必要がある**ので
  ([public-pages.md](public-pages.md))、管理画面がこれを不備として出す
- **slug の一意性は 2 つの表にまたがる。** DB の制約 1 本では守れないので、保存側が両方を見て弾き、
  test が守る。route が持つアドレスとの衝突も同じ扱いになる
- **版を初めて切る操作は「移す」。** いまの本文を `{slug}/version/{n}` へ rename し、空いた slug で
  指し先の行を作る。本文のコピーが生まれない
- **版番号は admin が決める。** 画面は既定を出すだけ (初めて切るときは 1、以後は最大 + 1) で、打ち直せる。
  本文の `Ver.` 表記と版番号がずれている実データがあるため。使用済みの番号は slug の一意性が弾く
- **版を持つのをやめる操作は持たない。** 版なし slug に本文を戻すと `{slug}/version/{n}` が 404 になるか、
  本文が 2 つに割れるかのどちらかになる。版を 1 つだけ持つ状態は読者から見て版なしと区別が付かないので、
  やめる必要も無い

## 意図的に持たないもの

| 持たないもの | 理由 |
|---|---|
| 別の検索エンジンへの投影 | 全文検索も facet も同じ Postgres で完結する。投影が無ければ反映待ちも無い |
| dataset の履歴 / experiment の版 | 記述の訂正は履歴ではない。版を持たせると pin する対象が 1 段増える |
| experiment の行 | content の中の要素で足りる。集計は検索用の行が引き受ける |
| `versionIds` / `latestVersion` のような二重管理 | 台帳から導出できる |
| 生 HTML (rawHtml) | 公開画面が読んでいない。値と装飾の分離にもなっていない |
| サイトコンテンツの生 HTML と許可リストの sanitize | 生 HTML を parse しなければ、出せる集合が markdown の集合そのものになる |
| navigation のテーブル | admin が編集する UI を持たない。コードの定数で足りる |
| alert の期間指定 | 現行の 2 件とも空。持つと表示の判定が 2 本立てになる |
| 文の中の見出し・表・箇条書き・強調・上付き | 実データでほぼ空 (見出しと表は 0%、強調 0.6%、箇条書き 0.3%)。持たなければ許可集合が型そのものになる |
| アーカイブ由来の生メタデータ (originalMetadata) | 必要になった時点で外部キャッシュとして置き直せる |
| 抽出した派生値の層 (searchable) | catalog のキーとして値スロットに吸収する |
| 申請の中身 (氏名・連絡先・住所) | 個人情報を抱えない。admin 画面が要るときは上流を直読みし、キャッシュしない |
