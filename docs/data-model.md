# データモデル

研究・バージョン・下書き・データセットを DB にどういう形で保存し、どの制約を付けているかをまとめる。語の意味は [concepts.md](concepts.md)、項目定義と語彙は [catalog.md](catalog.md)、外部データは [upstream.md](upstream.md)、下書きの編集は [editing.md](editing.md)、公開の操作は [publishing.md](publishing.md)、ファイルは [files.md](files.md)、記事とお知らせは [site-content.md](site-content.md) にある。テーブルと型の定義はコード (`app/db/schema/`、`app/content/types.ts`) にあり、この文書にはコピーしない。

## 研究の内容の保存形式

研究の内容とデータセットの内容は、JSONB として保存する。保存先は Postgres だけで、編集中の内容も公開済みの内容も Postgres に保存する。

- 型は、下書きとバージョンで同じである。型が同じなので、公開は値のコピーで済む。
- 下書きとバージョンで違うのは、分け方だけである。下書きでは、研究の内容とデータセットの内容を別の行に保存する。バージョンでは、全部を 1 つにまとめて保存する。下書きの保存はデータセット 1 件ごとに行い、公開はまれにしか行わないので、下書きとバージョンのそれぞれに合った分け方にしている。
- 公開済みの内容を読むときは、バージョンの JSONB から取り出さない。JSONB は圧縮されると一部だけを読めず、データセット 1 件のためにバージョン全体を展開することになるためである。公開済みの内容は、データセットごとに内容を保存した検索用の行から読む。
- 項目の値を DB の列に分けない。どの形の値が入るかはキーの型で決まるので、列に分けると NULL を許す列が並び、整合を schema で保証できないためである。
- 独立したテーブルの行にするのは、研究の内容でないものだけである。次のものが当たる。
  - 検索用の行 (集計と索引)
  - ID の割り当て表 (一意性を DB の制約で保証する)
  - 項目定義と語彙 (参照整合性、[catalog.md](catalog.md))
  - 外部データ ([upstream.md](upstream.md))
  - ファイルのラベルと、研究のページに表示するかの設定 (研究を公開しなくても変わる、[files.md](files.md))
  - 操作の記録 (追記だけ)
  - コメント・ジョブ (研究を公開しなくても増減する)
- 解析手法はテーブルの行にしない。解析手法は、データセットの内容の中に順序付きで並ぶ要素で、要素の ID で指す。解析手法の集計は検索用の行で行う。
- 配列の要素 (研究代表者、関連論文など) には要素の ID を付ける。コメントや差分は、位置ではなく要素の ID で要素を指すので、要素を並べ替えても指す先が変わらない。
- 検索用の行はいつでも作り直せる。外部データは取り直せる。

### 書式付きテキスト

研究の内容のうち書式があるのは、書式付きテキスト (コード上は `RichText`、本文や自由記述の欄) だけである。どの値が書式付きテキストかは、キーの型で決まる。

- 書式付きテキスト以外の値 (accession、語彙の値、数値、疾患、名前) には書式が無い。リンクや単位は、表示する処理が値の型から作る。
- 書式付きテキストは、行 (line) の配列として保存する。1 つの行は配列で、配列の要素は「文字列」か「文字列と URL の組」である。見出し・表・箇条書き・強調・生の HTML は入らない。書けるものの範囲を型で決めているので、保存時の検査と表示時の sanitize を二重に書かずに済み、ポータルと同じ origin での stored XSS の経路も無くなる。
- リンクの URL は、表示するときに scheme を検査する。移行したデータは保存時の検査を通っていないためである。
- 入力は markdown で受け取り、保存するときに行の配列に変換する。変換できない記法は、書かれた文字のまま残し、拒否も削除もしない。記法が反映されていないことは、編集画面の隣に表示する公開ページで分かる。
- 単一の改行は行の区切りである。一度保存した書式付きテキストは、編集画面に表示して保存し直しても同じ内容になる。
- 出力は 3 つある (`app/content/richtext.ts`)。画面には、行の配列をそのまま描画する。plain text は JSON API と全文検索に使う。markdown は編集画面に返す。HTML の文字列を作る処理は無い。

### 数値

数値のキーには、数を 1 つではなく配列で保存する。1 つの欄に部位ごとの数が並ぶデータが多く、数を 1 つしか保存できないと、同じ事実を書式付きテキストと数値の 2 か所に書くことになるためである。

- 各数には、数の前に付ける文字列 (Prefix) と後に付ける文字列 (Suffix) を付けられる。画面には、Prefix・数・単位・Suffix をこの順にそのままつなげて表示する。区切りの記号も空白も、入力したとおりに表示する (Prefix `常染色体: `・数 `5961600`・Suffix ` SNVs` で `常染色体: 5,961,600 SNVs`)。部位や疾患ごとの数の見出しも、数えたものの名前も、括弧の注記も、書く人が表示のとおりに書けるようにするためである。
- Prefix と Suffix は、言語ごとに書く翻訳の組である。画面には、表示中の言語の Prefix と Suffix を表示する。言語ごとに書けないと、1 つの欄に部位や疾患ごとの数が並ぶときに、英語のページに日本語の見出しが並ぶためである。
- 幅のある値は、下限と上限で表す。上限は省略できる。下限も上限も、標準の単位に換算した値である。
- 単位は、換算のあるキー (データ量・配列長・深度・割合) にだけある。入力した単位での値も保存し、画面には入力した単位での値を表示する。換算が誤っていたと分かったときに、換算をやり直すためである。個数を数えるキーには単位が無い。数えたものの名前 (`SNVs`) は Suffix に書く。
- 換算は `app/content/units.ts` の 1 か所だけで行う。データ量も配列長も 1000 刻み (SI) で換算する。

### 一覧の要約

研究一覧の行に表示する要約 (`listingSummary`) は、研究の詳細から導出せず、admin が書く。

- 解析手法・データの種類・参加者の列の値は、詳細を足し合わせた表記や分類語であり、詳細の値とは形が違う。導出した値を初期値にすると、admin が書いた値と区別が付かなくなる。
- 提供者の列だけは例外である。一覧の行の提供者が空なら研究代表者の名前を表示し、admin が一覧の行の提供者を書いていれば、書いた値を表示する。名前が 1 つも無い要素は、保存のときに除く。

### 公開用の表示データ

公開用の表示データは、研究の内容から公開してよい部分だけを残したものである。`app/content/public.ts` の純関数で作る。

- 公開ページ、共有リンクのプレビュー、編集画面の隣の公開ページには、同じ関数を使う。違いは、未確定の値を残すかどうかの引数だけである。公開ページの処理からは、未確定の値を残す引数を渡せない。提供者がプレビューで見ている内容が、そのまま公開される内容であるようにするためである。
- 公開用の表示データを作る関数は、値を除くだけで、項目名も構造も値の表し方も変えない。そのため、戻り値の型は研究の内容の型と同じである。
- 除くのは、未確定の値 (プレビューでは残す) と、研究ごとの prefix の一覧に無いファイルの選択である。項目定義のキーは、どれも公開ページに表示する。
- 関数の入力は、研究の内容・制限公開データの利用者・研究ごとの prefix の一覧・アーカイブの日付とファイルである。関数の中から外部を呼ぶことはない。表示の処理が外部の可用性に左右されないようにするためである。
- データセットの日付は、この関数で 1 つに決める。後の処理では、どの日付を使うかを判断しない ([日付](#日付))。

## 実体と ID

研究とデータセットは実体 ([concepts.md](concepts.md)) として作り、研究 ID・データセット ID・バージョン番号は後から割り当てる。

- 実体は、研究 ID やデータセット ID が無くても作れる。研究 ID やデータセット ID を直しても、実体への参照はそのまま使える。管理画面の URL も実体の ID で作る。
- 研究 ID とデータセット ID は、ID の割り当て表 (`label_pin`) に保存する。種類と文字列の組は、ポータル全体で一意である。primary の ID と secondary の ID を区別せず、両方を合わせた中で一意である。バージョン番号は研究の中でだけ一意なので、バージョンの行に保存する。
- 研究が公開されているかは、公開中のバージョンがあるかで判定し、番号の大小では判定しない。番号には欠番があり得る。
- 割り当てを外した ID は再利用できる。研究 ID は、人が申請管理システムに入力する文字列が元で、入力の誤りの訂正が日常の操作だからである。例外は NHA ID である。
- 1 つの実体に複数の ID を割り当てられ、primary の ID は 1 つである。secondary の ID は、古い ID への外部からの参照をたどれるように残す。primary が 1 つであることは、部分 unique index で保証する。
- ID は、割り当てた時点で ID の割り当て表に入り、公開の前から有効である。同じ accession を 2 つの下書きで割り当てようとすると、アプリは 2 つ目の割り当てを拒否する。そのため、公開のときに実体をまとめる処理は要らない。下書きで作成したデータセットは、下書きを削除すると ID ごと消える。

### NHA ID

NHA ID は、ポータルが発行するデータセット ID で、`NHA` と 6 桁のポータル全体の通し番号 (`NHA000001`) である。

- 番号は再利用しない。割り当てを外しても、データセットが消えても、同じ番号は二度と発行しない。外部に書かれたリンクが、知らないうちに別のデータセットを指さないようにするためである。
- admin は NHA ID の文字列を選べず、発行の操作をするだけである。NHA ID の形の文字列を手で割り当てることはできない。
- 次の番号は、ID の割り当て表と操作の記録の両方を合わせた中で最大の番号の次である。番号は研究もバージョンも表さない。
- 研究 ID で始まるデータセット ID (`hum0014.v1.freq.v1`) も、ポータルが付けた ID である。研究 ID で始まる ID のあるデータセットでは、NHA ID が primary の ID で、研究 ID で始まる ID は secondary の ID として残っている。

### データセット ID から判定すること

データセット ID の文字列から判定するのは、ポータルが発行したものかどうかの 1 点だけである。

- primary の ID が `NHA` と 6 桁に完全に一致するか、`hum` で始まるなら、ポータルが発行したものとする。secondary の ID は判定に使わない。研究 ID で始まる古い ID が secondary の ID として残っているためである。
- primary の ID がまだ無いデータセットは、外部のものとして扱う。
- この判定で、総データ量とファイル形式を選択したファイルから作るか ([files.md](files.md)) と、日付をどこから取るか ([日付](#日付)) が決まる。バージョン番号など、それ以外の構造は ID から判定しない。

### データセットの所属と削除

データセットは 1 つの研究に属し、データセットの行の `research_id` が所属を表す。バージョンや下書きでデータセットを選んで載せる操作は無い。

- 研究にあるのは、公開済みのデータセットと、どれかの下書きで作成してまだ公開していないデータセットである。下書きに保存するのは、データセットの順 (`datasetIds`) とデータセットの内容だけで、「載せる・載せない」の選択は無い。
- バージョンには、載せた全データセットの内容を保存する。ただし、公開ページに各データセットの内容を表示するときは、検索用の行 (最新のバージョンのデータセットの内容) を読む。過去のバージョンのページでも、検索用の行を読む。
- データセットが公開中なのは、最新のバージョンに載っていて、primary のデータセット ID があるときである。バージョンのページに表示するのは、そのバージョンに載っていて、今も公開中のデータセットである。
- データセットの削除は、研究からデータセットを消す操作である。削除は、研究を公開しなくても反映される。アプリは、データセットを ID の割り当てごと消して検索用の行を作り直すので、削除したデータセットは公開ページからその場で消える。削除したデータセットの内容は過去のバージョンの内容に残るが、表示はしない。削除したデータセットを載せていたバージョンから下書きを作るとき (編集・コピー・取り下げ) は、削除したデータセットをデータセットの並びと関連論文から除き、データセットの内容も下書きにコピーしない。
- 関連論文から指すデータセットは、所有ではなく引用である。この研究のデータセットは実体の ID で、それ以外のデータセット (他の研究のデータセット、ポータルに無い accession) は書かれた ID の文字列で、研究の内容に保存する。表示するときに ID の割り当て表を引く。

## 値の状態 (未確定・該当なし・未翻訳)

値の状態の意味は [concepts.md](concepts.md) にあり、この節には保存の形と表示の決まりを書く。

- 公開の単位は研究のバージョンで、言語ではない。1 つのバージョンに日本語と英語の両方が入り、片方の言語が未翻訳のままでも公開できる。英語の内容が無い研究が実在するためである。代わりに、公開前の確認で未翻訳を一覧に表示する。
- 項目は次の 3 種類に分かれ、どれに当たるかは研究の内容の型で決まる。
  - 単一の値: 言語の区別が無い (数値、語彙の値、accession、論文の題名、研究費の課題番号の並び、関連論文が指すデータセットの並び)。
  - 翻訳の組: 言語ごとに表記がある (本文、機関名、研究課題名、数値の Prefix と Suffix)。
  - 言語ごとに別のものを指す値: URL だけである。
- 単一の値から翻訳の組への変更は機械的に行えるので、どちらにするか迷う項目は単一の値にしてよい。
- 両方の言語に同じ値をコピーしない。翻訳済みと判定されてしまうためである。
- 状態は言語ごとに決め、値の中の 1 か所にだけ保存する。片方の言語だけが未確定の値が実在するためである。
- 研究費の課題番号の並びと、関連論文が指すデータセットの並びは、状態を並び全体に 1 つだけ保存し、要素ごとには保存しない。表の行のほかの欄に値があって、並びの欄だけに値が無いことを該当なしで表し、提供者に問い合わせていることを未確定で表すためである。
- 空は状態ではなく、「値があって中身が空」である。必須の検査では、値が空かどうかを調べる。未確定は、admin が「提供者に問い合わせている」ことを示すために明示的に選ぶ。
- 公開前の確認で一覧に表示するのは未確定だけで、該当なしは表示しない。
- 未翻訳は値から決まる。翻訳の組で、両方の言語が値のある状態 (未確定でも該当なしでもない) で、片方の言語の値だけが空のときに未翻訳とする。両方の言語の状態が違う (日本語に値があり、英語が未確定) ときは未確定として数え、同じ不足を公開前の確認で 2 度表示しない。
- 該当なしの表示文字列は値として保存せず、表示する処理で作る。
- 公開ページでは、未確定の値と空の値を表示しない。該当なしは灰色の `N/A` と表示し、ポインタを合わせると「該当なし」(英語のページは「Not applicable」) を表示する。解析手法の表では該当なしがセルごとに並び、語のままでは値が読みにくくなるためである。灰色にするのは、値として書かれた「N/A」と見分けるためである。書体は値と同じにする。
- プレビューでは、未確定を提供者への問い合わせとして表示する。
- 検索と絞り込みに入るのは、値があるもの (未確定でも該当なしでもない) だけである。

### 表示する言語

どの言語の値を表示するかは `app/i18n/locale.ts` で決める。最初に、表示中の言語の状態を調べる。

- 該当なしと未確定は、もう一方の言語にフォールバックしない。
- 翻訳の組で表示中の言語の値が空のときは、もう一方の言語の値を代わりに表示し、未翻訳であることも表示する。
- URL はフォールバックしない。読者を別の言語のページへ送ることになるためである。

## 検索用の行

何が公開されているかの判定は、検索用の行 (`search_doc` と絞り込みの行) だけで行う。公開ページ・JSON API・公開検索の処理は、対象の集合も本文も検索用の行から読む。

- 検索用の行は、公開に関わる操作でしか作らない。そのため、編集中の値が公開側 (公開ページ・JSON API・公開検索) に現れる経路は無い。
- 検索用の行には、研究の内容かデータセットの内容 (公開用の表示データではない)、全文検索の列、語彙の絞り込みの行、数値の絞り込みの行がある。内容をそのまま保存するのは、admin が「このキーはまだ使われているか」を調べるときに、公開済みの内容を対象にするためである。
- アプリは、検索用の行を、公開・更新・取り下げ・ID の割り当てと解除・データセットの削除・外部データの更新・項目定義の変更と同じトランザクションで作り直す。「まだ反映されていない」状態は存在しない。
- 検索用の行を消す処理は「作り直す」の 1 つだけで、取り下げや削除のための専用の処理は無い。
- 作り直しの関数は `app/search/rebuild.server.ts` の 1 つで、範囲は研究単位か全件である。全件の作り直しは普段の操作として使え、2 度作り直しても同じ行になる。
- 作り直しは同時に 1 つだけ実行し、次の作り直しは前のトランザクションが終わるまで待つ。全件の作り直し (外部データの更新) と研究単位の作り直し (公開) は、研究の行の lock では互いに待たないので、重なると、後の作り直しが前の作り直しの行と重複して失敗するためである。
- データセットの検索用の行は、最新のバージョンのデータセットの内容から作る。研究の検索用の行には、配下の公開中のデータセットの全文と絞り込みの値の和集合を保存する。研究一覧での絞り込みの意味は [public-site.md](public-site.md) の「絞り込み」にある。
- 語彙の値の表示名は行に書かず、検索のときに join で引く。ICD10 の上位のコードでの絞り込みは、行に保存した祖先の ID の列で行う。

### 全文検索

全文検索の列は、公開用の表示データから作る。公開用の表示データに無い文字で検索用の行が見つかることが、構造的に起きないようにするためである。

- 全文検索の列には、語彙の値の code と両言語の表示名、疾患の呼称、研究 ID とデータセット ID を足す。
  - ID は secondary の ID も足す。secondary の ID は、開けば primary の ID のページへリダイレクトされる公開の ID で、古い ID で探す読者がいるためである。
  - JGAD のデータセットの行には、データセットのページに「JGA Study」として表示する JGAS の ID も足す。JGAS は研究 ID と JGA の accession の対応の取得元から読むので、取得で対応が変わると検索用の行も作り直される ([upstream.md](upstream.md) の「取り直しと失敗」)。
- 語彙の値に上位の値があるとき (ICD10 の 4 桁に対する 3 桁) は、上位の値の code と両言語の表示名も足す。絞り込みは 4 桁を 3 桁にまとめて数えるので、キーワードでも同じ単位で見つかるようにするためである。
  - 日本語の 4 桁の見出し語は、3 桁の見出し語に続けて読む書き方で、部位だけのものが多い (`C719` は「脳，部位不明」、その 3 桁の `C71` は「脳の悪性新生物＜腫瘍＞」)。3 桁の見出し語を足さないと、「悪性新生物」で探しても、`C719` だけを参照するデータセットは見つからない。
  - 3 桁の見出し語が複数の病名を並べるもの (`J30`「血管運動性鼻炎及びアレルギー性鼻炎」) では、`J301` のデータセットが「血管運動性鼻炎」でも見つかり、絞り込みの `J30` と同じ結果になる。
  - 上位の見出し語はページに表示しない。ただし、上位の見出し語は公開用の表示データにある値から決まるので、公開していない値で行が見つかることにはならない。
- 画面に文字として表示しない値 (実体の ID、状態、リンク先、ファイルの選択) は、全文検索の列に入れない。単位と、入力した単位での値も、全文検索の列に入れない。
- ファイル名とファイルのラベルは、全文検索の列に入れない。ファイル名の正本はファイルストアの研究ごとの prefix にあり、入れると検索用の行の作り直しがファイルストアの可用性に左右されるためである。ラベルを入れないのは、ラベルは研究を公開しなくても変わり、検索用の行は公開に関わる操作でしか作り直さないためである。
- 絞り込みの行は、データセットの内容から作る。未確定と該当なしの値は入れない。
- ファイル形式は、絞り込みの行ではなく、公開日と同じく検索用の行の列に保存する。絞り込みの行はキーごとの行で、ファイル形式はキーではないためである。ファイル形式の列は、外部のアーカイブのデータセットでは取得したファイルから、NHA ではファイルの選択の名前から作る。研究の検索用の行には、配下のデータセットのファイル形式をまとめて保存する。どちらの作り方もファイルストアを読まないので、検索用の行の作り直しはファイルストアの可用性に左右されない。
- 索引は PGroonga の n-gram (`TokenNgram`、`NormalizerNFKC150`) である。accession の途中での一致と日本語の部分一致の両方が要るので、形態素解析は使わない。
- 全文検索の列は、日本語と英語の列を連結した生成列である。全文検索の条件は `WITH ... AS MATERIALIZED` の中に書く。プランナが nested loop の内側で条件を評価し直すのを防ぐためである。

## 日付

日付は admin が設定するものとして保存し、操作の記録からは作らない。取り下げて再公開することも、同じ番号で更新することもあるためである。書式は `YYYY-MM-DD`、日付の区切りは日本時間で、言語の区別は無い。

- バージョンの公開日は、公開の操作のときに今日の日付を初期値にし、admin が変えられる。
- 研究の初公開日と最終公開日は、公開中のバージョンの公開日の最小と最大である。
- JGAD の公開日と更新日は、申請管理システムで公開の状態になった最初の日と最後の日である ([upstream.md](upstream.md))。
- 他のアーカイブのデータセットの公開日と更新日は、DDBJ Search が返す 2 つの日付をそのまま使う。取得元の日付をポータル側で補正しない。
- ポータルが発行した ID のデータセットでは、アプリが、データセットを初めて載せたバージョンの公開日を、公開のときにデータセットの内容に書く。一度入った日付は後の公開では変えず、直すときは admin が編集する。更新日も公開日と同じ値にする。データセットにバージョンが無く、「更新」と呼べる出来事が無いためである。
- 取得元が正本の日付は、データセットの内容に保存しない。同じ事実の出所を 2 つにしないためである。
- 行の `updated_at` は、表示する日付に使わない。バージョンの `updated_at` は公開した時刻で、語彙の統合で内容が書き換わっても変わらない。

## DB に置かないもの

次のものは、意図して DB に置いていない。

- データセットの履歴と解析手法のバージョン。データセットの内容の訂正は研究のバージョンの更新で行う。データセットや解析手法にバージョンを分けても、ID を割り当てる対象が 1 階層増えるだけである。
- 解析手法の行。データセットの内容の中の要素で足り、集計は検索用の行で行う。
- 公開の状態を表す列。バージョンの行があることが公開中であることを意味する。
- バージョンの一覧や最新の番号を別に保存する列 (`versionIds`、`latestVersion` など)。ID の割り当て表とバージョンの行から導出できるので、保存すると二重管理になる。
- 書式付きテキストの中の見出し・表・箇条書き・強調・生の HTML。書けるものの範囲を型で決めるためである。
- 申請の連絡先・住所・電話・研究分担者。個人情報を DB に置かないためで、取得の処理も連絡先・住所・電話・研究分担者を読まない。申請から下書きに取り込む値 (研究題目・目的・方法・対象、研究代表者の氏名と所属など) は、承認済みのデータ提供申請のキャッシュに入る ([upstream.md](upstream.md) の「取得元とキャッシュ」)。
