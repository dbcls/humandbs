# データモデル

研究・バージョン・下書き・データセットを DB にどういう形で保存し、どの制約を置いているかをまとめる。語の意味は [concepts.md](concepts.md)、下書きの編集は [editing.md](editing.md)、公開の操作は [publishing.md](publishing.md)、ファイルは [files.md](files.md)、記事とお知らせは [site-content.md](site-content.md) にある。テーブルと型の定義はコード (`app/db/schema/`、`app/content/types.ts`) にあり、ここにはコピーしない。

## 研究の内容の保存形式

研究の内容とデータセットの内容は、JSONB として保存する。保存先は Postgres だけで、編集中のものと公開済みのものを両方置く。

- 型は、下書きとバージョンで同じである。型が同じなので、公開は値のコピーで済む。
- 分け方だけが違う。下書きは研究の内容とデータセットの内容を別の行に分け、バージョンは全部を 1 つにまとめる。保存はデータセット 1 件ごとに行われ、公開はまれなので、それぞれに合った分け方にしている。
- 公開済みの内容を読むときは、バージョンの JSONB から取り出さない。JSONB は圧縮されると一部だけを読めず、データセット 1 件のためにバージョン全体を展開することになるためである。公開済みの内容は、データセットごとに内容を置いた検索用の行から読む。
- 項目の値を DB の列に分けない。どの形の値が入るかはキーの型で決まるので、列に分けると NULL を許す列が並び、整合を schema で保証できないためである。
- 独立したテーブルの行にするのは、研究の内容でないものだけである。検索用の行 (集計と索引)、ID の割り当て表 (一意性を DB の制約で守る)、項目定義と語彙 (参照整合性)、外部から取ってきたデータ、操作の記録・コメント・ジョブ (追記される) がこれに当たる。
- 解析手法はテーブルの行にしない。データセットの内容の中に順序付きで並ぶ要素で、要素の ID で指す。集計は検索用の行で行う。
- 配列の要素 (研究代表者、関連論文など) には要素の ID を付ける。コメントや差分が位置ではなく ID で要素を指すので、並べ替えても指す先がずれない。
- 検索用の行はいつでも作り直せ、外部から取ってきたデータは取り直せる。

### 書式付きテキスト

研究の内容のうち書式があるのは書式付きテキスト (コード上は `RichText`、本文や自由記述の欄) だけで、どの値が書式付きテキストかはキーの型で決まる。

- 書式付きテキスト以外の値 (accession、語彙の値、数値、疾患、名前) には書式が無い。リンクや単位は、表示する側が型から作る。
- 書式付きテキストは行 (line) の配列として保存し、1 つの行は「文字列」か「文字列と URL の組」の配列である。見出し・表・箇条書き・強調・生の HTML は入らない。書けるものの範囲が型そのものになるので、保存時の検査と表示時の sanitize を二重に書かずに済み、ポータルと同じ origin での stored XSS の経路も無くなる。
- リンクの URL は、表示するときに scheme を検査する。移行したデータは保存時の検査を通っていないためである。
- 入力は markdown で受け取り、保存するときに行の配列に変換する。変換できない記法は、書かれた文字のまま残し、拒否も削除もしない。記法が反映されていないことは、編集画面の隣の公開ページで分かる。
- 単一の改行は行の区切りである。一度保存した書式付きテキストは、編集画面に出して保存し直しても同じ内容になる。
- 出力は 3 つある (`app/content/richtext.ts`)。画面は行の配列をそのまま描き、plain text は JSON API と全文検索に使い、markdown は編集画面に返す。HTML の文字列を作る処理は無い。

### 数値

数値のキーには、数を 1 つではなく配列で保存する。1 つの欄に部位ごとの数が並ぶデータが多く、1 つしか置けないと同じ事実を書式付きテキストと数値の 2 か所に書くことになるためである。

- 各数には「何の数か」と「但し書き」を任意で付ける。どちらも言語ごとに書く翻訳の組で、表示中の言語のほうを表示する。1 つの欄に部位や疾患ごとの数が並ぶと、英語のページに日本語の「何の数か」が並ぶことになるためである。
- 幅のある値は、下限と任意の上限で表す。どちらも正準単位の値である。
- 入力した単位での値も残し、画面はこちらを表示する。換算が誤っていたと分かったときにやり直すためである。
- 換算は `app/content/units.ts` の 1 か所だけで行う。データ量も配列長も 1000 刻み (SI) で換算する。正準単位の無いキー (個数を数えるもの) は、入力した単位をそのまま使う。

### 一覧の要約

研究一覧の行に出す要約 (`listingSummary`) は、研究の詳細から導出せず、admin が書く。

- 解析手法・データの種類・参加者の列は、詳細を足し合わせた表記や分類語であり、詳細の値とは形が違う。導出した初期値を置くと、admin が書いた値と区別が付かなくなる。
- 提供者の列だけは例外で、空なら研究代表者の名前を表示し、書けばそちらを表示する。名前が 1 つも無い要素は、保存のときに除く。

### 公開用の表示データ

公開用の表示データは、研究の内容から公開してよい部分だけを残したものである。`app/content/public.ts` の純関数で作る。

- 公開ページ、共有リンクのプレビュー、編集画面の隣の公開ページは同じ関数を使う。違いは未確定の値を残すかどうかの引数だけで、公開ページの処理からはこの引数を渡せない。提供者がプレビューで見ている内容が、そのまま公開される内容であるようにするためである。
- 公開用の表示データは値を除くだけで、項目名も構造も値の表し方も変えない。そのため戻り値の型は研究の内容の型と同じである。
- 除くのは、未確定の値 (プレビューでは残す) と、研究ごとの prefix の一覧に無いファイルの選択である。項目定義のキーは、どれも公開ページに表示する。
- 入力は、研究の内容・制限公開データの利用者・研究ごとの prefix の一覧・アーカイブの日付で、関数が自分で外部を呼ぶことはない。表示の処理が外部の可用性に左右されないようにするためである。
- データセットの日付はここで 1 つに決め、後の処理では判断しない ([日付](#日付))。

## 実体と ID

研究とデータセットは実体 ([concepts.md](concepts.md)) として作り、研究 ID・データセット ID・バージョン番号は後から割り当てる。

- 実体は ID が無くても作れ、ID を直しても参照が壊れない。管理画面の URL も実体の ID で作る。
- 研究 ID とデータセット ID は ID の割り当て表 (`label_pin`) に置き、種類と文字列の組で全体で一意である。primary の ID と secondary の ID を合わせて一意になる。バージョン番号は研究の中でだけ一意なので、バージョンの行に置く。
- 研究が公開されているかは、公開中のバージョンがあるかで判定し、番号の大小では判定しない。番号には欠番があり得る。
- 割り当てを外した ID は再利用できる。研究 ID は申請管理システムに人が入力する文字列が元で、入力の誤りの訂正が日常の操作だからである。例外は NHA ID である。
- 1 つの実体に複数の ID を割り当てられ、primary の ID は 1 つである。secondary の ID は、古い ID への外部からの参照をたどれるように残す。primary が 1 つであることは部分 unique index で守る。
- ID は割り当てた時点で表に載り、公開を待たない。同じ accession を 2 つの下書きで割り当てようとすると、2 つ目は拒否される。そのため、公開のときに実体をまとめる処理は要らない。下書きで作ったデータセットは、下書きを削除すると ID ごと消える。

### NHA ID

NHA ID は、ポータルが発行するデータセット ID で、`NHA` と 6 桁のポータル全体の通し番号 (`NHA000001`) である。

- 番号は再利用しない。割り当てを外しても、データセットが消えても、同じ番号は二度と発行しない。外に貼られたリンクが、知らないうちに別のデータセットを指さないようにするためである。
- admin は文字列を選べず、発行を頼むだけである。この形の文字列を手で割り当てることはできない。
- 次の番号は、ID の割り当て表と操作の記録の両方にある最大の番号の次である。番号は研究もバージョンも表さない。
- 研究 ID で始まるデータセット ID (`hum0014.v1.freq.v1`) も、ポータルが付けた ID である。こうしたデータセットには NHA ID が primary の ID としてあり、研究 ID で始まる ID は secondary の ID として残っている。

### データセット ID から判定すること

データセット ID の文字列から判定するのは、ポータルが発行したものかどうかの 1 点だけである。

- primary の ID が `NHA` と 6 桁に完全に一致するか、`hum` で始まるなら、ポータルが発行したものとする。secondary の ID は見ない。研究 ID で始まる古い ID が secondary の ID として残っているためである。
- primary の ID がまだ無いデータセットは、外部のものとして扱う。
- この判定で、ファイルを選択できるか ([files.md](files.md)) と、日付をどこから取るか ([日付](#日付)) が決まる。バージョン番号など、それ以外の構造は ID から判定しない。

### データセットの所属と削除

データセットは 1 つの研究に属し、データセットの行の `research_id` が所属を表す。バージョンや下書きでデータセットを選んで載せる操作は無い。

- 研究にあるのは、公開済みのデータセットと、どれかの下書きで作成してまだ公開していないデータセットである。下書きに置くのは、データセットの順 (`datasetIds`) とデータセットの内容だけで、「載せる・載せない」の選択は無い。
- バージョンには載せた全データセットの内容を保存するが、公開ページが各データセットの内容を表示するときは検索用の行 (最新のバージョンのデータセットの内容) を読む。過去のバージョンのページでも同じである。
- データセットが公開中なのは、最新のバージョンに載っていて、primary のデータセット ID があるときである。バージョンのページに出るのは、そのバージョンに載っていて、今も公開中のデータセットである。
- データセットの削除は研究からデータセットを消す操作で、公開を待たずに反映される。ID の割り当てごと消え、検索用の行を作り直すので、公開ページからその場で消える。過去のバージョンの内容には残るが、表示はされない。
- 関連論文から指すデータセットは所有ではなく引用である。この研究のデータセットは実体の ID で、それ以外 (他の研究のもの、ポータルに無い accession) は書かれた ID の文字列で研究の内容に置き、表示するときに ID の割り当て表を引く。

## 値の状態 (未確定・該当なし・未翻訳)

値の状態の意味は [concepts.md](concepts.md) にあり、ここでは保存の形と表示の決まりを書く。

- 公開の単位は研究のバージョンで、言語ではない。1 つのバージョンに日本語と英語の両方が入り、片方の言語が未翻訳のままでも公開できる。英語の内容が無い研究が実在するためである。代わりに、公開前の確認で未翻訳を一覧に表示する。
- 項目は次の 3 種類に分かれ、どれに当たるかは研究の内容の型で決まる。
  - 単一の値: 言語の区別が無い (数値、語彙の値、accession、論文の題名)。
  - 翻訳の組: 言語ごとに表記がある (本文、機関名、研究課題名、数値の「何の数か」と「但し書き」)。
  - 言語ごとに別のものを指す値: URL だけである。
- 単一の値から翻訳の組への変更は機械的に行えるので、迷う項目は単一の値にしてよい。
- 両方の言語に同じ値をコピーしない。翻訳済みと判定されてしまうためである。
- 状態は言語ごとに決め、値の中の 1 か所にだけ置く。片方の言語だけが未確定の値が実在するためである。
- 空は状態ではなく、「値があって中身が空」である。必須の検査は空を見る。未確定は、admin が「提供者に問い合わせている」ことを示すために明示的に選ぶ。
- 公開前の確認で一覧に表示するのは未確定だけで、該当なしは表示しない。
- 未翻訳は値から決まる。翻訳の組で両方の言語に値があり (未確定でも該当なしでもない)、片方だけが空のときである。状態が食い違う (日本語に値、英語が未確定) ときは未確定として数え、同じ不足を公開前の確認で 2 度表示しない。
- 該当なしの表示文字列は値として保存せず、表示する側で作る。
- 公開ページでは、未確定と空の値を表示せず、該当なしは「該当なし」と表示する。プレビューでは未確定を提供者への問い合わせとして表示する。検索と絞り込みに入るのは、値があるもの (未確定でも該当なしでもない) だけである。

### 表示する言語

どの言語の値を表示するかは `app/i18n/locale.ts` で決める。表示中の言語の状態を先に見る。

- 該当なしと未確定は、もう一方の言語にフォールバックしない。
- 空の翻訳の組は、もう一方の言語の値を代わりに表示し、未翻訳であることを添える。
- URL はフォールバックしない。読者を別の言語のページへ送ることになるためである。

## 項目定義と語彙

データセットと解析手法の値のキーは、項目定義 (`content_key`) で決める。キーには、付く先 (データセットか解析手法か)、日本語と英語の表示名、値の型、表示順がある。

- キーの名前の変更は表示名の変更で、研究の内容は変わらない。研究の内容はキーを ID で指すためである。
- キーの追加は明示的な操作である。入力した文字列がそのまま項目定義に加わる経路は無い。編集画面からも、データ提供申請の取り込みからも、キーと語彙の値は作られない。
- admin が画面で追加・削除できるのは、解析手法の自由記述のキーだけである。名前の変更と並べ替えは、解析手法のキーなら型によらずできる。データセットのキーと、型が語彙・数値・疾患のキーの追加・削除・型の変更は、開発の作業である。これらのキーは絞り込みになり、集計と入力欄が必要になるためである。
- キーの名前は公開ページの表の見出しで、型のあるキーでは絞り込みの項目の名前でもある。名前は次のように書く。
  - 見出しは単数形で書く。値が複数あることは見出しで言わない。
  - 単位は入れない (`Read length (bp)` ではなく `Read length`)。数値は入力された単位のまま表示するため (`73 TB`)、見出しに単位を書くと値と食い違う。
  - 「〜の別」「〜の単位」は使わず、値を表す名詞で書く。有無を表すキーは「〜の有無」とする。
  - 括弧は半角で、前後に半角の空白を置く (`カバレッジ (深度)`)。
  - 型のあるキーの英語は文頭だけ大文字にし、略称と固有名詞の表記はそのまま残す (`Disease (ICD-10)`)。自由記述のキーはアーカイブ名を含むことがあるため (`Sequence Read Archive Accession`)、この規則を当てない。
  - 日本語と英語は同じものを指す。
  - このうち括弧・単位・「〜の別」と、型のあるキーの英語の大文字は、キーの追加と名前の変更のときにサーバーが確かめてエラーにする (`app/admin/catalog.ts` の `keyLabelProblem`)。
- 語彙と疾患の型のキーは常に絞り込みの項目になり、数値の型のキーは絞り込みのカテゴリ ([concepts.md](concepts.md)) が設定されたものだけが絞り込みの項目になる。絞り込みに使うかどうかはカテゴリの有無で表し、別の列は無い。公開日と更新日はキーではないが、絞り込みに出る。
- キーと語彙の値の code は検索の URL に出る (`?q=platform:hiseq-2500`)。そのため英語の表示名から機械的に作り、admin には入力させない (`app/admin/catalog.ts` の `codeFrom`)。同じ code があれば末尾に番号を付ける。組み込みの検索フィールドと同じ文字列は使えない。ICD10 だけは、code が規格のコードそのものである。
- 語彙の値の表示名は、英語が必須で日本語は任意である。日本語が空でも未翻訳に数えない。同じ語彙の中でも、日本語で書かれるかどうかが値ごとに違うためである。

### 画面から編集できる語彙

admin が編集するのは、データとともに増える語彙 (プラットフォーム、組織など) だけである。

- 値の集合がポータルの仕様として決まっている語彙 (公開区分、性別などの排他的な分類) と ICD10 は、画面から編集できない (`app/admin/catalog.ts` の `SETTLED_VOCABULARIES`)。ICD10 の見出し語は外部の規格で決まるためである。編集できない語彙も DB に置く。検索用の行が語彙の値の ID を参照するためである。
- 使われているキーと語彙の値は削除できない。公開中のデータセットか下書きの内容が、そのキーに値があるか、その語彙の値を指していれば、使われているとする。
- 語彙の値には、記事 ([site-content.md](site-content.md)) を 1 つ指定できる。公開ページは、その値の表示名を記事へのリンクにする。利用ポリシーの値から、ポリシーの本文を書いた記事へリンクするのに使う。記事は slug ではなく記事の ID で指すので、slug を変えてもリンクは切れない。記事を削除すると指定が外れる。
- 使われている語彙の値を整理するときは統合を使う。指している値を全部統合先へ書き換えてから、元の値を消す。統合できるのは同じ語彙の中だけである。
- 統合では、過去のバージョンの内容も書き換える。語彙の値は研究の内容そのものではなく、研究の内容が指す先だからである。語彙の値に「選べない」状態は無い。
- 項目定義や語彙を書き換えたら、検索用の行を全部作り直す。どの変更が行に反映されるかを操作ごとに判断すると、判断を誤った操作だけが反映されなくなるためである。例外はキーの並べ替えだけで、この判断は項目定義の書き込みをまとめた 1 か所に置く。

### 語彙の形

語彙には原則として階層が無く、階層があるのは ICD10 だけである。

- ICD10 は 3 桁の分類を根、4 桁をその子とする 2 層である。絞り込みの件数は根で数える。
- 製品を指す語彙の値は、会社名を `maker` 列に分けて置く。会社名を親にすると、絞り込みの一覧に会社名が並んでしまう。表示名は会社名を含んだ全体のままで、分けて使うのは表示するときだけである。
- 1 つの語彙の値は 1 つのものを指す。
- 表示順 (`position`) は編集フォームの候補と一覧のセルで使い、絞り込みの一覧は件数の順に並べる。

## 疾患 (ICD10)

疾患の値は、語彙の値への参照の列 (0 個以上) と、呼称 (日本語と英語) でできている。

- 参照が 1 つも無い値は正しい状態である。分類に載っていない疾患が実データにあるためである。
- 呼称は値に、見出し語は語彙の値に置く。同じコードが研究ごとに違う集団の定義として書かれるので、呼称を語彙に寄せると区別が失われるためである。表示は、呼称があれば呼称、無ければ見出し語である。
- 1 つの値は複数の分類の語彙の値を指せる。分類を足しても値の形は変わらない。
- コードは 3 桁と 4 桁だけを使う。移行も申請からの下書きの作成も、同じ正規化 (`app/icd10/codes.ts`) を通し、語彙にあるコードになるまで末尾を削る。3 桁を 4 桁へ広げることはしない。書いた人が選ばなかった細分を補わないためである。
- 分類そのものが語彙である。`npm run icd10:import` が 3 桁と 4 桁の全コードを語彙 `icd10` に入れ、別の辞書は置かない。再取り込みは code で照合して上書きし、語彙の値の ID は変わらない。
- 英語の見出し語は WHO の ICD-10 (Version 2019)、日本語は e-Stat の基本分類から取る。日本語にしか見出し語が無いコードは、英語の欄にも日本語の見出し語を置く (英語は必須のため)。英語にしか無いコードは日本語の欄を空にし、表示するときに英語の見出し語を使う。
- 参照が無い値は絞り込みの行を作らない。ただし呼称は全文検索に入るので、キーワードでは見つかる。

## 検索用の行

何が公開されているかの判定は、検索用の行 (`search_doc` と絞り込みの行) だけで行う。公開画面・JSON API・公開検索は、対象の集合も本文もこの行から読む。

- 行は公開に関わる操作でしか作られないので、編集中の値が公開側に現れる経路は無い。
- 行には、研究の内容かデータセットの内容 (公開用の表示データではない)、全文検索の列、語彙の絞り込みの行、数値の絞り込みの行を置く。内容をそのまま置くのは、admin が「このキーはまだ使われているか」を調べるときに、公開済みの内容を対象にするためである。
- 公開・更新・取り下げ・ID の割り当てと解除・データセットの削除・外部データの更新・項目定義の変更と同じトランザクションで作り直す。「まだ反映されていない」状態は存在しない。
- 行が消える経路は「作り直す」の 1 つだけで、取り下げや削除のための専用の処理は無い。
- 作り直しの関数は `app/search/rebuild.server.ts` の 1 つで、範囲は研究単位か全件である。全件の作り直しは普段の操作として使え、2 度作り直しても同じ行になる。
- データセットの行は、最新のバージョンのデータセットの内容から作る。研究の行には、配下の公開中のデータセットの全文と絞り込みの値の和集合を置く。研究一覧での絞り込みの意味は [public-site.md](public-site.md) の「絞り込み」にある。
- 語彙の値の表示名は行に書かず、検索のときに join で引く。ICD10 の上位のコードでの絞り込みは、行に置いた祖先の ID の列で行う。

### 全文検索

全文検索の列は、公開用の表示データから作る。公開用の表示データに出ない文字で行が見つかることが、構造的に起きないようにするためである。

- 語彙の値の code と両言語の表示名、疾患の呼称、研究 ID とデータセット ID を足す。ID は secondary の ID も足す。secondary の ID は、開けば primary の ID のページへリダイレクトされる公開の ID で、古い ID で探す読者がいるためである。
- 画面に文字として出ない値 (実体の ID、状態、リンク先、換算前の入力、ファイルの選択) は入れない。
- ファイル名は入れない。名前の正本はファイルストアの研究ごとの prefix にあり、入れると作り直しがファイルストアの可用性に左右されるためである。
- 絞り込みの行は、データセットの内容から作る。未確定と該当なしの値は入れない。
- 索引は PGroonga の n-gram (`TokenNgram`、`NormalizerNFKC150`) である。accession の途中での一致と日本語の部分一致の両方が要るので、形態素解析は使わない。
- 全文検索の列は、日本語と英語の列を連結した生成列である。全文検索の条件は `WITH ... AS MATERIALIZED` の中に置く。プランナが nested loop の内側で条件を評価し直すのを防ぐためである。

## 外部から取ってきたデータ

他のシステムが正本の値は、Postgres のキャッシュ用の表に置き、読む処理はキャッシュだけを見る。

- 取得元は 4 つある (`app/upstream/sources.ts`)。制限公開データの利用者 (CAU)、研究 ID と JGA の accession の対応、JGAD の日付の 3 つを申請管理システムの DB から、それ以外のアーカイブ (DRA、GEA、MetaboBank、BioProject) の日付を DDBJ Search から取る。
- 取得元が止まっても公開ページは表示できる。キャッシュは取り直せるので、バックアップの対象にしない。
- キャッシュに入れてよいのは、そのまま公開ページに出る値だけである。申請の中身 (連絡先、住所、申請書の本文) は持ち込まない。例外は照合のためのキー (利用課題の番号) で、公開用の表示データにも API にも出さない。
- CAU は研究の内容ではないので、値の状態が無く、未翻訳にも数えない。1 行は 1 つの利用課題で、人ごとにまとめない。
- CAU の国名は、申請者が英語で自由に書いた文字列を、ポータルの国名の表 (ISO 3166 の国コードごとの日本語名と英語名、`app/upstream/country.ts`) に照らして両言語の名前にする。表で分からない国名は、書かれた文字列のまま両言語に出す。訳せない国を一覧から除くより、英語のまま出す方がよいためである。
- 州は、米国・カナダ・オーストラリアのときだけ国名に添え、それ以外の国では表示しない。この 3 国では州が個人データの利用について独自の法を定めるので、州が利用の条件を表すためである。表で分からない州は出さない。欄には州の代わりに選択肢の既定値などが入っていることが多いためである。
- 研究 ID と accession の対応の正本は申請管理システムで、ポータルの ID の割り当ては正本ではない。食い違いは公開前の確認で一覧に表示する ([publishing.md](publishing.md))。
- キャッシュに入るのは公開済みの accession だけである。申請から下書きを作る処理はキャッシュを読まず、その都度申請管理システムを読む。
- 更新は取得元ごとに行い、それぞれ独立に失敗する。失敗した取得元は前回の値を残す。一時的に応答しないことと値を消したことを区別できず、消した側として扱うと公開ページが空になるためである。
- 成功した取得元だけを全件置き換え、同じトランザクションで検索用の行を作り直す。今回返らなかった行は消える。
- 取得元ごとに、最後に試した日時・最後に成功した日時・件数・直近の失敗の理由を記録し、`/admin` に表示する。
- 申請管理システムの DB への接続は read-only を強制する。接続の設定が無い環境では、この DB から取る 3 つを飛ばす。

## 日付

日付は admin が設定するものとして保存し、操作の記録からは作らない。取り下げて再公開することも、同じ番号で更新することもあるためである。書式は `YYYY-MM-DD`、日付の区切りは日本時間で、言語の区別は無い。

- バージョンの公開日は、公開の操作で今日を初期値にし、admin が変えられる。
- 研究の初公開日と最終公開日は、公開中のバージョンの公開日の最小と最大である。
- JGAD の公開日と更新日は、申請管理システムで公開の状態になった最初の日と最後の日である。
- 他のアーカイブのデータセットの公開日と更新日は、DDBJ Search が返す 2 つの日付をそのまま使う。取得元の日付をポータル側で補正しない。
- ポータルが発行した ID のデータセットは、初めて載せたバージョンの公開日を、公開のときにデータセットの内容へ書く。一度入った日付は後の公開では変えず、直すときは admin が編集する。更新日も同じ値にする。データセットにバージョンが無く、「更新」と呼べる出来事が無いためである。
- 取得元が正本の日付は、データセットの内容に保存しない。同じ事実の出所を 2 つにしないためである。
- 行の `updated_at` は、表示する日付に使わない。バージョンの `updated_at` は公開した時刻で、語彙の統合で内容が書き換わっても変わらない。

## DB に置かないもの

次のものは、意図して DB に置いていない。

- データセットの履歴と解析手法のバージョン。データセットの内容の訂正は研究のバージョンの更新で行い、分けても ID を割り当てる対象が 1 階層増えるだけである。
- 解析手法の行。データセットの内容の中の要素で足り、集計は検索用の行で行う。
- 公開の状態を表す列。バージョンの行があることが公開中であることを意味する。
- バージョンの一覧や最新の番号を別に置く列 (`versionIds`、`latestVersion` など)。ID の割り当て表とバージョンの行から導出できるので、置くと二重管理になる。
- 書式付きテキストの中の見出し・表・箇条書き・強調・生の HTML。書けるものの範囲を型で決めるためである。
- 申請の中身 (氏名、連絡先、住所)。個人情報を DB に置かないためで、必要なときは申請管理システムをその都度読み、キャッシュしない。
