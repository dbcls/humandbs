# 申請支援アシスタント

申請支援アシスタントは、データ提供の申請書と添付書類を解析して確認結果を作るツールである。ポータルとは別のサービス (`assistant-api/`) として動き、管理画面から使う。この文書には、ポータルとの境界だけを書く。アシスタントが何をどう調べるかは `assistant-api/` のドキュメントに、起動の手順は [development.md](development.md) にある。

## 呼び出し方

アシスタントには認証も認可も無いので、アシスタントを呼ぶときは、必ずポータルの 1 つの route を通す。アシスタントは compose のネットワークの中だけで動き、port を外部に公開しない。

- 誰が使えるかはポータル側で判定する。`/admin/assistant/api/…` の route (`app/routes/admin-assistant-api.ts`) が、`use-assistant` の権限 ([auth.md](auth.md)) を確かめてからリクエストを中継する。
- ポータルの他の場所からはアシスタントを呼ばない。アシスタントにリクエストを送るのは、中継のモジュール (`app/assistant/proxy.server.ts`) だけである。画面は中継の route の URL を使う。画面のコードにはサービスの URL を書かず、画面にサービスの URL を渡すこともない。
- 上の 2 つの決まりが守られないと、アシスタントは誰でも使える無認証の API になる。そのため、`app/assistant/boundary.test.ts` で、ソースを読んで確かめている。
- ポータルの資格情報は渡さない。リクエストからは、セッションの cookie と `Authorization` ヘッダを取り除く。応答の `Set-Cookie` も取り除く。`Set-Cookie` を残すと、アシスタントの cookie がポータルの origin に設定されてしまうためである。
- 他のサイトからのリクエストは拒否する。書き込みのリクエストは、ポータル全体の検査 ([auth.md](auth.md) の「CSRF」) が先に 403 にする。読み取りのリクエストでも、ブラウザが別のサイトから来たと示すとき (`Sec-Fetch-Site` が `same-origin`・`none` 以外) と、`Origin` が別のホストを指しているときは、中継の route が 400 を返す。API の形はアシスタント側で決まるもので、読み取りが何も変えないとは限らないためである。
- パスに `..` の区切りを含むリクエストは拒否する。アシスタントは、中継の route からしか呼ばれないことを前提に書かれているためである。
- パス・body・status は、そのまま中継する。ポータルのコードにも設定にも、アシスタントのエンドポイントを書かない。エンドポイントが増えても、ポータルを変えずに済むようにするためである。
- 中継の URL は `app/admin/urls.ts` の `assistantApiPath()` で作る。管理画面の URL には言語の prefix が無い。
- アシスタントのリダイレクトは、そのまま返す。相対の `Location` は、ポータルの URL として解決される。そのため、アシスタントはリダイレクトを返さないか、`Location` を中継の URL で書く。
- アシスタントが動いていないときは、画面に動いていないことを表示する。`HUMANDBS_ASSISTANT_ORIGIN` が空の環境だけでなく、設定されていても応答しないとき (container を止めたとき、起動の途中) も、同じ表示にする。アシスタントの無い環境を壊れた環境として扱わないためと、アシスタントを起動・停止するたびにポータルを作り直さずに済むようにするためである。
  - 画面を開くたびに、中継のモジュールがアシスタントのアドレスの root に `HEAD` を送り、数秒のうちに応答が返るかだけを調べる。status は問わない。root はアシスタントのエンドポイントではないので、ポータルのコードにも設定にも、エンドポイントを書かずに済む。画面が受け取るのは動いているかどうかだけで、アドレスは受け取らない。
  - 中継の route は、`HUMANDBS_ASSISTANT_ORIGIN` が空なら 503、設定されていて応答しなければ 502 を返す。画面を開いたあとにアシスタントが止まったときは、操作が 502 になる。

## 大きさと時間の上限

中継するリクエストの body の大きさと待ち時間の決まりである。

- body の大きさに上限を設けない。申請書の PDF は 1 MB を超えるので、この経路ではリバースプロキシの上限を外している (`docker/nginx/default.conf`)。他に上限を外しているのは、ファイルのアップロードを通す経路だけである。
- 1 つのリクエストで、応答の最初の 1 バイトが返るまでの上限は 5 分で、超えると 502 になる。ポータルの HTTP client が 5 分で待つのをやめるので、前段のタイムアウトを延ばしても変わらない。
- 5 分を超える処理を 1 つのリクエストで行わない。リクエストを受け付けて ID を返し、進み具合を別のリクエストで取得する形にするか、途中経過を送り始める形にする。

## 外への通信の制限

アシスタントが外部から取得する URL は、申請書と検索結果から来るので、内部のサービスを指定されることがある。そのため、アシスタントは宛先を検査してから接続する (`assistant-api/src/url_guard.py`)。

- 接続を許すのは http と https だけである。ホスト名を 1 回だけ名前解決し、得たアドレスが 1 つでもグローバルでなければ拒否する。接続には、解決したそのアドレスを使う。名前解決をやり直すと、DNS rebinding で別のアドレスに接続されるおそれがあるためである。
- リダイレクトでは、1 回ごとに同じ検査を行う。Playwright で開くページについては、ページが出すすべてのリクエストを検査する。
- ネットワークでも、アシスタントを分けている。`assistant-api` が同じネットワークにいるのは `app` だけで、アシスタントは DB とファイルストアには接続できない ([deployment.md](deployment.md))。

## 役割分担

ポータルは URL、認可、管理画面のレイアウト、部品を担当し、アシスタントは画面の中身、API、申請書の解析、外部サービスとの通信、自身の状態を担当する。

- 画面はアシスタント側が書き、ポータルの部品で組み立てる ([development.md](development.md) の「画面の規則のテスト」)。
- ポータルのデータは、公開 API ([public-api.md](public-api.md)) から読む。公開 API は認証が要らないので、資格情報を渡さずに済み、ポータルの DB に接続する経路も作らない。
- アシスタントの状態は、アシスタントの中だけで管理する。申請書と解析の途中結果は、container の `work/` (名前付き volume) に保存し、ポータルの PostgreSQL にもファイルストアにも入れない。失っても申請書をもう一度アップロードすればよいので、backup の対象にしない。

## やっていないこと

- アシスタントに認証を付けること。ポータルが前段で認可するので、2 つ目の認可があると結果が 2 通りになる。
- アシスタントの API をポータル側で型付けすること。API の形はアシスタント側で決まるもので、ポータルに型のコピーを書くと、エンドポイントが増えるたびに両方を直すことになる。
