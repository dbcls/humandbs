# 申請支援アシスタント

申請書とその添付を読んで、確認の材料を作る道具。ポータルの隣で動く別のサービスで、管理画面から
使う。ここに書くのは**ポータルとの境界**で、アシスタント自身が何をどう調べるかは
`assistant-api/` 側の doc にある。

## 境界

**アシスタントは認証も認可も持たない。** compose のネットワークの中だけで動き、port を外に出さない。
誰が使えるかを決めるのはポータル側で、`/admin/assistant/api/…` の proxy が `use-assistant` を
確かめてから要求を渡す ([auth.md](auth.md))。

不変条件は 2 つだけで、この 2 つが崩れるとアシスタントは無認証で誰にでも開いた API になる。
どちらも `app/assistant/boundary.test.ts` が source を読んで守る。

- **proxy は capability を確かめてから渡す** (`app/routes/admin-assistant-api.ts`)
- **ポータルの他のどこからもアシスタントを呼ばない。** 画面は proxy のアドレスを叩き、
  サービスのアドレスを知らない

**ポータルの資格情報は渡さない。** session cookie と `Authorization` は proxy が落とす。cookie は
ここではセッションそのものなので、渡せばアシスタントがポータルのセッションを読める場所になる。
帰りも同じで、`Set-Cookie` は落とす — アシスタントが置く cookie はポータル自身の origin に載る。

**よそのサイトから来た要求は渡さない。** `Origin` がポータル自身のホストと違えば 400 になる。
React Router は画面を持つ route の action に同じ検査をかけるが、データだけを返す route にはかけない。
ポータルの他の書き込みは形が分かっていて cookie も `SameSite=Lax` だが、**ここは形がアシスタントの
もの**なので、ポータルに当てられる検査は当てておく。

**API の形はアシスタントのもの。** proxy は道のり・body・status を素通しする。ポータルはどんな
endpoint があるかを知らないので、アシスタントが endpoint を増やしてもポータルは変わらない。

## 素通しの境目

**4 つだけある。** どれもポータル側の都合で、アシスタントの API の設計に効く。

| | |
|---|---|
| **道のり** | `..` を節に持つ道のりは 400。アシスタントは「ここからしか呼ばれない」前提で書かれているので、他のアドレスに手が届く経路を作らない |
| **method** | `GET` / `HEAD` / `POST` / `PUT` / `PATCH` / `DELETE` が届く。`OPTIONS` はフレームワークが自分で答え、それ以外の綴りは 405 で止まる。同じ origin なので preflight は起きない |
| **body の大きさ** | 上限なし。申請書の PDF は 1MB を超えるので、`/admin/assistant/api/` だけ前段の上限を外してある (`docker/nginx/default.conf`)。サイトの他のところは 1MB のまま |
| **時間** | **1 つの要求で、応答の 1 バイト目までが 5 分。** 超えると 502 になる |

**5 分は動かせない。** ポータルが使う HTTP client がそこで待つのをやめるので、前段の timeout を
伸ばしても変わらない。**5 分を超える処理を 1 つの要求で持たない** — 受け付けて id を返し、進み具合を
別の要求で取りに来るか、途中経過を流し始める。流し始めていれば、そのあと何分かかってもよい。

**アドレスに言語の prefix は付かない。** 画面は `/ja` と `/en` の下にもあるが、proxy は 1 つだけ
登録されている。`/en/admin/assistant` を開いた画面から相対のアドレスで叩くと 404 になるので、
**アドレスは `app/admin/urls.ts` の `assistantApiPath()` から取る**。

**redirect はそのまま返る。** `Location` を相対で書くとブラウザはポータルの側で解決するので、
`/api/…` はポータルの public API を指してしまう。アシスタントは redirect を返さないか、
proxy のアドレスで書く。

## 責務

| | 持つもの |
|---|---|
| ポータル | アドレス (`/admin/assistant` と `/admin/assistant/api/*`)、認可、画面の器、部品 |
| アシスタント | 画面の中身、API、申請書の解析、外部サービスとのやりとり、自分の state |

**画面はアシスタント側が書き、ポータルの部品で組む。** 見た目の規則は [ui.md](ui.md) にあり、部品は
`app/components/` にある。管理画面の幅・余白・押せるものの大きさは区画の側が決めるので、画面が
書くことは無い ([ui.md](ui.md) の「幅」)。

**ポータルのデータはアシスタントが public API から読む。** 認証が要らないので資格情報を渡す必要が
なく、ポータルの DB に触る経路も作らない ([public-api.md](public-api.md))。

## state

**アシスタントは自分のファイルシステムに置く。** 申請書と解析の途中結果はアシスタントの中で完結し、
ポータルの Postgres にも S3 にも入らない。**置き場は container の中の `work/`** で、これは名前付きの
volume なので repo には何も溜まらない。

失えばやり直しになるが、それはもう一度読ませれば済むもので、ポータルのデータではない。backup の
対象にしない。

## 動かす

サービスは profile の後ろにいる。先にリポジトリ直下の `.env` で、ポータルがアシスタントへ届くよう
`HUMANDBS_ASSISTANT_ORIGIN` を設定する。compose network 内では次の値になる。

```dotenv
HUMANDBS_ASSISTANT_ORIGIN=http://assistant-api:8000
```

使う外部サービスの値は、`.env.example` の `HUMANDBS_ASSISTANT_` で始まる変数に設定する。対応関係は `.env.example` のコメントにある。

Google Cloud のサービスアカウント鍵の設定は [assistant-api/README.md](../assistant-api/README.md#google-cloud) を参照する。

上記設定の完了後、以下のコマンドでアシスタントを起動する。

```bash
docker compose --profile assistant up -d
```

`.env` の `HUMANDBS_ASSISTANT_ORIGIN` が空のままなら、**画面は「動いていません」と言う**。
申請管理システム DB と同じ形で、無い環境が壊れた環境にならないようにしてある
([development.md](development.md))。

## 意図的にやっていないこと

| やらないこと | 理由 |
|---|---|
| アシスタントに認証を持たせること | ポータルが前に立つので、2 つ目の認可があると答えが 2 通りになる |
| アシスタントの port を外に出すこと | proxy を迂回する経路になる |
| API を型で受けること | 形はアシスタントのもの。ポータルが写しを持つと、増えるたびに両方を直すことになる |
| state をポータルの DB に持つこと | 移植の範囲を越える。ポータルのデータではない |
| アシスタントからポータルの DB を読ませること | public API で足りる。認証が要らないので資格情報も渡らない |
| 5 分より長く待てるようにすること | 待つのをやめる場所を伸ばすより、長い処理を分けるほうが画面も作りやすい |
