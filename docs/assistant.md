# 申請支援アシスタント

申請支援アシスタントは、データ提供の申請書と添付書類を解析して確認結果を作るツールで、ポータルとは別のサービス (`assistant-api/`) として動き、管理画面から使う。ここにはポータルとの境界だけを書く。アシスタントが何をどう調べるかは `assistant-api/` のドキュメントに、起動の手順は [development.md](development.md) にある。

## 呼び方

アシスタントには認証も認可も無いので、ポータルの 1 つの route を通してだけ呼ぶ。アシスタントは compose のネットワークの中だけで動き、port を外に公開しない。

- 誰が使えるかはポータル側で判定する。`/admin/assistant/api/…` の route (`app/routes/admin-assistant-api.ts`) が `use-assistant` の権限 ([auth.md](auth.md)) を確かめてから要求を中継する。
- ポータルの他の場所からはアシスタントを呼ばない。画面は中継の route の URL を使い、サービスの URL を知らない。
- この 2 つの決まりが崩れると、アシスタントは誰でも使える無認証の API になる。そのため `app/assistant/boundary.test.ts` がソースを読んで確かめている。
- ポータルの資格情報は渡さない。セッションの cookie と `Authorization` ヘッダを取り除き、応答の `Set-Cookie` も取り除く。アシスタントの cookie がポータルの origin に設定されてしまうためである。
- 他のサイトからの要求は拒否する。書き込みはポータル全体の検査 ([auth.md](auth.md) の「CSRF」) が先に 403 にし、読み取りでも `Origin` が別のホストを指していれば中継の route が 400 を返す。API の形はアシスタント側で決まるもので、読み取りが何も変えないとは限らないためである。
- パスに `..` の区切りを含む要求は拒否する。アシスタントは中継の route からしか呼ばれないことを前提に書かれているためである。
- パス・body・status はそのまま中継し、ポータルはアシスタントのエンドポイントを知らない。エンドポイントが増えてもポータルを変えずに済むようにするためである。
- 中継の URL は `app/admin/urls.ts` の `assistantApiPath()` で作る。管理画面の URL には言語の prefix が無い。
- アシスタントのリダイレクトはそのまま返す。相対の `Location` はポータルの URL として解決されるので、アシスタントはリダイレクトを返さないか、中継の URL で書く。
- アシスタントが起動していない環境では 503 を返し、画面に動いていないことを表示する。アシスタントの無い環境を、壊れた環境として扱わないためである。

## 大きさと時間の上限

中継する要求の body の大きさと待ち時間の決まりである。

- body の大きさに上限を置かない。申請書の PDF は 1 MB を超えるので、この経路ではリバースプロキシの上限を外している (`docker/nginx/default.conf`)。他に上限を外しているのは、ファイルのアップロードを通す経路だけである。
- 1 つの要求で応答の最初の 1 バイトが返るまでの上限は 5 分で、超えると 502 になる。ポータルの HTTP client がそこで待つのをやめるので、前段のタイムアウトを延ばしても変わらない。
- 5 分を超える処理を 1 つの要求で行わない。受け付けて ID を返し、進み具合を別の要求で取得する形にするか、途中経過を送り始める形にする。

## 外への通信の制限

アシスタントが外部から取得する URL は申請書と検索結果から来るので、内部のサービスを指定されることがある。そのため宛先を検査してから接続する (`assistant-api/src/url_guard.py`)。

- 通すのは http と https だけである。ホスト名を 1 回だけ名前解決し、得たアドレスが 1 つでもグローバルでなければ拒否し、接続には解決したそのアドレスを使う。名前解決をやり直すと、DNS rebinding で別のアドレスに接続されるおそれがあるためである。
- リダイレクトは 1 回ごとに同じ検査を通す。Playwright で開くページについては、ページが出すすべての要求を検査する。
- ネットワークでも分けている。`assistant-api` が同じネットワークにいるのは `app` だけで、DB とファイルストアには接続できない ([deployment.md](deployment.md))。

## 役割分担

ポータルは URL、認可、管理画面のレイアウト、部品を担い、アシスタントは画面の中身、API、申請書の解析、外部サービスとの通信、自身の状態を担う。

- 画面はアシスタント側が書き、ポータルの部品で組み立てる ([development.md](development.md) の「画面の規則のテスト」)。
- ポータルのデータは公開 API ([public-api.md](public-api.md)) から読む。認証が要らないので資格情報を渡さずに済み、ポータルの DB に触れる経路も作らない。
- アシスタントの状態はアシスタントの中だけで管理する。申請書と解析の途中結果はコンテナの `work/` (名前付き volume) に保存し、ポータルの PostgreSQL にもファイルストアにも入れない。失っても申請書をもう一度アップロードすればよいので、バックアップの対象にしない。

## やっていないこと

- アシスタントに認証を付けること。ポータルが前段で認可するので、2 つ目の認可があると結果が 2 通りになる。
- アシスタントの port を外に公開すること。中継の route を迂回する経路になる。
- アシスタントの API をポータル側で型付けすること。API の形はアシスタント側で決まるもので、コピーを置くとエンドポイントが増えるたびに両方を直すことになる。
- アシスタントの状態をポータルの DB に置くこと。ポータルのデータではない。
- 5 分より長く待てるようにすること。長い処理は分けたほうが画面も作りやすい。
